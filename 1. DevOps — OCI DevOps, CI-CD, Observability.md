## OCI DevOps delivery model

### Named pipeline stages, in order

Course diagram gives the exact stage names/sequence behind the general
"compile/test then deploy" description below:

**Build Pipeline (CI):** Code Repository (triggered by a commit) → **Run
Build** → **Test Artifacts** → **Deliver Artifacts** — writes to **OCI
Artifact Repositories** (Container Registry for images/Helm charts, Artifact
Registry for generic packages — both already named below, now shown as the
literal build-pipeline output).

**Deployment Pipeline (CD):** **Deploy to staging environment** (pulls from
Container/Artifact Registry) → **Run Integration Tools** → **Approval** →
**Deploy to PROD**.

**Two things worth holding onto specifically:**
- **Approval is a named, discrete pipeline stage**, not just a general best
  practice — a manual gate built into the deployment pipeline model itself,
  sitting between integration testing and the production deploy.
- **Deploy targets are grouped as "OCI platforms"**: Compute hosts (VM and
  Bare Metal), Container Engine for Kubernetes (OKE), and Functions — the
  same three categories the "CodeDeploy" translation row below already
  lists, now with the actual grouping label the Console/diagrams use.

- A DevOps project groups repositories, build pipelines, artifacts, deployment pipelines, environments, and triggers.
- A managed build runs stages that compile and test code, then writes versioned outputs to OCI Container Registry (container images/Helm charts) or Artifact Registry (generic packages).
- Deployment pipelines promote a known artifact to OKE, instance groups, or Functions. Separate build and deployment responsibilities so the deployable version is traceable.
- External-repository tokens belong in Secret Management/Vault; authorize pipeline resources with IAM policies and dynamic groups.
- Build/deployment logs go to OCI Logging, and DevOps emits Monitoring metrics for successes, failures, and duration.

## Release strategy and controls

| Requirement | OCI pattern | Key design point |
| --- | --- | --- |
| Low-risk continuous rollout | Rolling deployment | Health checks and an explicit rollback criterion are still required. |
| Validate new version with a small audience | Canary deployment | Route/traffic design determines who receives the canary; deployment alone does not. |
| Fast rollback with parallel environments | Blue-green deployment | Requires duplicate capacity and controlled traffic switch. |
| Reproducible infrastructure | Terraform + Resource Manager | Store Terraform source/state appropriately, run plans before applies, and review drift. |
| Trace an outage across services | APM + Logging + Monitoring | APM is not a replacement for logs, alarms, or audit events. |

## Terraform / Resource Manager — syntax precision, not just IaC concepts

**Resource *type* is provider-specific; resource *name* is not — a real,
easy-to-conflate distinction.** Every resource block has two separate
naming layers:
```hcl
resource "oci_core_vcn" "lab_vcn" { ... }
        └────type────┘  └─name─┘
```
- The **type** (`oci_core_vcn`, `oci_containerengine_cluster`, etc.) genuinely
  **is** provider-namespaced — it maps directly to that provider's schema/API,
  which is why every OCI resource type carries the `oci_` prefix (confirmed
  across every stack in `terraform/`). You cannot reuse an OCI resource type
  with another provider.
- The **name** (`lab_vcn`) is an **arbitrary local label the author invents**
  to reference the resource elsewhere in config (`oci_core_vcn.lab_vcn.id`)
  — it has nothing to do with the provider at all, and Terraform doesn't
  validate it against any provider schema.

**The trap, confirmed by a real MyLearn skill-check miss**: a question asked
which statements about Terraform are **FALSE**, and one option read
"Resource names in Terraform are provider specific." This statement is
**false** — but it's easy to mark it *true* by unconsciously reading "resource
names" as "resource types." Terraform's own docs are careful to always say
"type" and "name" separately for exactly this reason; a statement that blurs
them under the generic word "name" is a real candidate for being the false
claim in a "spot the false statements" question.

**Two other facts from that same question, confirmed against this session's
own working `.tf` files:**
- **Provider aliases are real** — `provider "oci" { alias = "home" }`
  configures a second, distinctly-addressable provider instance (e.g. a
  different region/tenancy) alongside the default one, used directly in
  `lab-storage-stack`/`lab-oke-official-module-stack`.
- **Terraform CLI version and provider version are independent, separately
  declared fields** — `required_version` (CLI) and `required_providers { oci
  = { version = ... } }` (provider) are two uncoupled constraints in every
  stack's `versions.tf`, not one combined version requirement.

**Terraform is IaC, not IaaS — a category distinction, not trivia.**
Terraform is Infrastructure as **Code** tooling: it calls a provider's APIs
to create/manage infrastructure but hosts none of its own. IaaS
(Infrastructure as a **Service**, e.g. OCI Compute) means the *provider*
hosts infrastructure you consume. Stopping Terraform doesn't remove any
resource it created — it was never the thing running them, only the tool
that declared and applied their desired state.

## Observability

- Use **Monitoring** for metrics and alarms, **Logging** for service/application logs, **APM** for application traces and performance, and **Logging Analytics** for broader log analysis.
- Use **Events**, **Notifications**, and **Functions** for event-driven automation; limit responder permissions and make actions idempotent.
- Use **Audit** for who changed OCI control-plane resources, not as application trace telemetry.
- Define service-level objectives, dashboards, alert routes, and deployment gates before production rollout.
