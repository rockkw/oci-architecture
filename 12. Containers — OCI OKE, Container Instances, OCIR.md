## OKE architecture

- **Control plane**: fully managed by Oracle regardless of tier, comprising the
  standard Kubernetes control-plane components — `kube-apiserver`,
  `kube-scheduler`, `kube-controller-manager`, `cloud-controller-manager`, and
  `etcd` — all abstracted away entirely; you never provision, patch, or scale
  these yourself. Basic clusters have a free control plane (subject to
  account-type quotas); Enhanced clusters are a paid tier with additional managed
  features.
- **Basic vs. Enhanced — reliability commitment, not just feature set:** Basic
  clusters carry a **Service Level Objective (SLO)** — a stated reliability target
  with no financial remedy if missed. Enhanced clusters are the tier where the
  paid features live, but the exam-relevant distinction to hold onto is SLO
  (Basic) vs. an actual **financially-backed SLA** consideration entering the
  picture at Enhanced — don't reduce "Basic vs. Enhanced" to only a feature-list
  comparison; a design requiring a contractual reliability guarantee, not just a
  target, needs Enhanced regardless of whether Basic's feature set would otherwise
  suffice.
- **Concrete features Basic does not support at all** (Enhanced is a strict
  superset — nothing is Enhanced-only-missing):
  - **Virtual node pools** — the single most exam-relevant gap: a design that
    needs Virtual Nodes has already decided the cluster tier, independent of any
    other requirement.
  - Fine-grained cluster add-on deployment and configuration.
  - Workload identity.
  - Increased numbers of worker nodes (Basic has a lower worker-node ceiling than
    Enhanced, independent of the 20,000-node platform maximum noted above).
  - Financially-backed SLA (restating the SLO/SLA point above as a concrete list
    item, since it's exactly this list the exam is likely drawing from).
- **Creation defaults differ by tool — and this is easy to get backwards:**
  - **Console**: a new cluster defaults to **Enhanced**; you have to explicitly
    opt into Basic.
  - **CLI/API**: a new cluster defaults to **Basic**; you have to explicitly
    specify Enhanced to get it.
  - Creating as Enhanced up front is positioned as the easier path if you might
    ever want Enhanced features later — because of the next point:
- **Tier change is one-way: upgrade only, never downgrade.** You can upgrade a
  Basic cluster to Enhanced later, but you **cannot** downgrade an Enhanced
  cluster back to Basic once created. Same asymmetric-migration shape as Object
  Storage versioning (`Enabled` → can go `Suspended`, never back to fully
  `Disabled`) — a pattern worth recognizing generally: several OCI features are
  one-way doors once turned on, not toggleable back and forth. If a design might
  need Basic's lower cost/simplicity later, that has to be decided at creation
  time, not deferred.
- **Node pool types — three, not two:**
  - **Managed nodes** — standard OCI Compute VM or bare-metal instances organized
    into a **NodePool**. Explicitly **partly managed by customers**: Oracle
    orchestrates the pool (scaling, placement), but two node-level components are
    yours to understand as the actual working parts of each node — the
    **Kubelet** (the per-node agent that communicates with the control plane,
    reports node/pod status, and receives pod scheduling instructions) and the
    **container runtime** (what actually pulls images and runs containers on that
    node, e.g. containerd). This is the concrete "what does 'you own
    patching/lifecycle' actually mean" answer — it means the OS and these two
    components on each Compute instance.
  - **Virtual nodes** — the serverless option (see below), also organized into a
    **NodePool**, but Oracle-managed end to end.
  - **Self-managed nodes (Instance Pool)** — a **third, distinct pattern**: you
    bring your own OCI **Instance Pool** (the same Instance Pool resource covered
    in [[3. Compute — OCI Compute, Instance Pools, Load Balancers, Volumes]]) and
    join it to the cluster as worker nodes yourself, rather than letting OKE
    create/manage a NodePool resource for you. This is the "bring your own
    compute lifecycle" option — you own everything about the pool's
    provisioning/scaling (via the Instance Pool's own autoscaling config), OKE
    just accepts the nodes joining. Distinct from "Managed nodes" above: managed
    nodes are still an OKE-native NodePool resource that OKE orchestrates; a
    self-managed Instance Pool is your own independent Compute resource that
    happens to register with the cluster.
  - Shape/architecture choice matters for the exam: VM vs. Bare Metal, and **ARM (Ampere)** vs. **AMD/Intel** — including GPU shapes for ML workloads. A single cluster can mix architectures; pods target a specific architecture via `nodeSelector`.
- At current scale, OKE supports clusters up to 20,000 worker nodes and up to 256 pods per managed node — know the *existence* of hard scale limits for design questions, not necessarily the exact numbers.

### Supported images for Managed Nodes — a third image category

Beyond the platform/custom/BYOI split already covered in the "Images" section
above, Managed Nodes specifically have their own dedicated category:

- **OKE images**: Oracle-provided, **built on top of a platform image**, already
  configured with everything a node needs to join the cluster (kubelet,
  container runtime, required software). Distinct from a bare platform image
  or a self-customized one — this is Oracle pre-doing the OKE-specific
  customization for you.
- **Why pick an OKE image over a platform image**: **faster managed-node
  provisioning** during cluster creation and updates, since the node doesn't
  need to bootstrap OKE-specific configuration on first boot.
- **Naming convention**, worth being able to read directly rather than treating
  as an opaque string:
  ```
  <platform-image-name>-OKE-<kubernetes-version>-<OKE-build-number>
  ```
  Real example: `Oracle-Linux-8.7-Gen2-GPU-2023.01.31-3-OKE-1.25.4-549` — this
  is `Oracle-Linux-8.7-Gen2-GPU-2023.01.31-3` (the platform image) +
  `OKE-1.25.4-549` (Kubernetes 1.25.4, OKE build 549).
- **Query supported shapes/images via CLI**:
  ```bash
  oci ce node-pool-options get --node-pool-option-id all
  ```
  The direct CLI counterpart to the `oci_containerengine_node_pool_option`
  Terraform data source [[terraform/lab-oke-stack]] and
  [[terraform/lab-oke-gpu-stack]] both already use to look up a live node
  image instead of hardcoding one — this is genuinely the same query, just via
  CLI instead of `terraform plan`.
- **Custom images can also be used for Managed Nodes** — built on top of a
  supported platform image or OKE image, with your own tailored
  customizations. **Console cannot provision a managed node pool from a custom
  image at all — this requires CLI or API**, specifying the custom image's OCID
  directly via `--node-image-id`. A real tool-capability gap, not just a
  default/convenience difference (compare to the Basic/Enhanced
  Console-vs-CLI *default* asymmetry above — this one is Console literally
  lacking the capability, not just defaulting differently).
- **Full CLI shape for creating a managed node pool** (`oci ce node-pool
  create`), useful as the concrete, unabstracted view of what
  `oci_containerengine_node_pool` in Terraform is doing underneath:
  `--cluster-id`, `--node-image-id`, `--node-shape`, `--kubernetes-version`,
  and `--placement-configs` as a JSON array of per-AD entries (each with its
  own `availability-domain`, `subnet-id`, and `faultDomains` list) — this is
  the same multi-AD placement structure [[terraform/lab-oke-stack]]'s
  `node_config_details { placement_configs { ... } }` block expresses in
  Terraform's syntax instead of raw JSON.

### Shape support/exclusions for Managed Nodes

Not every Compute shape category can be used as a managed node — a real,
concrete exam-testable exclusion list, not just "most shapes work":

**Supported:**
- Flexible shapes, **except** flexible shapes configured to create burstable
  instances (e.g., `VM.Standard.E3.Flex` set up as burstable).
- Bare Metal shapes — both standard and GPU.
- HPC shapes — **except** in RDMA networks.
- VM shapes — standard, GPU, and Dense I/O.

**Not supported at all:**
- **Dedicated VM Host shapes.** A direct, concrete limitation on the Dedicated
  VM Host capacity type covered in
  [[3. Compute — OCI Compute, Instance Pools, Load Balancers, Volumes]] — that
  note explains what a Dedicated VM Host is (no other tenant sharing the
  physical host) but this is the first place establishing it **cannot** be
  used to run OKE managed nodes at all.
- **Micro VM shapes.**
- **HPC shapes specifically on Bare Metal in RDMA networks** (the negative
  case of the RDMA exception above — RDMA networking and OKE managed nodes
  don't combine, regardless of the underlying shape family).
- **Burstable instances**, restated as its own bullet — worth connecting
  directly to the "Instance variants" section in
  [[3. Compute — OCI Compute, Instance Pools, Load Balancers, Volumes]]: of the
  three variants covered there (burstable, shielded, confidential), burstable
  is the one with a concrete, confirmed OKE exclusion; shielded/confidential
  compatibility with managed nodes isn't addressed by this slide either way.

### Prerequisites to create an OKE cluster

Two distinct categories of prerequisite, worth keeping separate since they fail
differently (a quota shortfall rejects outright; a missing IAM grant is an
authorization error; missing/misconfigured network resources can manifest as a
much less obvious symptom like a node timing out rather than an upfront error):

**1. Sufficient quota (service limits)** — four categories:
- **Compute instance quota**: at least one compute instance (node) available in
  the tenancy.
- **Block Volume quota**: persistent volume claims must request a **minimum of
  50GB**.
- **Load Balancer quota**: sufficient quota in the region.
- **VCN and Subnet quota**: sufficient in the region.

**2. Required IAM policies** — the specific statement list (`<group-name>` and
`<location>` are placeholders, same syntax as every other policy in
[[5. Security — OCI IAM, WAF, Certificates, Vault, Cloud Guard]]):
```
Allow group <group-name> to manage cluster-family in <location>
Allow group <group-name> to use subnets in <location>
Allow group <group-name> to use network-security-groups in <location>
Allow group <group-name> to use vnics in <location>
Allow group <group-name> to use private-ips in <location>
Allow group <group-name> to manage instance-family in <location>
Allow group <group-name> to read virtual-network-family in <location>
Allow group <group-name> to inspect compartments in <location>
Allow group <group-name> to manage public-ips in <location>
```
(`manage public-ips` only needed if the design uses public IPs — e.g. a public
API endpoint, as [[terraform/lab-oke-stack]] does.)

**Straight from Oracle's official docs (Creating a Cluster), a detail the
course slide didn't mention:** cluster creation authorization requires either
tenancy Administrators membership, **or** a group granted the specific
**`CLUSTER_MANAGE` permission** — named that way in the docs, distinct
phrasing from the course's `manage cluster-family` resource-family statement.
Unconfirmed whether these are the same underlying grant under different
names or genuinely distinct — the docs link to a page literally titled
"Policy Configuration for Cluster Creation and Deployment," which is next in
this course's own playlist, so resolve this the next time that video is
watched rather than assuming either framing is complete on its own.

**Which of the three creation paths does Terraform actually use?** The API
one. Terraform doesn't drive the Console UI — the OCI Terraform provider is
built on the OCI Go SDK, which calls the same underlying `CreateCluster` API
operation shown under the docs' "API" tab. So
[[terraform/lab-oke-stack]]'s `oci_containerengine_cluster` resource is the
API path from the "Ways to create an OKE Cluster" three-option slide, not
Console (Quick/Custom Create) or a raw `oci` CLI invocation — though CLI and
Terraform both ultimately hit the same API underneath, just through different
client layers. Relevant to the `CLUSTER_MANAGE` question above: whatever
permission the API path requires is exactly what the identity applying
Terraform needs — there's no separate "Terraform-specific" auth requirement
distinct from the API's own.

**Also from the official docs — OKE handles AD/FD spread automatically, you
don't design it yourself the way you would for a plain Compute instance
pool:**
- **Control plane**: Oracle-managed, automatically distributed across
  multiple availability domains in the region, where supported.
- **Worker nodes**: automatically distributed as evenly as possible **across
  fault domains within an availability domain**, subject to any other
  infrastructure constraints you've set.

This is a real distinction from the HA design work in
[[Lab 2 - OCI Architect Pro Exam - HADR Design]], where AD/fault-domain
placement for a Compute instance pool is something you explicitly design and
configure (`placement_configs` per AD, spreading across fault domains
deliberately). For OKE worker nodes specifically, that even-distribution-
across-fault-domains behavior is automatic — you supply *which* AD(s) a node
pool's `placement_configs` should use, but OKE handles the fault-domain
balancing within that placement for you, rather than you assigning fault
domains node-by-node.

**3. Network resources, and a real gap in what the course specifies:** VCN,
subnets, internet gateway, route table, and security lists must exist. OKE
offers to **automatically create and configure new network resources** for
you — or you can **designate existing ones**, but the course states these
"must be pre-configured appropriately" without detailing exactly what that
means. See [[terraform/LABS.md]]'s `lab-oke-stack` section: this is the live,
unresolved open question behind that stack's node-registration-timeout
issue, since it brings its own pre-existing network (built for prior labs,
not built specifically for OKE) rather than using OKE's auto-create option.

**Both quota and IAM were checked directly against the tenancy and ruled out**
as the cause of that timeout (see [[terraform/LABS.md]] for the actual limit
values and policy statements verified) — narrowing the remaining candidates
specifically to network/NSG configuration, not capacity or authorization.

**Quick Create workflow — narrows what "pre-configured appropriately" actually
means.** OKE's Quick Create (Console default settings, a few clicks) auto-
provisions **three distinct regional subnets**, purpose-built specifically for
OKE: one for the **Kubernetes API**, one for **worker nodes**, and one for
**load balancers** — not just a generic public/private pair. Requires
membership in a policy-granted group for the new-network-resource creation
step (satisfied by the same `Allow ... to manage all-resources` policy already
confirmed above).

This is the strongest lead yet on `lab-oke-stack`'s node registration timeout:
that stack reuses `lab-network-stack`'s public subnet and
`lab-private-network-stack`'s private subnet — both **general-purpose subnets
built for earlier, non-OKE labs**, not the three OKE-specific,
purpose-segmented subnets Quick Create would generate. The gap is plausibly
that a single shared private subnet, sized and secured for a generic app tier,
is missing NSG/security-list rules specific to what worker nodes actually need
(e.g., reaching the Kubernetes API subnet specifically) that Quick Create's
auto-created, purpose-built subnets would carry by default.

**Custom Create workflow — corrects/sharpens the framing above.** Custom Create
explicitly supports "precise network resource selection using **existing**
public or private subnets for Kubernetes API, worker nodes, and load
balancers" — so reusing existing subnets isn't itself wrong (Custom Create is
built for exactly that). The three **roles** are still distinct even when
you're selecting existing subnets for them, though: `lab-oke-stack` supplies
only **two** subnets for those three roles (the public subnet doing double
duty for both the Kubernetes API role and the load balancer role, per
`service_lb_subnet_ids` — see [[terraform/LABS.md]]).

**RESOLVED**, via Oracle's official `oracle-terraform-modules/terraform-oci-oke`
module — collapsed subnet roles turned out not to be the actual issue.
`lab-oke-stack` creates **no NSG at all**, and its subnet's default security
list has only SSH/ICMP/443 — missing the actual required bidirectional ports
between control plane and workers: **6443** (Kubernetes API), **10250**
(Kubelet — the specific port worker registration/health-check needs),
**12250** (OKE control plane), and **10256** (health check). See
[[terraform/LABS.md]]'s `lab-oke-stack` section for the full rule-by-rule
comparison against Oracle's module and the fix.

**Fix applied and confirmed working (2026-09-15):** added the missing NSGs
and rules directly to `lab-oke-stack`. Both worker nodes reached `ACTIVE`
cleanly on the next apply — no timeout, on the first attempt with the fix in
place. Diagnosis fully verified, not just theorized.

Other Custom Create capabilities, for completeness:
- Tailor new cluster properties, **including encryption**.
- Define node pools immediately, delay node pool creation, or create a
  **node-pool-free cluster** entirely.
- **A node-pool-free cluster specifically facilitates installing Calico
  without pod recreation.** Calico is a third pod-networking CNI option this
  note hadn't covered — alongside Flannel (legacy overlay) and VCN-Native
  (`OCI_VCN_IP_NATIVE`, the option [[terraform/lab-oke-stack]] actually uses)
  already documented in "OKE pod networking" below. Calico isn't elaborated on
  further here since the course didn't go deeper on it at this point — flag
  for a follow-up pass if it comes up again.

## OKE Virtual Nodes (the Fargate analog)

- **Requires an Enhanced cluster.** Virtual node pools are not available on Basic
  clusters at all — this alone can force the Enhanced tier decision before any
  other requirement is even considered.
- A **virtual node pool** is a distinct pool type from a managed node pool — pods scheduled onto it run on Oracle-managed, isolated serverless capacity. No node infrastructure to provision, patch, scale, or upgrade.
- **Built on the open-source CNCF Virtual Kubelet project** — this is the actual
  underlying technology, not a proprietary Oracle mechanism.
- **Two components, the Virtual Nodes analog of Managed Nodes' Kubelet/container
  runtime pair** — but Oracle-managed instead of customer-managed:
  - **Virtual Kubelet** — handles pod management (the counterpart to a Managed
    Node's Kubelet).
  - **CI Runtime** — handles container instance management (the counterpart to a
    Managed Node's container runtime); notice this reuses **OCI Container
    Instances** as the actual execution substrate underneath a virtual node,
    tying this section back to the Container Instances section below rather than
    being an unrelated third mechanism.
  - Virtual Nodes **delegate all pod-lifecycle management responsibility to
    Virtual Kubelet** — the concrete mechanism behind "no infrastructure to
    manage," the same way Managed Nodes' Kubelet/runtime pair was the concrete
    answer to "you own patching/lifecycle" above.
- **Pod density: over 10x a managed node's limit.** The "OKE architecture" section
  above notes a platform-wide managed-node ceiling of 256 pods per node — Virtual
  Nodes support **more than ten times that** per virtual node. Relevant to a
  design question framed around pod-density/bin-packing efficiency: Virtual Nodes
  aren't just "no infrastructure to manage," they're also a materially different
  scaling shape than a managed node, not merely a serverless wrapper around the
  same per-node limits.
- **Placement constraint, easy to miss:** a virtual node pool is configured by the
  customer and lives **within a single Availability Domain and Fault Domain** —
  it is not automatically spread across ADs just because it's serverless. Don't
  assume "serverless" implies region-or-AD-wide HA by default; achieving
  multi-AD resilience for virtual nodes requires **multiple virtual node pools**,
  one per AD, the same explicit per-AD placement pattern managed node pools need
  (see the three-tier AD/HA reference diagram in
  [[9. Networking — OCI VCN, DRG, Gateways, Load Balancers]]).
- **Mixed clusters**: a single OKE cluster can combine one managed node pool (steady-state workloads) + one virtual node pool (bursty workloads), often paired with an autoscaler (e.g., Karpenter) for the virtual side.
- Supports on-demand virtual node cycling (cordon/drain/replace) to roll out configuration changes without manual node management.
- **Exam framing**: reach for Virtual Nodes when the requirement is "run pods without managing node infrastructure, but still inside Kubernetes semantics." Reach for Container Instances instead when the requirement doesn't need Kubernetes at all.

## OCI Container Instances (cluster-less containers)

- Serverless compute service for running one or more containers directly on OCI with VM-level isolation — no Kubernetes cluster, no ECS-style cluster construct, nothing to manage beneath the container.
- Configure via a flexible compute shape (CPU/memory scale together; network bandwidth scales with OCPUs), environment variables, restart policy, graceful shutdown behavior.
- Pulls images from OCIR or third-party registries (Docker Hub, GHCR, Quay, other private registries); private registry credentials come from OCI Vault Secrets.
- Billing: charged while Active/Updating, paused while Stopped, nothing while Failed/Deleted.
- Typical use cases: APIs/web apps, CI/CD build-and-deploy jobs, automation tasks, batch/data processing, dev/test — i.e., workloads that don't justify a Kubernetes cluster.

## OCIR (OCI Registry)

- Regional, fully managed private (or optionally public) container image registry.
- **Access control is entirely OCI IAM policy** — who can create repositories, push/pull images, or manage settings, scoped by compartment. There is no parallel registry-native identity system to reason about separately.
- Private, in-VCN image pulls can go through the **Service Gateway** — no public internet exposure required.
- **Image scanning**: integrates with the OCI Vulnerability Scanning Service (VSS) to scan images for vulnerable packages on push/ingestion.
- **Image signing/verification**: supports container image signing and verification as a separate supply-chain-security control from scanning.
- **Lifecycle/retention policies**: auto-delete images matching criteria (e.g., untagged for N days, not pulled in N days) — this is the direct analog to ECR's "EXPIRE only" lifecycle actions from the AWS notes.

### OCIR addressing terminology

- **Region key**: the short region identifier used in OCIR hostnames — e.g. `iad`
  (Ashburn) or the full `us-phoenix-1` form (both appear in Oracle's own examples,
  so don't assume every region has a short 3-letter key; Phoenix specifically uses
  its full name, not a shortened one).
- **Repository name**: can be **hierarchical/nested**, not just a flat name — e.g.
  `project01/acme-web-app/component1/subcomponent1` is a valid single repository
  name, letting you organize repos by project/app/component without a separate
  folder construct.
- **Tenancy namespace**: the same unique per-tenancy string Object Storage uses
  (`data.oci_objectstorage_namespace`) — OCIR reuses this value rather than having
  its own separate namespace concept.
- **Registry identifier** (the full pushable/pullable address):
  `<region-key>.ocir.io/<tenancy-namespace>/<repository-name>`

**Confirmed directly against `terraform/lab-oke-app-stack`**: the stack's
`repository_path` output builds exactly this format
(`${var.region_key}.ocir.io/${namespace}/${repo_name}`), and building it required
the same region-key-vs-full-region-name distinction this slide calls out —
`us-phoenix-1` resolves to `phx.ocir.io`, not `us-phoenix-1.ocir.io`, despite what
this slide's own example format might suggest generalizes to every region.

**Two more addressing levels beyond the registry identifier:**
- **Tag**: a version string (`4.6.3`, `version2.0.test`) — arbitrary, not required to
  follow semver.
- **Image name**: `<repo-name>:<tag>` — repo name plus tag combined, one level more
  specific than a bare repository name.
- **Image path** (the fully pushable/pullable address, one level past the registry
  identifier): `<region-key>.ocir.io/<tenancy-namespace>/<repo-name>:<tag>`

**Discrepancy worth flagging, straight from the course's own examples:** the slide
mixes `iad.ocir.io` (short region key) and `us-phoenix-1.ocir.io` (full region name)
as if either form works for any region — but the confirmed, actually-working value
for Phoenix from the Terraform work above is `phx.ocir.io`, not
`us-phoenix-1.ocir.io`. Don't copy a region-key format directly from a course slide
example without checking Oracle's actual region-key reference table for the specific
region in use — the short/long key convention isn't uniform enough to guess.

### Managing OCIR images and security

**Image lifecycle operations, beyond the retention-policy coverage above:**
- **Delete vs. undelete**: a deleted image is recoverable (**undelete**) — don't
  treat an image delete as instantly, irreversibly gone the way you might assume;
  there's a recovery window before it's actually purged.
- **Untag vs. delete**: two distinct operations — untagging removes a tag from an
  image without deleting the underlying image data (useful for retagging/cleanup
  workflows); deletion removes the image itself.
- **Pulling images during Kubernetes deployment from a private repo**: requires
  using `kubectl` to create a **Docker registry secret** in the cluster first — this
  is the actual mechanism that answers "how does OKE authenticate to pull a private
  OCIR image," distinct from the cluster's own node-principal/IAM identity. Relevant
  directly to [[terraform/lab-oke-app-stack]]: its `lab-app` OCIR repo is
  `is_public = false`, so deploying to it from `lab-oke-stack`'s cluster (once its
  node pool issue is resolved) needs this registry-secret step, not just network
  reachability to `phx.ocir.io`.

**Security — authentication and access control:**
- **Auth token**: the credential Docker CLI actually authenticates with for
  push/pull (`docker login <region-key>.ocir.io`) — distinct from an OCI API
  signing key; generated under Identity → Users → your user → Auth Tokens, same
  mechanism already noted in [[terraform/LABS.md]]'s `lab-oke-app-stack` manual
  deployment steps.
- **Repository access policies**: standard IAM policies scoped to OCIR resources
  (repos, image push/pull, management), following the same subject/verb/resource
  structure as every other OCI policy in [[5. Security — OCI IAM, WAF, Certificates, Vault, Cloud Guard]].
- **`allow service <service-name> to ...` — a policy subject type not yet covered
  elsewhere in these notes.** Distinct from the group/dynamic-group subjects
  Section 1 of the Security note covers in depth — this grants a first-party OCI
  *service itself* (not a group of your own resources) permission to act. Real
  example from the course, wiring Vulnerability Scanning Service into OCIR image
  scanning:
  ```
  allow service vulnerability-scanning-service to read repos in (tenancy || compartment acme-compartment)
  allow service vulnerability-scanning-service to read compartments in (tenancy || compartment acme-compartment)
  ```
  The `(tenancy || compartment acme-compartment)` location syntax is also new —
  an **OR across two scopes** in one statement, rather than a single location.

### Accessing a cluster with kubectl

Two setup paths, both converging on the same destination:
- **Cloud Shell**: browser-based, no local install.
- **Local Installation**: `kubectl` installed on your own machine.

Both write the kubeconfig to the same standard location: **`$HOME/.kube/config`**
— confirms this is a fixed convention, not something specific to any one
setup path. This is exactly the file
[[terraform/LABS.md]]'s `lab-oke-app-stack` manual deployment steps populate
via `oci ce cluster create-kubeconfig --file ~/.kube/config ...`; either the
Console's guided setup or that CLI command land in the same place.

## OKE pod networking

- **Flannel CNI** (overlay networking) — the traditional/legacy option.
- **VCN-Native Pod Networking CNI** (Kubernetes 1.22+, the Console default on newer clusters) — pods get real VCN IP addresses via multiple VNICs per node, each with multiple secondary IPs, from a pre-allocated warm pool for lower scheduling latency. Pods become first-class VCN citizens, directly reachable and governed by VCN security lists/NSGs — this is the pattern referenced across the other OCI compute/networking notes (e.g., the OKE lab stacks in `terraform/`).
- **Exam framing**: choose VCN-native pod networking when pods need to be addressed/secured like normal VCN resources (NSG rules, direct routing); Flannel is the simpler overlay fallback.
