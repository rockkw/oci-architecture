### Translation from AWS Lambda notes

| AWS memory anchor | OCI service/pattern | OCI distinction |
| --- | --- | --- |
| AWS Lambda | OCI Functions | Functions run container images using the Fn Project model. Design application, function, image, networking, and IAM resource-principal access. |
| Lambda runtime/layers | Function container image and dependencies | OCI Functions is container-image based; do not transfer AWS managed-runtime/layer limits or defaults. |
| EventBridge | OCI Events + rules + Functions/Notifications/Streaming | Events carry OCI resource state changes; match rules and make consumers idempotent. |
| API Gateway + Lambda | OCI API Gateway + Functions | API Gateway defines request auth/routing/rate controls; Functions implement business processing. |
| Lambda VPC access | Function application subnet/VCN configuration | Network path, NAT/Service Gateway, NSGs, and private endpoint access are OCI design decisions. **IP consumption model also differs, not just config.** OCI's ENI equivalent is the **VNIC** — same primitive (attachable network interface, own private IP, subnet/NSG membership), different name. The gap isn't "OCI lacks the concept," it's pooling: post-2019 Lambda maintains a *shared pool* of ENIs per subnet/security-group combo, so concurrent invocations reuse pooled ENIs and IP usage barely scales with concurrency. OCI Functions has no equivalent pooling layer over VNICs — every invocation runs as its own container with its own VNIC, so IP consumption scales roughly linearly with concurrency. That's exactly why Oracle publishes an explicit subnet-sizing formula (see "Sizing the subnet" below) instead of treating it as a managed, invisible detail the way Lambda does. |
| CloudWatch/X-Ray | Monitoring, Logging, APM | Metrics, logs, and traces are separate OCI signals. |

## OCI Functions architecture

- OCI Functions executes serverless functions packaged as container images. Store images in OCI Container Registry and manage delivery with OCI DevOps where appropriate.
- Group functions in an application and configure the network/subnets needed to reach private dependencies or approved external services. **An application can select up to 3 subnets** — this is the concrete Console reality behind the `3 × number_of_subnets` term in the IP-sizing formula below: the "3 reserved IPs per subnet" scales because the Console literally lets you attach more than one subnet to a single application.
- **Shape is set at the application level, not per-function**: choosing a shape (e.g. `GENERIC_X86`) when creating the application locks in compatibility for every function grouped under it — you can't mix shapes across functions in the same application, only across separate applications.
- Use resource principals/dynamic groups and IAM policies for OCI API access. Do not embed user API keys in code.
- Keep configuration and secrets outside code: use environment/configuration patterns and Secret Management/Vault for credentials.
- Functions should be stateless, bounded in duration, idempotent when retried, and safe to invoke concurrently.

### Invocation mechanics — what "cold start" actually means in OCI terms

- **Invocation paths**: Fn Project CLI, OCI SDKs, signed HTTP requests, or
  triggered by other OCI services (Events, API Gateway, etc.). Every function
  has a **unique invoke endpoint** specifically for signed HTTP requests —
  distinct from the general "call it via SDK/CLI" paths.
- **The actual cold-start mechanism, concretely**: on the **first** invocation,
  OCI Functions pulls the container image, runs it as a container, and
  executes the function — this is the cold-start latency the note's
  "Performance, resilience, and operations" section above already flags as a
  concern, now with the actual cause attached to it.
- **Warm path**: subsequent requests to the **same** function are routed to
  the **already-running container**, skipping the pull/start steps —
  materially faster, which is the entire reason "test with realistic bursts"
  matters: a burst of traffic after idle time pays the cold-start cost on
  every concurrent first-hit, not just once.
- **Idle eviction**: after a period of inactivity, the container is removed
  to free resources — this is the mechanism that makes cold starts recur
  over time, not a one-time startup cost. A low-traffic function with gaps
  between invocations will cold-start repeatedly, not just on its very first
  call ever.

### The full invocation architecture, drawn end-to-end

Course diagram ("What Happens When You Invoke a Function?") makes concrete
what the rest of this note states as separate design rules:

- **Every invocation path converges on the same invoke endpoint** — Fn
  Project CLI talks to it directly; **both** external callers *and* other
  OCI services (IaaS/PaaS/SaaS) reach it via the same "signed request to
  functions invoke endpoint(s)" path. There isn't a separate, lower-trust
  path for external vs. internal callers — the endpoint and its signing
  requirement are uniform.
- **IAM is checked as part of every invocation, not just deployment.** The
  diagram draws a direct line from Oracle Functions to the IAM Service — this
  is the runtime enforcement point for "use resource principals/dynamic
  groups... for OCI API access" (already stated above), not a
  deploy-time-only concern.
- **The running container sits inside a VCN/Subnet** with direct paths to
  **DBaaS** and other in-VCN resources — the concrete picture behind "Function
  in VCN → private endpoint" in the event-driven design table below.
- **Logging is a first-class output of the invocation flow itself**, not a
  bolt-on: both the OCI Console and the function's execution write to OCI
  Logging and external logging services as part of the same diagram, not a
  separate "add observability later" step.

## Event-driven design

| Requirement | OCI starting pattern | Design concern |
| --- | --- | --- |
| OCI resource state change | Events rule → Function/Notifications/Streaming | Filters can match event attributes; consumer must tolerate duplicates/retries. |
| Public HTTPS API | API Gateway → Function | Define authentication, authorization, request validation, throttling, errors, and observability. |
| Asynchronous buffering | Streaming/Queue pattern → Function/consumer | Design ordering, retry, poison-message handling, and back-pressure. |
| Scheduled operation | Scheduler/automation pattern → Function | Make execution idempotent and alert on missed/failed runs. |
| Private database/API call | Function in VCN → private endpoint | Design DNS, NSG, routing, secrets, and connection pooling. |

### Real use cases, worked end-to-end

Introduces **Service Connector** — the piece that sits between an event/log
source and a consumer (Functions, Streaming, Object Storage, etc.), routing
data from one OCI service to another without you hand-wiring the
plumbing. Not a Function-specific concept, but shows up repeatedly as the
"glue" in front of Functions in these patterns.

**Use case 1 — Enforce corporate security policies/governance:**
`Resource Change Events (Audit Logs) → Service Connector → Functions`. The
Function audits and tears down noncompliant resources it finds — e.g.,
automatically shutting down a Compute instance if it has a public IP address
it shouldn't. This is a concrete instance of the "OCI resource state change"
row in the table below, specifically for compliance enforcement rather than
general automation.

**Use case 2 — Ingest access logs into security incident management:**
`VCN → Logging → Service Connector → Functions`, parsing network access
logs and forwarding them to an external SIEM (Splunk, ELK). Concrete
instance of routing OCI-native Logging output to an external logging
service, not just OCI Logging/Logging Analytics.

**Use case 3 — High-volume ETL** (stated throughput: **~1-1.5 million files
per day**, a real number worth remembering as evidence Functions scales to
genuine production ETL volume, not just lightweight glue code):
1. Insurance claims XML files uploaded to Object Storage
2. Upload event generated
3. Events Service invokes the Function
4. Function reads the XML file from Object Storage
5. Function transforms and inserts the data into **Exadata Cloud Service**

This is the fully worked version of the "OCI resource state change" row
below (Object Storage upload → Events → Function), extended one step
further into a real downstream database write — worth using as the concrete
mental model when a scenario asks about event-driven ETL into a database.

### Functions service limits — real numbers, region-scoped

Per Oracle's Service Limits reference, all limits below are scoped **per
region**, not per tenancy or per compartment:

| Resource | Universal Credits | Pay As You Go / Trial |
|---|---|---|
| Applications | 20 | 10 |
| Functions | 500 | 50 |
| Total memory for **concurrent** function execution | 60GB (180GB for a 3-AD region) | 60GB (180GB for a 3-AD region) |
| Total memory for **provisioned** concurrency | 40GB | 40GB |

Two things worth holding onto for the exam:
- **The concurrent-execution memory limit scales with AD count** — the
  60GB figure is the base, but a region with three availability domains
  effectively gets 180GB. Don't assume the limit is a flat number
  independent of which region a design targets.
- **These are hard ceilings, not soft targets** — actual memory usage is
  always ≤ the stated limit, for both concurrent and provisioned
  concurrency. A design that needs more than the default supports needs an
  explicit service limit increase request before going to production, not
  just careful capacity planning within the default.

### Sizing the subnet — the minimum-IP-addresses formula

Functions run inside a VCN subnet, and every concurrent execution consumes
an IP address — this is the formal capacity-planning formula for sizing that
subnet before deployment, not something to eyeball:

```
minimum_required_number_of_IP_addresses =
  ( Σ (max_memory_required_by_function × max_number_of_executions_of_function)
    across all functions in the application
    / 14 )
  + (3 × number_of_subnets)
```

**Three steps:**
1. For each function, compute its own max memory × max expected concurrent
   executions — this is a per-function figure, not a single blended number.
2. Sum that across every function in the application, then **divide by 14**
   — a fixed conversion factor (effectively, each concurrently-executing
   function "costs" the network the equivalent of 14MB per IP consumed).
   Not a value you tune; it's a constant in the formula.
3. Add **3 reserved IPs per subnet** — this is the standard OCI subnet
   reservation (first 2 + last address of any subnet's CIDR, already covered
   generically in [[9. Networking — OCI VCN, DRG, Gateways, Load Balancers]]),
   scaled by how many subnets the design actually uses.

**Why this matters for the exam:** a subnet sized without running this
calculation can run out of IP addresses under real concurrent load even
though the *service limit* (memory) headroom looks fine — these are two
independent constraints (region-level memory quota vs. subnet-level IP
capacity) that both have to be satisfied, not one derived from the other.

**Worked example, closing the loop from formula to an actual CIDR decision:**
single function, 512MB (0.5GB) memory, 2000 max concurrent executions, 1
subnet:
```
((0.5 × 2000) / 14) + (3 × 1)
= (1000 / 14) + 3
= 72 + 3          (1000/14 ≈ 71.4, rounded up)
= 75 minimum required IP addresses
```
**Conclusion: a /25 CIDR block is sufficient** (128 total addresses). This is
the piece the raw formula doesn't show on its own — translating an IP-count
requirement into an actual subnet-size decision you'd put in a VCN design.
When a scenario gives memory + concurrency numbers and asks for a CIDR size,
work the formula through to a raw address count first, then pick the
smallest standard subnet size (`/24` = 256, `/25` = 128, `/26` = 64, etc.)
that covers it.

## Performance, resilience, and operations

- Cold-start, image size, concurrency, downstream connection limits, and timeout behavior are architecture concerns. Test with realistic bursts.
- Do not open database connections per event without considering pooling/proxy/application limits.
- Emit structured logs; use Monitoring alarms and APM where tracing is required. Use Audit for OCI management operations.
- Use retries only with idempotency and a bounded failure path; send persistent failures to an operational queue/workflow rather than retrying indefinitely.
- A function is not a replacement for long-running, stateful, or specialized compute workloads; consider Container Instances, OKE, or Compute when appropriate.
