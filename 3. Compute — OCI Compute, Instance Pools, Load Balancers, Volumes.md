## Compute selection and lifecycle

- Use VM shapes for general workloads; use bare metal, GPU, HPC, or specialized shapes only when workload requirements justify them.
- Flexible shapes let you select OCPUs and memory within shape limits. Capacity and shape availability are regional/AD considerations.
- Use custom images, instance configurations, and instance pools for consistent fleet deployment.
- Plan maintenance, boot-volume backup, OS patching, IAM instance principals, and observability from the start.
- Do not keep durable application state only on an instance's local/ephemeral storage.

## Capacity type

Distinct from shape selection — this is *how* you acquire capacity for a given
shape, not which shape you pick.

- **On-demand:** default; no commitment, standard pricing.
- **Preemptible:** significantly cheaper capacity that OCI can reclaim with a short
  notice window when it needs the capacity back. Fits batch/fault-tolerant/stateless
  workloads that can checkpoint or simply restart — not a fit for anything that needs
  guaranteed uptime. Directly analogous to AWS Spot, but don't assume identical
  interruption mechanics — verify OCI's specific notice period and behavior.
- **Capacity Reservation:** the opposite end of the spectrum — reserves capacity for
  a specific shape/AD combination so it's guaranteed available when you need to
  launch, even under regional capacity pressure. Useful for DR failover capacity you
  need to know will actually be there, or for planned scaling events. Costs the same
  as running the instance whether or not you actually launch into the reservation.
- **Dedicated VM Host:** you get an entire physical host dedicated to your VM
  instances only — no other tenant's VMs share the hardware, unlike standard VM
  shapes which run on shared bare metal under the hood. This is the middle ground
  between a standard VM shape (shared host, cheaper) and full Bare Metal (no
  hypervisor at all) — relevant for compliance/isolation requirements that stop short
  of needing bare metal's raw hardware access.

## Images

- **Platform image:** Oracle-provided, maintained OS image (Oracle Linux, Ubuntu,
  Windows, etc.) — patched and supported by Oracle on a regular cadence.
- **Custom image:** captured from an existing instance's boot volume — used to
  standardize a fleet's baseline (the note's existing "consistent fleet deployment"
  point above is this). You own patching/maintenance once you've customized it.
- **BYOI (Bring Your Own Image):** import an image built entirely outside OCI (e.g.,
  from on-prem or another cloud) rather than starting from a platform image and
  customizing it. Relevant for migration scenarios where an exact existing image
  needs to move as-is, not be rebuilt from an OCI base.

## GPU shapes

Selected the same way as any other flexible/fixed shape, but worth calling out
separately because of the cost and quota implications: GPU shapes bill
significantly more per hour than standard compute, and most tenancies start with a
**zero GPU service limit** — a limit increase request is required before you can
launch one, independent of whether the shape shows as available in the region.

See [[terraform/lab-oke-gpu-stack]] for the concrete shape list (VM.GPU2.1 /
VM.GPU3.x / VM.GPU.A10.x for VM shapes with no RDMA; BM.GPU* bare-metal shapes
support RDMA cluster networking for multi-node training) and for the specific
"apply will fail on a capacity/limit error" failure mode this produces in practice
when the limit increase hasn't been granted yet.

## OSMS (OS Management Service)

Patch and update management for instances — the actual OCI service behind this
note's existing "plan OS patching from the start" guidance above. Tracks available
updates, lets you group instances for coordinated patching, and reports compliance
status against a defined patch baseline, instead of patching each instance by hand
or building that tooling yourself. Relevant to the exam's operations-burden angle:
OSMS is the managed alternative to a self-built patch pipeline, the same way Instance
Pools are the managed alternative to hand-rolled fleet scaling.

## Connecting to an instance

- **SSH (Linux):** the default path — generate a keypair, supply the public key via
  instance metadata at launch (`ssh_authorized_keys`), connect with the private key.
  This is exactly the flow used in [[terraform/lab-nsg-stack]] (direct public IP) and
  [[terraform/lab-bastion-stack]] (no public IP — routed through a managed Bastion
  session instead, since the instance has no direct public exposure).
- **Instance console connection:** a serial-console-style connection independent of
  the instance's network stack entirely — the fallback when SSH itself is
  unreachable (misconfigured networking, guest OS firewall lockout, boot failure).
  This is the tool that would have shortened today's `lab-bastion-stack` firewalld
  troubleshooting if SSH itself had been the thing broken, rather than just port 443.
- **RDP (Windows):** the Windows equivalent of SSH access, same public-IP-or-Bastion
  pattern applies.

## Infrastructure maintenance

OCI schedules maintenance on the underlying physical infrastructure (host patching,
hardware issues) that can affect running instances. Two outcomes depending on
`recovery_action` in the instance's availability configuration:

- **Live migration:** the default for VM shapes where supported — the instance
  moves to healthy hardware with no reboot, transparent to the workload.
- **Reboot migration / instance reboot:** used when live migration isn't possible for
  the shape/scenario — the instance restarts, briefly unavailable.

Design implication: a single instance's availability during a maintenance event
depends on which recovery action applies to its shape — don't assume live migration
is universal. This is part of why the note's HA section above spreads instance pools
across fault domains: a maintenance event is exactly the kind of correlated-failure
scenario that isolation is meant to absorb.

## Instance variants (security/performance flavors)

Distinct from shape selection — these are properties you can enable on top of a
chosen shape, not alternative shapes themselves:

- **Burstable instances:** baseline OCPU utilization with the ability to burst above
  it for a period — cost-efficient for workloads that are mostly idle with
  occasional spikes, rather than paying full-rate for peak capacity around the clock.
- **Shielded instances:** adds a virtual Trusted Platform Module (TPM) and Secure
  Boot enforcement, protecting against boot-level/rootkit-style attacks by verifying
  the boot chain hasn't been tampered with. A security-posture checkbox, not a
  workload-performance one.
- **Confidential computing:** encrypts memory in use (not just at rest or in
  transit) so that even someone with host/hypervisor access can't read the
  instance's in-memory data. Relevant for the exam's "why not just encryption at
  rest" trap — confidential compute closes the in-use gap those don't cover.

## High availability and scaling

- Availability domains are physically isolated data centers in regions that have multiple ADs; fault domains are isolation groups within an AD. **Every AD has exactly 3 fault domains** — a fixed number, not something that varies by region or AD count. This is why 3-way spread patterns recur across OCI HA designs (e.g. the three-tier diagram in [[9. Networking — OCI VCN, DRG, Gateways, Load Balancers]] shows fault-domain-spread instances behind a Load Balancer's Backend Sets).
- Spread an instance pool across fault domains, and across availability domains when the region/service architecture supports the required level of resilience.
- Place a Load Balancer in front of healthy backends. Health checks must reflect readiness; unhealthy backends are removed from rotation.
- Instance-pool autoscaling responds to a defined metric/schedule. Capacity scaling does not solve database, session-state, or downstream bottlenecks.
- Use regional DR architecture when an AD-level design cannot meet the required RTO/RPO.

## Storage with Compute

- **Boot Volume:** persistent boot disk; back it up separately from the instance.
- **Block Volume:** durable block storage for single/multi-attach patterns supported by the service; use backups/clones and volume groups for recovery workflows.
- **File Storage:** managed shared NFS file system.
- **Object Storage:** object/data-lake/backup distribution pattern, not a mounted block volume replacement.
