## Object and Archive Storage

- Use Object Storage for durable objects, backups, logs, static content, and data-lake patterns. Use Archive Storage for infrequently retrieved, long-retention objects.
- Object lifecycle policies can archive, change tier, delete objects/versions, and clean incomplete multipart uploads. Test destructive rules in nonproduction.
- Lifecycle actions are asynchronous/best effort; do not model an immediate tier transition as a transactional workflow.
- Use versioning and retention/immutability features where required, then design deletion/legal-hold governance explicitly.
- Replication is regional bucket-to-bucket replication. The destination has read-only replication behavior; understand what source deletion, object-name conflicts, and lifecycle rules do before using it for DR.
- Use Service Gateway for private VCN access to supported Oracle services such as Object Storage.

## File and Block Storage

- **File Storage** provides shared NFS access; protect mount targets with VCN routing/NSGs and size performance for aggregate client demand.
- **Block Volume** provides durable block devices for Compute. Choose performance, backup, clone, and replica topology according to workload RPO/RTO.
- **Volume groups** coordinate backups/clones for related volumes; they are useful when application consistency spans disks.
- Do not confuse File Storage's shared filesystem behavior with Object Storage APIs or Block Volume device semantics.

## File Storage deep dive

Topics from the mind map above that the one-line "File Storage" bullet didn't cover
in enough depth to be exam-testable on their own:

- **File System vs. Mount Target:** these are two separate OCI resources, not one —
  the **File System** is the actual NFS filesystem/data; the **Mount Target** is the
  network-attached endpoint (with its own private IP in a subnet) that clients
  connect through to reach it. A File System is only reachable via export paths
  associated with a Mount Target — you don't mount a File System directly, you mount
  through its Mount Target. This split matters for network design: NSGs/security
  lists that control access are applied to the **Mount Target's** VNIC, not to the
  File System resource itself.
- **NFS Export Options:** per-export access control layered on top of Mount Target
  network access — controls which source CIDRs can mount, read/write vs. read-only
  access, and whether root-squash applies (mapping the client's root user down to an
  unprivileged user on the export, a common NFS security default worth verifying
  rather than assuming). This is a second, filesystem-level access gate distinct
  from — and in addition to — the NSG/security-list gate on the Mount Target's VNIC.
- **File System paths:** the export path (e.g. `/myfileshare`) is what clients
  actually reference in their mount command, separate from any OS-level path
  structure inside the filesystem once mounted. Don't conflate the export path with
  a directory path inside the mounted filesystem — they're two different
  namespaces.
- **In-transit encryption:** File Storage supports encrypting NFS traffic between
  the client and the Mount Target, distinct from at-rest encryption (which the
  note's Encryption and protection section below covers for OCI storage broadly).
  Worth calling out because it's opt-in configuration on the client/mount side, not
  automatic the way at-rest encryption is.
- **Snapshot vs. Clone:** a **Snapshot** is a point-in-time, read-only capture of the
  filesystem, accessible via a hidden `.snapshot` directory inside the mounted
  filesystem itself — useful for quick self-service file recovery without a full
  restore workflow. A **Clone** creates a new, independent, writable File System
  from a snapshot — the File Storage equivalent of Block Volume's backup-vs-clone
  distinction covered above, but File Storage's snapshot mechanism is
  filesystem-native (browsable inside the mount) rather than a separate
  backup-service object the way Block Volume backups are.
- **Usage & Metering:** File Storage bills by the amount of data actually stored
  (not a pre-provisioned capacity number the way Block Volume requires you to pick a
  size up front) — relevant to the exam's cost-model framing: File Storage's
  pay-for-what-you-use metering is a distinct cost shape from Block Volume's
  provisioned-capacity billing, worth stating explicitly when a scenario asks you to
  justify a storage choice on cost grounds.

## Block Volume deep dive

Topics from the mind map above that the general File/Block section didn't cover in
enough depth to be exam-testable on their own:

- **Boot Volume vs. Block Volume:** a Boot Volume is created automatically with an
  instance from its source image and holds the OS; a Block Volume is a separate,
  independently-lifecycled device you attach for data. Both support backup/clone/
  resize, but a Boot Volume's lifecycle is tied to the instance in ways a data Block
  Volume's isn't (e.g., you can detach and reattach a Boot Volume to a different
  instance for recovery scenarios a data volume wouldn't need).
- **Backup vs. Clone:** a **backup** is a point-in-time, storage-service-side copy
  you restore *from* (creates a new volume when restored) — the DR/retention
  mechanism. A **clone** is an immediate, full-copy *new volume* created directly
  from an existing one (or from a backup) — the fast-provisioning mechanism, e.g.
  spinning up a duplicate environment. Same underlying tech, different purpose:
  backup for recoverability over time, clone for point-in-time duplication.
- **Resize:** Block Volumes (and Boot Volumes) can be resized larger online, without
  detaching or downtime — but growing the volume doesn't automatically grow the
  filesystem on top of it; that's a separate, OS-level step (`resize2fs`,
  `growpart`, etc.) after the OCI-side resize completes. A common exam trap: "resize
  the volume" and "the OS sees the new space" are not the same completed action.
- **Performance tiers (Balanced / Higher Performance) and Dynamic Performance:**
  Block Volumes have selectable performance tiers trading cost against IOPS/
  throughput; **Dynamic Performance** auto-scales a volume's performance based on
  its utilization rather than requiring you to provision for peak load up front.
  Relevant to the exam's cost-vs-performance framing — don't default to the highest
  tier without a stated throughput requirement driving it.
- **Volume attachment types — iSCSI vs. paravirtualized:** **paravirtualized**
  attachment is simpler (no in-guest iSCSI configuration needed) and is the default
  for most shapes, but has a lower per-instance volume-count limit and isn't
  available on every shape. **iSCSI** attachment requires the guest OS to run iSCSI
  initiator commands to connect the volume, but scales to a much higher number of
  attached volumes per instance and works on shapes paravirtualized doesn't support
  (notably bare metal). Shape choice can force the attachment type decision, not just
  volume-count needs.
- **Volume access types (single-attach vs. multi-attach):** by default a Block
  Volume attaches to exactly one instance. **Multi-attach** lets the same volume
  attach to multiple instances concurrently — but OCI does not provide clustering/
  concurrency control on top of that; the workload itself (a cluster-aware
  filesystem or application, e.g. OCFS2) is responsible for coordinating concurrent
  writes, or data corruption results. This is distinct from a **Volume Group**,
  which coordinates backup/clone timing across several *separate* volumes attached
  to one instance — multi-attach is one volume shared by several instances, the
  inverse relationship.
- **Cross-region and cross-AD volume replication:** Block Volume backups/replicas
  can be copied to a different region or a different availability domain for DR —
  distinct from the general "replica topology" language already in this note's
  encryption/protection section below; the mind map's `B.V → B.V` chain is exactly
  this replication relationship (source volume → replicated copy elsewhere).

## Encryption and protection

- OCI storage is encrypted at rest. Use Vault customer-managed keys when policy/control requirements need them, and plan key availability/rotation before use.
- Backups, replicas, and archive copies have different recovery times and operational paths. State the RPO, RTO, and restore test for each data class.
- Use IAM policies and compartment boundaries to restrict bucket, object, filesystem, and volume access.

## Storage decision guide

| Need | Starting OCI service | Key question |
| --- | --- | --- |
| API-addressed objects, backups, logs | Object Storage | Access pattern, lifecycle, replication, immutability. |
| Long retention, rare access | Archive Storage | Retrieval time/process and restore testing. |
| Shared POSIX/NFS filesystem | File Storage | Client throughput, network, mount security. |
| Persistent disk for Compute/database | Block Volume | Performance, backups, clones/replication, consistency. |
| Temporary high-speed local data | Instance local storage | Can the workload lose it? If no, persist elsewhere. |
