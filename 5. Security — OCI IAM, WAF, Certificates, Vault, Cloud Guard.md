### AWS-to-OCI security translation

| AWS memory anchor | OCI service or pattern | OCI-specific distinction |
| --- | --- | --- |
| AWS account / Organizations / SCP | Tenancy, compartments, IAM policies, quotas, budgets | Compartments partition resources inside a tenancy, not separate accounts. Policies inherit down the hierarchy and are allow-only; OCI has no general explicit-deny/SCP equivalent. |
| IAM users, groups, Identity Center | IAM identity domains, users, groups, roles, federation | Identity domains manage authentication, MFA, SSO, lifecycle, and federation; IAM policies authorize OCI resources. |
| IAM role / instance profile / STS | Dynamic group + IAM policy; instance/resource principal | OCI resources match a dynamic-group rule and receive a policy grant. Do not recreate an AWS AssumeRole workflow. |
| KMS / Secrets Manager / CloudHSM | Vault, Secret Management, Dedicated KMS | Vault manages keys, Secret Management manages secret versions, and Dedicated KMS is a single-tenant HSM partition with more customer responsibility. |
| ACM | Certificates service; Load Balancer certificates | OCI Certificates manages CA-issued/imported certificates. Certificates are regional; do not import the AWS CloudFront/us-east-1 rule. |
| AWS WAF / Shield | OCI WAF, DDoS protection, Network Firewall | WAF is L7 web protection. DDoS protection and routed Network Firewall are separate layers, not one-to-one Shield replacements. |
| GuardDuty / Security Hub / Config | Cloud Guard, Security Zones, Audit, Logging | Cloud Guard detects posture/risk and can respond; Security Zones prevent noncompliant operations; Audit records API activity. |
| Inspector | Vulnerability Scanning Service (VSS) | VSS scans Compute hosts and container images; it is not a behavioral-threat detector. |
| Macie | Data Safe; Cloud Guard/Object Storage controls | No exact generic OCI Object Storage PII-discovery equivalent. Data Safe focuses on Oracle Database sensitive data. |

### Shared responsibility model — what moves, what never does

Source: Oracle and KPMG Cloud Threat Report (2019), via MyLearn. The stack —
User Access/Identity, Data, Application, Guest OS, Virtualization, Network,
Infrastructure, Physical — splits differently by service model:

| Layer | On-Prem | IaaS | PaaS | SaaS |
| --- | --- | --- | --- | --- |
| User Access/Identity | Customer | Customer | Customer | **Customer** |
| Data | Customer | Customer | Customer | **Customer** |
| Application | Customer | Customer | Customer | Provider |
| Guest OS | Customer | Customer | Provider | Provider |
| Virtualization | Customer | Provider | Provider | Provider |
| Network | Customer | Provider | Provider | Provider |
| Infrastructure | Customer | Provider | Provider | Provider |
| Physical | Customer | Provider | Provider | Provider |

**The line that never moves, regardless of service model: User Access/Identity
and Data are always the customer's responsibility**, even under SaaS where the
provider owns everything else. This is the generic industry framing (matches
AWS's own shared-responsibility messaging), not an OCI-specific twist — but
it's the reason Section 1's IAM/dynamic-group design rules and Section 2's
Vault/Secret Management guidance in this note exist at all: no service model
choice ever relieves you of owning identity and data protection, so "we moved
to SaaS/PaaS" is never itself a security answer to an exam scenario about
access control or data governance.

**Common mistakes that misread this boundary (MyLearn, "Architect Security
Solutions" module):**
- *"We're on the cloud, so Oracle handles security."* Oracle handles
  infrastructure security only — data, access, and configuration security are
  always the customer's.
- *"We use Autonomous Database, so we don't need to worry about DB security."*
  Oracle manages the database engine; the customer still manages who can
  access it, what data is sensitive, and how it's monitored — ADB's
  autonomy narrows the *operations* burden (patching, tuning), not the
  *security-ownership* boundary.
- *"Our data is encrypted, so it's secure."* Default encryption protects data
  at rest, but if IAM policies are too permissive, anyone with access can
  still read it — encryption and access control are separate controls, and
  one doesn't substitute for the other.

## 1. Identity, authentication, and authorization

### Core OCI model

- **Tenancy:** top-level OCI account boundary.
- **Compartments:** organize and isolate resources by environment, workload, or delegated administration boundary. Policies at a parent compartment apply to child compartments.
- **Identity domains:** manage users, groups, MFA, SSO, federation (SAML 2.0/OIDC), and identity lifecycle.
- **IAM policies:** grant authorization to OCI services.
- **Dynamic groups:** identify OCI resources as principals; policies then grant those resources permission to call OCI APIs.

### What a dynamic group actually is, and what's in it by default

A dynamic group is **not** a container you manually add members to (unlike a regular IAM group). Instead, it's a **matching rule** — OCI evaluates the rule continuously, and any resource meeting the criteria at call time is treated as a member, automatically, with no membership list to maintain. This is the entire mechanism that replaces AWS's instance-profile/AssumeRole pattern.

**Default state: zero dynamic groups exist in a new tenancy or compartment.** Nothing is a member of anything until you write a matching rule. There's no "default dynamic group" the way AWS has default service roles in some contexts — OCI requires you to explicitly define which resources should be treated as identities.

**Matching rule syntax and what it can match on:**
```
ALL {resource.type = 'fnfunc', resource.compartment.id = '<compartment-ocid>'}
```
- `resource.type` — the OCI resource type acting as the principal: `instance` (a Compute VM), `fnfunc` (a Function), `ApiGateway`, `computecontainerinstance`, etc.
- `resource.compartment.id` — scope the rule to a specific compartment (most common, keeps blast radius contained)
- `resource.id` — scope to one specific resource by OCID (tightest possible scope, but brittle if that resource is ever recreated — OCIDs are not stable across recreate/replace in Terraform)
- Tag-based matching is also supported (`tag.<namespace>.<key>.value = '...'`) for grouping by freeform/defined tags instead of compartment or type
- `ALL` requires every condition to match; `ANY` requires at least one — mixing these up is a common real-world debugging trap

**Real example hit in Lab 1 (API Gateway invoking a Function):**
```
ALL {resource.type = 'ApiGateway', resource.compartment.id = 'ocid1.compartment.oc1..aaaaaaaa7s64nst5is7tmveri2ymuenrjrcg5h5n2lxnvamdtk7cuazg32da'}
```
This says: "any API Gateway resource in the `sandbox` compartment should be treated as a dynamic-group member." Once matched, a policy statement then grants that dynamic group actual permissions (see below). Without this dynamic group existing, the Gateway has **no identity at all** to present when it tries to call the Functions service — which is exactly why the Gateway/Function/Deployment resources could all be *created* successfully (that happened under the Administrators identity via Resource Manager) while *invocation at runtime* still failed with a 500. Creating a resource and that resource acting as a caller are two entirely different principals, needing two entirely separate authorizations. This is a core exam distinction: **provisioning identity ≠ runtime identity.**

### What a policy actually does, and what's granted by default

Policy form:
~~~
Allow <subject> to <verb> <resource-type> in <location> [where <conditions>]
~~~

- **Subject**: a regular IAM group, or a dynamic group (from above)
- **Verb**: privilege escalates `inspect` → `read` → `use` → `manage`, in that order — each verb is a strict superset of the one before it. `manage` includes full lifecycle (create/update/delete); `use` typically covers day-to-day operational actions without deletion rights; `read` is metadata/list-level; `inspect` is the bare minimum (list resource names/existence, no content). **Verb-to-action mapping varies by resource type** — always check the specific service's policy reference rather than assuming, since "use" means different concrete API calls for `functions-family` than for `object-family`.
- **Resource-type**: often a `-family` grouping (e.g., `functions-family`, `virtual-network-family`) that bundles several individual resource types under one grant, or a specific singular resource type for tighter scoping
- **Location**: `in compartment <name>`, `in tenancy`, or `in compartment id <ocid>`
- **Conditions** (`where`): further restrict by request attributes — source IP, resource tags, request time, etc.

**Default state: implicit deny, everywhere, always.** A brand-new compartment, a brand-new dynamic group, a brand-new user — none of them can do anything until an explicit `Allow` statement grants it. There is no OCI equivalent of AWS's occasional permissive service defaults. **The one built-in exception** is the tenancy's **Administrators** group, which ships with a tenancy-wide `Allow group Administrators to manage all-resources in tenancy` policy from day one — this is why resources created under an Administrators-member identity (like the Terraform applies in this lab) "just work" without any policy authoring, while separate service-to-service calls (Gateway → Function) still need their own explicit grant regardless of the human operator's permissions.

**OCI has no general explicit-deny statement** the way AWS IAM/SCPs do. You cannot write "deny X" to override an "allow X" granted elsewhere in the hierarchy — the only lever is *not granting* the permission in the first place, or scoping grants narrowly enough (compartment, resource type, conditions) that the unwanted access was never possible. This reframes "least privilege" in OCI as entirely about what you choose to grant, not what you explicitly block.

Example — permit application instances to read Object Storage without distributing user API keys:
~~~
Allow dynamic-group app-instances to read object-family in compartment app-data
~~~

Example — the fix actually applied in Lab 1, granting the Gateway's dynamic group permission to invoke Functions:
~~~
Allow dynamic-group api-gateway-dynamic-group to use functions-family in compartment sandbox
~~~

### Identity design rules

- Separate emergency/tenancy-administrator access from daily administration; use MFA.
- Federate the corporate IdP instead of duplicating users where practical; map IdP groups deliberately and test offboarding.
- Prefer instance principals, resource principals, workload identity, and dynamic groups over long-lived user API credentials.
- Version-control policies and review effective access after group changes or compartment moves.

> **Exam distinction:** “An EC2 app assumes a role” normally translates to **dynamic group + IAM policy + instance/resource principal** in OCI.

### Home region vs. subscribed regions — IAM writes replicate, and replication isn't instant

Every OCI tenancy has exactly one **home region**, set at tenancy creation and rarely changed afterward. IAM resources — users, groups, **dynamic groups**, and **policies** — are always authored/written in the home region, then **replicated out** to every other subscribed region the tenancy uses. This matters operationally: if you're working in a non-home region (very common — you pick whatever region is closest or matches a workload's placement, which frequently isn't the home region), every dynamic group or policy change you make still has to round-trip through the home region and propagate back out before it takes effect where you're actually testing.

**Check your home region before troubleshooting an IAM-looks-right-but-still-fails problem:**
```bash
oci iam region-subscription list --output table
```
Look for `is-home-region: True` in the output.

**Real example hit in Lab 1:** tenancy home region was `us-ashburn-1`, but the entire lab (Gateway, Function, dynamic group evaluation) ran in `us-phoenix-1` — a subscribed, non-home region. A newly created dynamic group and its policy grant matched Oracle's documented syntax exactly, resource creation succeeded, direct Function invocation succeeded — but the Gateway's runtime call to Functions kept failing with `functionBackend.notFoundOrNotAuthorized` for far longer than the few minutes typically expected for IAM propagation. First-time replication of a *brand-new* dynamic group to a non-home region can take meaningfully longer than routine policy edits — the lag isn't necessarily proportional to how simple the change looks.

**Practical takeaway for both the lab and the exam:** don't assume identity-related failures are a configuration mistake just because the syntax checks out. If you're in a non-home region, budget real wait time (potentially 15-20+ minutes for a first-time dynamic group, not the 2-3 minutes typical for most propagation) before concluding the policy itself is wrong. Repeatedly editing the dynamic group or policy during this window can restart the propagation clock rather than fix anything — a clean, single correct configuration left alone is more likely to resolve than a series of edits made out of impatience.

### The same philosophy shows up in networking — recognize the pattern across domains

Dynamic groups replace static, long-lived credentials with **identity-based** trust: a policy grants access to "whatever matches this rule" rather than to a specific hardcoded principal. The networking domain has a direct parallel worth recognizing as the same underlying idea, not a coincidence: **NSG-to-NSG security rules** let one Network Security Group name another NSG (not a CIDR) as its allowed source. A database NSG can say "allow from the app-tier NSG" the same way an IAM policy says "allow this dynamic group" — both move the trust boundary from something static (an IP, a long-lived key) to something that tracks membership automatically as resources scale in and out.

When a scenario question is testing "least privilege that survives autoscaling," this is the pattern in both domains: dynamic groups on the identity side, NSGs on the network side. Full NSG-based tier-isolation Terraform example lives in Note 9, Section 3.

### A gap worth flagging from hands-on lab work: SSH keys aren't secrets management

If you're following the compute instance examples in Note 8.1 (Terraform/Resource Manager hands-on reference), you'll see instance metadata set like:
```hcl
metadata = {
  ssh_authorized_keys = file("~/.ssh/id_rsa.pub")
}
```
This is fine — it's the **public** key, which isn't secret material, so putting it in Terraform config (even committed to Git) isn't a Vault violation. The trap is conflating this with actual secrets: if a lab or real design ever needs to inject a **private** key, a database password, or an API token into an instance at launch, that does **not** belong in `metadata` or in `.tfvars` — it belongs in **Secret Management**, retrieved by the instance at boot via its instance principal, per the rotation lifecycle already covered below (pending → current → previous → deprecated). Metadata is appropriate for non-sensitive bootstrap data (like a public key or a cloud-init script); it is not a secrets store.

## 2. Vault, encryption keys, and secrets

### Vault and customer-managed keys

- **Vault** manages vaults, customer-managed encryption keys, key versions, and access controls.
- OCI services commonly use envelope encryption: a data-encryption key protects data and a Vault master encryption key protects that data-encryption key.
- Plan rotation, recovery dependencies, and authorization before disabling or deleting a key: unavailable keys can make dependent data inaccessible.
- Audit records Vault/key management operations. Enable appropriate service logging when cryptographic data-plane evidence is required.

### Secret Management

- Store passwords, API keys, SSH keys, and tokens in **Secret Management**, never in code, instance metadata, or unprotected Terraform state.
- Secrets use a symmetric Vault key and have lifecycle states including **current**, **pending**, **previous**, and **deprecated**.
- Safe rotation sequence: create pending secret → update/validate the target and applications → promote to current → retain rollback capability → deprecate old version.
- Automatic generation/rotation is available for supported targets and Functions-based workflows. Cross-region replicas are read-only; use them deliberately in DR designs.

### Dedicated Key Management

- Default choice for OCI service encryption/key management: **Vault**.
- Choose **Dedicated KMS** only for a stated requirement such as a single-tenant HSM partition, direct HSM interfaces (for example PKCS#11), or deeper HSM control.
- Oracle operates the highly available HSM infrastructure; the customer has extra responsibility for HSM users, keys, and replica synchronization.

### Database encryption trap

Do not equate storage encryption with database-native TDE. For Oracle databases, first identify whether the requirement is encryption at rest, TDE/key administration, customer-managed keys, protected backups, or cross-region DR; the OCI database service determines the viable design.

## 3. Certificates and TLS

- Use **OCI Certificates** to manage certificate authorities and certificates, including lifecycle/renewal for supported CA-issued certificates.
- Associate certificates with the supported OCI service, such as Load Balancer. Imported X.509 certificates use PEM format.
- **mTLS** requires a client-trust design (CA/CA bundle) as well as the server certificate.
- Protect private keys and design renewal/deployment before expiration.
- OCI certificates are regional resources. Select the certificate in the relevant service/region, rather than applying AWS ACM regional assumptions.

## 4. Edge and network protection

### OCI Web Application Firewall

OCI WAF protects HTTP/HTTPS applications at Layer 7.

- Use access rules for URL/header/request criteria, IP lists, geolocation, bot controls/challenges, and rate limiting.
- Use protection rules for common attacks such as SQL injection and XSS. Tune in log/detect mode before blocking if false positives are possible.
- Publish changes, verify propagation, and review WAF logs/recommendations.
- Protect the origin separately so traffic cannot bypass WAF; layer Load Balancer controls, NSGs/security lists, and application authentication.

### DDoS, Network Firewall, and network controls

- OCI includes always-on DDoS protection capabilities for public OCI infrastructure. Combine resiliency, origin restrictions, and WAF; do not model this as a selectable AWS Shield tier.
- **Network Firewall** is a managed, routed network control. VCN/DRG route tables must steer traffic through firewall endpoints—it does nothing merely by existing.
- **NSGs** apply focused rules to VNICs/resources; **security lists** apply at subnet level. Prefer NSGs for precise least privilege.
- Use **Bastion** and private subnets for administration instead of broadly exposing SSH/RDP. Use Service Gateway/private endpoints when applicable.

> **Design check:** WAF inspects web requests; Network Firewall inspects routed network traffic; NSGs/security lists allow or deny flows. They are complementary.

### Network Firewall deployment: distributed vs. centralized, and the route tables that make it work

MyLearn's dedicated "OCI Network Firewall" module names two deployment
models:

- **Distributed model** — a firewall instance per VCN, each inspecting only
  its own VCN's traffic.
- **Centralized model** — one firewall instance in a Hub VCN, reached by
  every Spoke VCN via the DRG, inspecting traffic for the whole hub-and-spoke
  estate from a single place.

**The centralized model traced through its actual route tables** — this is
the concrete mechanism behind the existing "VCN/DRG route tables must steer
traffic through firewall endpoints — it does nothing merely by existing"
principle above, made literal:

1. **IGW Route Table** (Hub VCN): `10.0.1.0/24 → 10.0.4.112` (the firewall's
   private IP) — inbound internet traffic destined for the Spoke's Web App
   subnet is routed to the firewall *first*, not directly toward the DRG/spoke.
2. **Firewall Subnet Route Table**: `0.0.0.0/0 → IGW` — the firewall's own
   return path to the internet, once it has inspected and allowed traffic.
3. **Web App Route Table** (Spoke VCN): `0.0.0.0/0 → 10.0.4.112` — critically,
   the *spoke's own outbound* traffic is also routed back through the
   firewall, not out through a local internet gateway of its own (the Web
   App subnet has none). Every packet leaving the spoke, not just inbound
   traffic, transits the centralized firewall.

**Why this is the design worth defaulting to for an exam scenario spanning
multiple VCNs:** a distributed model means provisioning, licensing, and
keeping firewall *policy* in sync across every VCN independently — a
centralized hub firewall inspects all spoke traffic (both directions) from
one policy, one place, at the cost of routing every packet through the hub
first. This is the same hub-and-spoke shape as
[[Lab 5 - OCI Architect Pro Exam - Zero Trust Packet Routing]]'s Cross-VCN
ZPR scenario above — Network Firewall (Layer 2) and cross-VCN ZPR (Layer 3)
solve different problems on the identical topology: Network Firewall
inspects packet *content* centrally, ZPR governs *identity-based*
reachability regardless of where a firewall sits.

### Network Firewall use cases — three concrete scenarios, one shared allow/deny pattern

MyLearn's "OCI Network Firewall" module frames the service through three
named use cases, each with a real customer-VCN diagram and a matching route
table (client → firewall → IGW/NAT or Service Gateway):

**Use Case 1 — Perimeter Security.** *"Protect your applications and network
against known vulnerabilities, until you have time to patch/update"* —
explicitly framed as **virtual patching**, a stopgap, not a substitute for
actually remediating the vulnerability. Enforces stateful allow/deny rules
based on the full **5-tuple** (source IP, destination IP — both IPv4 and
IPv6 — port, and protocol), with rules combinable across allow/deny/grey
lists for compliance flexibility.

**Use Case 2 — Intrusion Detection and Prevention.** The IDS/IPS engine is
**Palo Alto Networks' own threat analysis engine**, fed by **Unit 42**
(Palo Alto's threat research arm) for exploit signatures, malware, malicious
URLs, spyware, and command-and-control (C2) traffic detection. **OCI Network
Firewall is white-labeled Palo Alto technology for its IDS/IPS
capability** — worth remembering as a specific vendor fact, not a
generic "Oracle built this" assumption, the same way OKE's CNI options
(Note 12) name specific upstream projects rather than in-house Oracle code.

**Use Case 3 — Selective Access to Oracle Services Network (OSN).**
URL/FQDN inspection rules gate outbound access to only a named allowlist of
destinations, explicitly framed as **outbound data-exfiltration
prevention** — the stated example: "allow Ubuntu servers to only do
`apt-get` to `*.canonical.com` for updates," blocking every other outbound
destination by default. Traffic to Oracle Services (Streaming, Oracle
Services in general) routes through a **Service Gateway**, not an Internet
Gateway or NAT Gateway — reinforcing this note's Section 4 point that OCI's
private-access patterns vary by destination type rather than following one
uniform mechanism.

**The shared Allowlist vs. Denylist pattern (Use Cases 1 and 3 both show
this explicitly) — the real teaching point, and a recurring theme across
this whole note:**

| | Denylist | Allowlist |
| --- | --- | --- |
| Explicit rule | `src: any, dst: any, condition **≠** match → Blocked` | `src: any, dst: specific, condition **=** match → Permitted` |
| Default catch-all | **Permitted** | **Blocked** |

A denylist is fail-open by construction — anything not specifically named
gets through. An allowlist is fail-closed — anything not specifically named
is blocked. This is the identical default-allow-vs-default-deny tension
already established for IAM (Section 1: implicit deny, everywhere) and ZPR
(default-deny by design) — Network Firewall is simply the one place in this
note where the operator explicitly chooses which posture a given rule set
takes, rather than the platform imposing one by default. For an exam
scenario emphasizing compliance or data-exfiltration prevention specifically
(as in Use Case 3), the allowlist's fail-closed default is the
correct choice — a denylist can never fully enumerate "everything bad,"
only "everything known-bad so far."

### OCI Bastion service vs. a self-managed ("self-service") bastion host

MyLearn frames this as a direct before/after comparison — a self-hosted
bastion instance versus the managed **OCI Bastion** service — using the same
target architecture (Main VCN, a private subnet with Web-App-01/02 as target
resources) for both, so the only variable is the bastion mechanism itself.

**Self-service (self-managed) bastion host limitations:**

![](5.%20Security%20—%20OCI%20IAM,%20WAF,%20Certificates,%20Vault,%20Cloud%20Guard/mylearn_self_service_bastion_scenario.png)

- Management overhead — it's a Compute instance you patch, size, and operate.
- Security is on you — it's another host with its own attack surface.
- Requires a public IP address to be reachable at all.
- Cannot be deployed in private subnets or Security Zones — the public-IP
  requirement directly conflicts with a Security Zone's noncompliant-public-
  resource guardrail (Section 5), which is part of why this option is
  structurally weaker, not just less convenient.
- Performance scaling is the operator's problem (it's a real instance under
  real load).
- Added cost for the bastion host itself, running continuously.

**OCI Bastion service — the managed replacement:**

![](5.%20Security%20—%20OCI%20IAM,%20WAF,%20Certificates,%20Vault,%20Cloud%20Guard/mylearn_oci_bastion_service.png)

- Free service, no management overhead — Oracle operates it.
- Security is handled by OCI; access is controlled via **IAM policies**
  instead of host-level hardening.
- Does **not** require a public IP address — reachability goes through a
  **Service Gateway**, not an Internet Gateway, which is the key architectural
  difference from the self-managed diagram above (public endpoint → Internet
  Gateway → host, versus public endpoint → Service Gateway → OCI Bastion).
- **Can** be deployed in private subnets and Security Zones — this is the
  direct fix for the self-managed option's structural conflict with Security
  Zones.
- Session-based, time-limited access to a target private endpoint rather than
  a standing host you SSH into directly.

**Required IAM policies for OCI Bastion — three separate grants, not one.**
This is the concrete instantiation of "control access using IAM policies"
above; each grant maps to a distinct capability, so under-granting one still
lets the others fail silently rather than as an obvious single permission
error:

```
# Manage bastions, sessions, and networks
Allow group <domain-name>/<group-name> to manage bastion-family in compartment <compartment-name>
Allow group <domain-name>/<group-name> to manage virtual-network-family in compartment <compartment-name>

# Read compute instances and Oracle Cloud Agent plugins
Allow group <domain-name>/<group-name> to read instance-family in compartment <compartment-name>
Allow group <domain-name>/<group-name> to read instance-agent-plugins in compartment <compartment-name>

# Inspect work requests
Allow group <domain-name>/<group-name> to inspect work-requests in compartment <compartment-name>
```

- **`manage bastion-family`** — create/update/delete the Bastion resource
  itself and its sessions; **`manage virtual-network-family`** — needed
  because a Bastion is provisioned into a VCN/subnet, so network-family
  management is a real prerequisite, not an unrelated grant.
- **`read instance-family` + `read instance-agent-plugins`** — the target
  Compute instance must be readable, and specifically its Oracle Cloud Agent
  plugin state, since session-based Bastion access (as opposed to
  port-forwarding) depends on the agent being visible/active on the target.
- **`inspect work-requests`** — Bastion session creation is asynchronous
  (an OCI work request under the hood); without this grant a user can create
  a session but can't see whether it succeeded, failed, or is still
  provisioning.

**Exam framing:** whenever a scenario mentions a Security Zone *and* a need
for administrative SSH/RDP access, a self-managed bastion is disqualified by
construction (it needs a public IP, which the zone forbids) — OCI Bastion is
the only compliant answer, not just the "better practice" one.

**AWS comparison — no single named "Bastion" service; two services converge
on the same outcome:**

- **AWS Systems Manager Session Manager is the closer functional match.**
  Browser- or CLI-based shell access to an instance via the SSM agent — no
  bastion host, no open inbound SSH/RDP port, no public IP, access governed
  entirely by IAM policy. This is free, like OCI Bastion, and is the
  idiomatic AWS answer to "how do I reach a private instance without exposing
  it" — the SSM agent plus IAM-policy-gated access plays the same role OCI
  Bastion plays here, more so than a literal bastion host does.
- **EC2 Instance Connect Endpoint** (added 2023) is the more literal
  bastion-shaped analog: a VPC-resident endpoint that brokers SSH/RDP to a
  target with no public IP required, access controlled via IAM — structurally
  closest to OCI Bastion's own diagram (public endpoint → managed broker →
  private target, no Internet Gateway hop).
- **Self-managed jump host** is AWS's older pattern, and maps directly to the
  "self-service bastion host" limitations slide above — a public-subnet EC2
  instance with a public IP, full patching/scaling/cost burden on the
  customer.

**Net: this is not an AWS-to-OCI exception.** The capability exists on both
clouds; AWS just split it across two services (SSM Session Manager for
general shell access, Instance Connect Endpoint for the more bastion-specific
case) rather than shipping one named "Bastion" product the way OCI does.

**Build steps (MyLearn "Demo: Manage Bastion") and the fuller connection
path:**

![](5.%20Security%20—%20OCI%20IAM,%20WAF,%20Certificates,%20Vault,%20Cloud%20Guard/mylearn_bastion_demo_steps.png)

1. Create a VCN with two private subnets — one for the Bastion, one for the
   target hosts. Notice both subnets are private; unlike the earlier
   comparison diagrams, this scenario has no public subnet at all.
2. Provision a target instance and enable the **Bastion plug-in** on it (an
   Oracle Cloud Agent plugin) — this is the concrete thing the
   `read instance-agent-plugins` IAM grant above is checking the state of.
3. Create the Bastion resource itself, scoped to the target subnet.
4. Create a Bastion **session** against a specific target instance/port.
5. Connect — the SSH client talks to the Service Gateway on port 22, which
   routes to the OCI Bastion, which brokers a **Managed SSH Session** into
   the actual target VM. The end-to-end path is `SSH Client → Service Gateway
   → OCI Bastion → Session → Managed SSH Session → target VM`, which is the
   fully expanded version of the simpler "public endpoint → Service Gateway →
   OCI Bastion" arrow drawn in the earlier OCI Bastion Service diagram — the
   session object sits between the Bastion and the actual managed connection
   to the target.

### Zero Trust Packet Routing (ZPR)

**Hands-on lab:** [[Lab 5 - OCI Architect Pro Exam - Zero Trust Packet Routing]]
builds the concepts below as an actual Terraform stack (`lab-zpr-stack`) —
VM-01/VM-02 SSH lockdown, dry-run verified against a live tenant.

From MyLearn, "Architect Security Solutions" — Step 2 ("Protect the Network")
groups network controls into two pairs: **WAF & Network Firewall** (inspect
web/packet content) and **NSG, ZPR & DDoS** (control what traffic is allowed to
flow at all). ZPR is the newest piece here and not yet covered elsewhere in
this note.

- **NSGs control port-level traffic per instance** — the existing
  allow/deny-by-rule model already documented above.
- **ZPR instead uses security attributes for intent-based access control**:
  resources are tagged with security attributes, and policy is written against
  those attributes rather than against IPs, CIDRs, or NSG membership lists.
  This is a *declarative, identity-of-the-resource* model, conceptually
  parallel to how dynamic groups replace static IAM principals (Section 1) —
  the same "match on what something *is*, not on a static address" pattern
  showing up a third time, alongside dynamic groups (identity) and
  NSG-to-NSG rules (network).
- **Only explicitly authorized traffic can flow** — ZPR is default-deny by
  design, consistent with the tenancy-wide implicit-deny posture already
  described for IAM policies (Section 1).

**Enabling ZPR — the Console's own "Enable ZPR" dialog confirms three facts
that resolve open questions elsewhere in this note and in
[[Lab 5 - OCI Architect Pro Exam - Zero Trust Packet Routing]]:**

1. **"Enabling ZPR in a tenancy creates a default `oracle-zpr` security
   attribute namespace"** — confirms the default namespace name (Lab 5's
   Terraform stack defines its own custom namespace, `ZprLabRole`, rather
   than using this default one — both are valid; a tenancy is not limited to
   the default).
2. **"Enabling ZPR won't affect communication between resources without
   security attributes. ZPR policy is only enforced on resources with
   security attributes."** This is the exact mechanism Lab 5's live test
   (Section A5) proved empirically: untagged resources are entirely
   unaffected by ZPR being enabled tenancy-wide; only a resource that is
   itself tagged becomes subject to ZPR's default-deny.
3. **"For resources with security attributes, ZPR policy is evaluated
   first. If ZPR policy permits communication, then other controls are
   evaluated in a layered approach. If ZPR policy doesn't allow
   communication, the request is dropped."** This is the authoritative,
   Oracle-stated version of what Lab 5 discovered by experiment: ZPR isn't
   just "independent" of NSGs/security lists/IAM — it's evaluated **first**,
   as a gate that traffic must pass before any other control is even
   consulted. A security list wide open on port 22 is irrelevant if ZPR's
   policy doesn't separately authorize that connection — exactly what Lab
   5's SSH-block test showed (TCP handshake completes, since that's below
   ZPR's layer, but the application-level SSH banner never arrives once ZPR
   drops the request).

**Official policy syntax examples — straight from the Console's own policy
builder** (Security → Zero Trust Packet Routing → Policies → Add policy
statements → Manual/Policy template builder), useful as ground truth
alongside the MyLearn slide examples already in this note:

```
in vcn-network:db VCN allow db-client:app1 endpoints to connect to db-server:app1 endpoints

in vcn-network:db VCN allow app:front-end endpoints with protocol = 'tcp/999-11199' to connect to app:back-end endpoints

in vcn-network:db VCN allow app:front-end endpoints to connect to '192.168.1.1/16'
```

Three things worth noting against
[[Lab 5 - OCI Architect Pro Exam - Zero Trust Packet Routing]]'s applied
policy:
- **`with protocol = ...` sits between the source endpoints and `to connect
  to`** in this official example (`app:front-end endpoints with protocol =
  'tcp/999-11199' to connect to app:back-end endpoints`) — Lab 5's applied
  statement placed `with protocol=` at the very end, *after* the destination
  endpoints, and that version was accepted by the live API too. Both
  placements may be valid ZPR Policy Language, or this may be a stricter
  documented convention worth matching going forward — not yet confirmed
  either way.
- **Protocol supports a port *range*** (`'tcp/999-11199'`), not just a
  single port — Lab 5's `'tcp/22'` only exercised the single-port form.
- **Example 3 shows a plain CIDR as a valid destination** (`'192.168.1.1/16'`)
  alongside a tagged endpoint as the source — confirming a ZPR policy can mix
  an attribute-based endpoint with a traditional CIDR on the other side of
  the same statement, not just attribute-to-attribute.

### Cross-VCN ZPR — the gap NSGs and security lists cannot close

**"Two Applications. One Spoke."** (MyLearn "CROSS-VCN ZPR" module) is the
concrete scenario that motivates cross-VCN ZPR specifically, and it resolves
Lab 5's own open question about `with protocol=` clause placement.

**Topology:** a hub-and-spoke design — Hub VCN (`lb_subnet` with two Public
Load Balancers, `fw_subnet` with a Network Firewall) connected via a **DRG**
to a Spoke VCN (`app_subnet` with two application instances, `db_subnet`
with two databases). Two separate applications, **App-A and App-B, share the
same `app_subnet`** — a common, cost-driven real-world pattern (one spoke
serving multiple workloads) that creates a genuine isolation problem.

**The question: what stops App-A's load balancer from reaching App-B's
VMs?**
- **Security lists: No.** They apply at the *subnet* level. Both apps share
  one subnet, so a security list has no way to distinguish "traffic destined
  for App-A" from "traffic destined for App-B" — it can only reason about the
  subnet as a whole.
- **NSGs: Partially.** NSG-to-NSG references (Section 1's "same philosophy
  shows up in networking" pattern) work *within a single VCN* — but this
  traffic crosses a VCN boundary via the DRG. **Once traffic crosses VCNs,
  NSG-to-NSG referencing stops working entirely, and the design falls back to
  CIDR ranges** — reintroducing the exact address-based fragility ZPR exists
  to eliminate.

**This is the precise, concrete gap cross-VCN ZPR closes.** The layered
network controls (Layer 1: NSGs/security lists; Layer 2: Network Firewall —
SSL Inspection requiring a per-app decryption profile, inline Intrusion
Prevention, URL/FQDN filtering) all have real value, but none of them can
express "App-A's load balancer may reach App-A's instances, and only
App-A's" once the traffic has to cross a VCN boundary — that's Layer 3.

**The tagging scheme is namespace-per-resource-type**, not one namespace
with a role ENUM the way this note's earlier ZPR lab used: `vcn:hub-vcn` /
`vcn:spoke-vcn` (tags the VCNs themselves), `lb:App-A` / `lb:App-B` (tags
each load balancer), `instance:App-A` / `instance:App-B` (tags each app
instance), `db:DB-A` / `db:DB-B` (tags each database). Every resource in the
path carries an attribute identifying which application it belongs to.

**The solution — three ZPR policy statements per application, chaining the
full request path one hop at a time:**

```
1. In app.vcn:hub-vcn VCN, allow 0.0.0.0/0 to connect to app.lb:App-A endpoints with protocol tcp/443

2. Allow app.lb:App-A endpoints in app.vcn:hub-vcn VCN to connect to app.instance:App-A endpoints with protocol tcp/443 in app.vcn:spoke-vcn VCN

3. In app.vcn:spoke-vcn VCN, allow app.instance:App-A endpoints to connect to app.db:DB-A endpoints with protocol tcp/1521
```

Each statement authorizes exactly one hop of the path (internet → LB → App
tier → DB tier) — there is no single statement authorizing the whole
end-to-end flow. App-B would need its own identical three-statement set,
referencing `App-B`/`DB-B` throughout; nothing here is shared between the
two applications, which is exactly the isolation property the scenario
needed.

**This resolves Lab 5's open `with protocol=` placement question — the
same-VCN and cross-VCN grammars are genuinely different shapes, not just
optional clause reordering:**
- **Same-VCN** (statement 1 and 3 above): `in <VCN> allow <source> to connect
  to <dest> endpoints with protocol=X` — protocol clause at the end, matching
  the earlier same-VCN examples in this note.
- **Cross-VCN** (statement 2): `allow <source> in <source VCN> to connect to
  <dest> with protocol=X in <dest VCN>` — no `<VCN> allow` prefix at all;
  instead each endpoint carries its *own* `in <VCN>` suffix, and the protocol
  clause sits *between* the destination endpoint and the destination VCN
  clause. Lab 5's statement (single-VCN, protocol at the very end) doesn't
  cleanly map to either form exactly, which is consistent with ZPR Policy
  Language tolerating some clause-order flexibility rather than one strict
  grammar — but the cross-VCN case clearly needs its own `in <VCN>` scoping
  on each side, which single-VCN statements don't.

**Defense in depth, unifying all three layers (the module's closing
framing) — worth keeping as the mental model for exam scenarios:**

| Layer | Control | Scope |
| --- | --- | --- |
| 1 | NSGs & Security Lists | Port-level controls at subnet/VNIC |
| 2 | OCI Network Firewall | Payload inspection and advanced threats (SSL inspection, intrusion prevention, URL/FQDN filtering) |
| 3 | Cross-VCN ZPR | Intent-based segmentation — identity, not IP addresses |

None of these three layers replaces the others — Layer 1 handles coarse
port/subnet boundaries cheaply, Layer 2 adds deep packet inspection for
genuine threats, and Layer 3 is the only layer that can express
per-application identity once traffic crosses a VCN boundary. A design that
only reasons about Layers 1–2 will hit exactly the "two apps, one spoke"
gap described above.

**This confirms — not just "candidates" — a genuine AWS-to-OCI exception,
now backed by a concrete cross-VCN example**: AWS security groups/NACLs have
no cross-VPC identity-based referencing mechanism at all; a security group
reference is scoped to a single VPC just like an OCI NSG, and AWS has no
declarative attribute/tag-driven policy layer that sits above VPC peering to
express "App-A may reach App-A, not App-B" without falling back to CIDR
ranges the way this exact scenario shows OCI NSGs also degrading to. See
[[AWS to OCI Exceptions]].

**"Simple Scenario" — the reference topology ZPR policy gets layered onto
(MyLearn "OCI Zero Trust Packet Routing"):**

![](5.%20Security%20—%20OCI%20IAM,%20WAF,%20Certificates,%20Vault,%20Cloud%20Guard/mylearn_zpr_simple_scenario.png)

A single VCN ("Supremo Virtual Network") holds five subnets, each with its own
CIDR and its own network/security configuration (the shield icon, called out
in the legend as "Network and security configuration: Access rules and
policies" — one per subnet, not one blanket rule for the VCN):

| Subnet | CIDR | Resource | Access pattern |
| --- | --- | --- | --- |
| Science App and DB Subnet | 10.0.3.0/24 | Science App (10.0.3.55), Central Database (10.0.3.66) | Private |
| Ingestion Subnet | 10.0.5.0/24 | Ingestion (10.0.5.15) | Public |
| Supremo App Subnet | 10.0.1.0/24 | Supremo App (10.0.1.11) | Public |
| Aggregation Subnet | 10.0.4.0/24 | Aggregation (10.0.4.10) | Private |
| Supremo Database Subnet | 10.0.2.0/24 | Supremo Database (10.0.2.22) | Private |

**Three distinct traffic sources, three distinct entry paths** — this is the
part that makes "just use NSGs" harder here than in a simple two-tier web app:
- **Scientist** reaches the Science App via **Site-to-Site VPN → Dynamic
  Routing Gateway** — a hybrid on-prem path, not a public endpoint.
- **Devices** (IoT-style) write to an **Object Store Bucket**, which the
  Ingestion subnet reads via the **Service Gateway** — traffic that never
  touches the public internet despite the source being external hardware.
- **User** reaches the Supremo App over the **Internet Gateway** — the one
  genuinely public-internet path in the diagram.

**Internal data flow, left to right:** Science App → Central Database (writes
locally), Central Database → Ingestion → Aggregation → Supremo Database, and
Supremo App reads from Supremo Database directly. Notice the internal
green-arrow flow crosses *every* subnet boundary in the design — Science
App/DB subnet → Ingestion subnet → Aggregation subnet → Supremo Database
subnet — which is exactly the shape of problem ZPR's attribute-based policy is
positioned to solve more cleanly than a matching set of NSG-to-NSG rules
would: five subnets, each needing a distinct policy, with data legitimately
crossing all of them in sequence.

**Public vs. private access is a subnet-level property here, not a
resource-level one** — per the legend, Ingestion and Supremo App subnets are
drawn as "public access," while Science/DB, Aggregation, and Supremo Database
are "private access." This is worth watching for a contradiction (or
clarification) once the actual ZPR policy videos define how attributes
override or compose with this subnet-level public/private designation.

**The motivating problem ZPR solves: hand-authored NSG rules don't scale
without silent errors.** MyLearn walks the Scientist→Science App VPN path from
the topology above into its actual NSG rule-set, then shows how the review
process itself fails to catch a bug:

![](5.%20Security%20—%20OCI%20IAM,%20WAF,%20Certificates,%20Vault,%20Cloud%20Guard/mylearn_zpr_nsg_rule_bug.png)

```
# In Science App and DB Subnet (Scientist connecting to Science App via VPN)
ROUTE DESTINATION: "160.32.103.0/30"  TARGET TYPE: "Dynamic Route Gateway"

# In Science App NSG
NSG INGRESS  SOURCE TYPE: CIDR  SOURCE: "160.32.103.0/30"  PROTOCOL: TCP  SOURCE PORT: ALL  DESTINATION PORT: 8888
NSG EGRESS   SOURCE TYPE: CIDR  SOURCE: "110.0.3.66/32"    PROTOCOL: TCP  SOURCE PORT: ALL  DESTINATION PORT: 1521

# In Central Database NSG
NSG INGRESS  SOURCE TYPE: CIDR  SOURCE: "10.0.3.55/32"     PROTOCOL: TCP  SOURCE PORT: ALL  DESTINATION PORT: 1521
```

**The bug:** the Science App NSG's egress rule sources from `110.0.3.66/32` —
an extra leading `1` turns the Central Database's real address (`10.0.3.66`,
per the topology diagram above) into an unrelated /32. It's a single
fat-fingered digit, buried in a wall of near-identical CIDR/port syntax across
three separate rule blocks, and the workflow itself is built for two humans
to review it: a **network operator** authors the rule, a **security operator**
approves it — and the slide's own framing is that the reviewer **approves the
policy but fails to notice the bug**. This isn't a hypothetical risk; it's
the actual failure mode being demonstrated.

**Why this is the argument for ZPR, not just an NSG cautionary tale:** the
error surface here is a direct function of the topology's shape from the
diagram above — five subnets, each needing its own NSG ingress/egress pair,
with addresses and ports repeated by hand across every rule. Every additional
subnet or resource multiplies the number of near-identical CIDR strings a
human has to eyeball-diff correctly. ZPR's attribute-based model (tag a
resource with what it *is*, write policy against the tag) removes the
repeated-CIDR-typo failure mode entirely, since there's no per-resource IP
address to transcribe in the first place — expect the upcoming ZPR
demo/policy videos to make this comparison explicit.

**ZPR's four-pillar pitch (MyLearn) — confirms the attribute-based framing
above and adds a genuinely new operational benefit:**

1. **Intent-based security policies** — rules are written in simple language
   focused on *which data should be accessible*, with no IP addresses or
   network configuration involved. This confirms the "match on what something
   is, not a static address" framing already used above for ZPR/dynamic
   groups/NSG-to-NSG rules.
2. **Decoupling security from network configuration** — network admins can
   change network settings (re-subnet, re-IP, re-route) **without touching
   security policy at all**. This is the new fact: in the NSG world just
   demonstrated, changing the Central Database's IP would require finding and
   updating every NSG rule that referenced `10.0.3.66/32` by hand — exactly
   the kind of manual, error-prone edit that produced the bug above. ZPR
   policy written against an attribute survives the underlying address
   changing entirely.
3. **Enforcement at the network layer** — policy isn't just descriptive; it's
   actually enforced in the data path, guaranteeing all traffic matches the
   intended rules (not merely "recommended" or "audited after the fact").
4. **Continuous monitoring** — the system watches for modifications that
   could compromise the stated security intent, aiming for a consistently
   strong posture over time rather than a point-in-time correct
   configuration that silently drifts (which is what actually happened in the
   NSG bug scenario — a config that was wrong from the moment it was
   approved, with no mechanism to flag it).

**This directly answers the AWS-equivalence question raised earlier:** pillar
2 (security decoupled from network config, surviving re-addressing) has no
NSG/security-group parallel on either cloud — AWS security groups and NACLs
are still address/port rules that must be manually updated if the underlying
resource's IP changes. This looks like a genuine candidate for
[[AWS to OCI Exceptions]] once the syntax/demo videos confirm how policy
attributes are actually defined and attached.

**The actual mechanism — security attributes tagged directly on resources
(MyLearn "OCI Zero Trust Packet Routing - Workflow"):**

![](5.%20Security%20—%20OCI%20IAM,%20WAF,%20Certificates,%20Vault,%20Cloud%20Guard/mylearn_zpr_workflow.png)

Confirms the two-part model the four pillars implied:
- **ZPR security attributes identify the resources you want to protect**
  (compute instances, databases) — shown as literal tags attached to
  resources in the diagram: the Science App carries `#app:science` and
  `#Prod`; the Central Database carries `#database:sensitive`. These are the
  "intent" labels pillar 1 described — no IP address appears anywhere in the
  tag itself.
- **ZPR policies express security intent about which access paths are
  allowed and where data is allowed to go** — the policy layer references
  these attributes (e.g., "allow `#app:science` to reach
  `#database:sensitive`") rather than the CIDR-based NSG rules from the
  earlier bug scenario.

**Why this slide reframes the scenario, not just the mechanism:** the
population reaching the Science App has widened from a single Scientist over
Site-to-Site VPN to **"University & Industry Scientists + other clients"**
arriving over the **Internet Gateway** — labeled "Broader Public Access" — and
the diagram explicitly draws an **External Attacker** inside that same
broader-access population, indicating this is deliberately the harder,
more realistic threat model ZPR needs to hold up against, not the narrow
single-trusted-user case from the original topology. The Central Database
(`#database:sensitive`) sits behind the Science App subnet regardless of
which specific client connects — the attribute-based policy is what has to
keep the attacker's traffic from reaching `#database:sensitive` even though
network-layer reachability into the subnet has broadened.

**This confirms the AWS-exceptions candidate above.** ZPR attributes are tags
on the resource itself, evaluated by policy independent of IP/CIDR — genuinely
distinct from security groups/NSGs, which are still fundamentally
address-and-port constructs no matter how they're organized. Move this from
"candidate" to a confirmed entry in [[AWS to OCI Exceptions]]: **AWS has no
resource-attribute-tag-driven zero-trust routing primitive** — the nearest
partial analogs (security group references, resource tags used in IAM
conditions) don't unify network reachability and security intent into one
declarative attribute the way ZPR does.

**The actual policy statement, and where enforcement really happens:**

![](5.%20Security%20—%20OCI%20IAM,%20WAF,%20Certificates,%20Vault,%20Cloud%20Guard/mylearn_zpr_policy_enforcement.png)

```
ZPR Policy: In network:prod VCN allow app:science endpoints with protocol = "tcp/888"
to connect to database:sensitive endpoints with protocol = "tcp/1521"
```

This is the syntax the four-pillar/tag slides were building toward: a policy
reads almost like a sentence — *which tagged endpoints, over which protocol,
may reach which other tagged endpoints* — with zero IPs, zero CIDRs, zero
subnet references. Compare directly against the NSG rule-set from the bug
scenario above: that took three separate rule blocks (route, NSG ingress, NSG
egress) with four repeated CIDR values to express the same intent; this is
one statement.

With this policy in place, the External Attacker arriving over the same
broadened "Broader Public Access" path is blocked (shown as the ⊘ icon
labeled "(ZPR protection)") — critically, **the attacker is stopped even
though it isn't a Central Database or Science App NSG rule doing the
blocking.** The slide's own callout makes the architectural point explicit:
**"While ZPR security policies and attributes are not managed at the network
layer, security is still enforced at the network so that unwanted traffic is
blocked."** This is pillar 3 ("Enforcement at the network layer") made
concrete: ZPR policy is authored and evaluated as a security-attribute
statement, but OCI still enforces the resulting decision in the actual data
path — the attacker's packets don't get an opportunity to reach
`#database:sensitive` regardless of what NSG/security-list rules exist,
because the attacker was never granted a matching attribute in the first
place. This is the same *provisioning identity ≠ runtime identity* /
default-deny posture already established for IAM (Section 1) — ZPR extends
that same default-deny discipline to network reachability itself.

### Second use case: guarding against accidental exposure, not just deliberate attack

The Science App scenario above was about *deliberately* broadened access
(more client types allowed in). MyLearn's **CarCo** example is the more
common real-world failure mode: an **accidental self-inflicted
misconfiguration** — a routine network change with no malicious intent that
silently exposes a database, with nothing in the app's own behavior signaling
that anything went wrong.

**The bug (MyLearn "CarCo Network Update Introduces a Security Issue"):**

![](5.%20Security%20—%20OCI%20IAM,%20WAF,%20Certificates,%20Vault,%20Cloud%20Guard/mylearn_zpr_carco_exposure_bug.png)

- CarCo runs a Telemetry Receiver App (App Subnet, public) talking to a
  Database (DB Subnet, also public) — a car's telemetry data flows in via the
  Internet Gateway, into the app, into the database.
- A network engineer makes a routing change so the **DB subnet now uses the
  default route via the Internet Gateway** (rather than, say, a NAT Gateway
  or no default route at all) — likely intended to fix some unrelated
  outbound-connectivity problem, not to expose anything.
- The database nodes were already using **easily guessable credentials** —
  latent, pre-existing weak security hygiene that had been surviving purely
  because the DB subnet had no inbound path from the public internet.
- **The route change removes that accidental protection.** The app keeps
  working perfectly — nothing breaks, nothing alerts, no error appears
  anywhere in the telemetry pipeline — while the database is now directly
  reachable from the internet with weak credentials. MyLearn's own framing:
  "the network continues to work perfectly... but a new security issue is
  introduced," and cites research that **exposed databases with guessable
  credentials are breached within 30–45 minutes of exposure.**

**Why this is the more dangerous failure mode than the Science App scenario:**
there, a human had to decide to widen access to more client types — a
decision someone could review. Here, a routine, unrelated routing change is
the entire cause; nothing in the change itself mentions the database, and the
database's vulnerability (weak credentials) was true both before and after
the change — only reachability changed. **This is exactly the class of bug
Section 5.5's earlier point about compartment/NSG blast radius doesn't catch
by itself**, since the App and DB subnets in this scenario are *both* public
to begin with; there's no compartment boundary or private-subnet design being
violated, just a route table change with an unintended side effect three
layers away from the person who made it.

**The ZPR fix — same one-line-policy pattern as the Science App case:**

![](5.%20Security%20—%20OCI%20IAM,%20WAF,%20Certificates,%20Vault,%20Cloud%20Guard/mylearn_zpr_carco_protected.png)

```
in networks:carconet VCN allow apps:tele-app endpoints
to connect to db:tele-db endpoints
```

- The Telemetry Receiver App is tagged `apps:tele-app`; the Database is
  tagged `db:tele-db`. The policy allows only that specific tagged pair to
  connect — nothing about a route table, subnet, or gateway is referenced.
- **The network engineer can still make the exact same routing change as
  before** — ZPR doesn't block or restrict the route update itself. The
  diagram shows the External Attacker's connection now blocked (⊘, labeled
  "No route to DB" from the attacker's perspective) purely because ZPR
  enforcement sits in the packet path independent of whatever the route table
  says.
- **The core lesson, stated directly on the slide: "networking changes can't
  invalidate ZPR security policies."** This is the real value proposition
  ZPR is pitched on — not "fewer rules to write" (the earlier NSG-typo
  argument) but **structural independence between whoever manages routing and
  whoever's security intent must hold**, so a well-intentioned, functionally
  correct network change can no longer accidentally become a security
  incident. This is the same "decoupling security from network
  configuration" pillar from the four-pillar slide, now shown solving an
  accidental-misconfiguration case rather than a broadened-access case.

**Provisioning ZPR via Terraform — supported, not Console/CLI-only.** Two
resource types, in the `oracle/oci` provider since **v6.12.0 (October
2024)**:

```hcl
# One-time: onboard ZPR into the tenancy (must target the root compartment)
resource "oci_zpr_configuration" "this" {
  compartment_id = var.tenancy_ocid
  zpr_status     = "ENABLED"
}

# The policy itself — statements are ZPR Policy Language, list, max 25 per policy
resource "oci_zpr_zpr_policy" "this" {
  compartment_id = var.tenancy_ocid
  name           = "example-zpr-policy"
  description    = "Compute-to-database access"
  statements = [
    "endpoint type='database' from security_attribute='app-tier' to security_attribute='db-tier' allow"
  ]
}
```

**The gap to know about:** the security attributes themselves (the
`#app:science`/`#database:sensitive`-style tags shown on resources above)
are **not** a standalone `oci_zpr_*` resource — they're attribute
blocks/fields added incrementally, service by service, onto each individual
OCI resource type as Oracle extends ZPR support (Compute landed in v6.15.0;
Functions, HeatWave, OpenSearch, and GoldenGate landed together in v7.22.0,
Oct 2025). This means the *policy engine* (`oci_zpr_zpr_policy`) has been
stable and available since late 2024, but whether a specific target resource
type can actually be *tagged* with a security attribute via Terraform depends
on when that service's provider support shipped — worth checking the current
provider's resource docs for the specific service in a real design rather
than assuming blanket ZPR-tagging coverage.

## 5. Posture, detection, vulnerability management, and audit

### Cloud Guard and Security Zones

- **Cloud Guard** monitors configuration weaknesses, metrics/logs, and risky activity. Detectors create problems; responders can suggest, assist, or automatically perform corrective actions.
- Target Cloud Guard at the tenancy or selected compartments. Test automatic responders before broad production use.
- **Security Zones** are preventive guardrails assigned to compartments. OCI validates create/update operations against their recipe and denies violations, such as a prohibited public subnet.
- Use Security Zones to prevent future noncompliance; use Cloud Guard to find existing drift/risk. Cloud Guard must be enabled before Security Zones are created.

### Vulnerability scanning and investigation

- **VSS** scans Compute hosts and container images for vulnerabilities, exposed ports, and configuration/benchmark issues. Configure recipes and targets at the needed compartment scope.
- Private targets require a suitable network path (for example, Service Gateway) and permissions. Scanning does not replace patching or endpoint detection/response.
- Surface VSS results in Cloud Guard when centralized triage/remediation is needed.
- **Audit** answers who did what and when for OCI API activity. Use Logging, Connector Hub, Object Storage, and/or a SIEM for analysis and retention.

| Requirement | OCI starting point | Key distinction |
| --- | --- | --- |
| Prevent public or noncompliant resource creation | Security Zones | Preventive: operation is denied. |
| Find weak configuration/risky activity and respond | Cloud Guard | Detectors create problems; responders can act. |
| Find CVEs, open ports, host/container issues | Vulnerability Scanning Service | Scanning, not behavioral threat detection. |
| Investigate API changes | Audit + Logging/SIEM | Evidence trail, not automatic remediation. |
| Protect web applications from SQLi/XSS/bots/floods | OCI WAF | L7 protection; prevent origin bypass. |
| Protect encryption keys and credentials | Vault + Secret Management | Separate lifecycles for keys and secrets. |
| Find sensitive data in Oracle Database | Data Safe | Not generic Object Storage Macie equivalence. |

## 5.5 Composing this note into one architecture

Every control above is covered individually, but the diagram shows how they actually
compose into a real design — worth walking end-to-end once, since the exam tests
whether you can place controls in relation to each other, not just define each one:

**Compartment split, not just a network boundary:** the diagram separates
**Frontend-Compartment** (edge, LB, web tier) from **Backend-Compartment**
(app/DB/bastion) as two distinct IAM/compartment boundaries, each with its own VCN
— not one flat VCN with subnets. This is a deliberate blast-radius design: a policy
compromise or misconfiguration in the frontend compartment doesn't automatically
carry authorization into the backend compartment's resources, since compartments
are the actual IAM scoping boundary (Section 1's "Core OCI model"), not just a
labeling convention.

**Edge path, layered, each control doing a different job:**
`Public Internet → WAF → Network Firewall → Load Balancer (private subnet) → Web
Servers`. This directly matches Section 4's "Design check" callout (WAF inspects web
requests, Network Firewall inspects routed traffic, NSGs/security lists allow-or-deny
flows) — the diagram is the concrete instantiation of that abstract layering
statement. Notice the Load Balancer sits in a **private subnet** behind the Network
Firewall, not directly internet-facing — this is the "protect the origin separately
so traffic cannot bypass WAF" principle from Section 4's WAF notes, made literal:
even if someone found the LB's address directly, the Network Firewall/WAF path is
still the only route in per the VCN's routing, not just a recommendation to trust.

**TLS terminates at the Load Balancer, backed by two separate services:**
**Certificates** (Section 3) issues/manages the cert; **OCI KMS/Vault** (Section 2)
protects the private key material behind it. The diagram shows both feeding the LB
independently — this is envelope encryption's general shape (a key-management layer
underneath a service-specific credential) showing up again, the same pattern Section
2 already describes for data encryption, just applied to TLS instead of storage.

**App tier reached only from the LB, DB tier reached only from the App tier:** the
diagram's dashed lines (App Subnet-Private ↔ DB Subnet-Private, App Subnet-Private ↔
Web Servers) show NSG-to-NSG trust exactly as described in Section 1's "same
philosophy shows up in networking" callout — each tier only accepts traffic from the
specific NSG in front of it, not from a broad CIDR. This is the least-privilege
tier-isolation pattern from Note 9 Section 3, drawn as an actual architecture instead
of described abstractly.

**IAM, Vulnerability Scanning, and Security Zone are drawn as cross-cutting, not
tier-specific:** IAM (Users/Groups/Policies) and Vulnerability Scanning sit outside
both compartments in the diagram, dashed-line-connected into the Web Server and App
tiers — visually reinforcing that these are tenancy/compartment-wide controls
applied *across* the architecture, not a resource living inside one subnet the way a
Load Balancer or web server does. The **Security Zone** wraps the Backend
Compartment's private subnet specifically (not the whole architecture) — a concrete
example of Section 5's "Security Zones are preventive guardrails assigned to
compartments," scoped here to just the tier that needs the strongest prevent-drift
guarantee.

**Admin access comes in through Bastion, not a direct path:** `OCI Admin → Bastion →
Private Subnet` on the diagram's right edge is Section 4's "Use Bastion and private
subnets for administration instead of broadly exposing SSH/RDP" principle, again
made concrete — notice the OCI Admin icon has no direct line to any app/DB/web
resource; Bastion is the only route drawn, matching [[terraform/lab-bastion-stack]]'s
actual implementation of this same pattern (private instance, no public IP, reached
only through a managed Bastion session).

**What the diagram does *not* show, worth noticing as an omission:** no Cloud
Guard icon and no explicit Audit/Logging path are drawn, even though both are core
to this note's Section 5 coverage. Don't read a reference diagram as a complete
control checklist — it's illustrating the *preventive/edge* control composition
specifically; posture monitoring (Cloud Guard) and the audit trail (Audit/Logging)
are tenancy-wide services that apply regardless of which architecture diagram you're
looking at, not something every diagram needs to re-draw.

**Update — "Step 4: Detect, Monitor, and Respond" fills that exact gap.** A
later slide in the same MyLearn module reuses this identical architecture but
adds the two missing pieces called out above: **Cloud Guard** and **Logging
Analytics**, both anchored on the public-internet side of the diagram
alongside WAF, feeding posture/log signal across the whole architecture
rather than living inside either compartment:

![](5.%20Security%20—%20OCI%20IAM,%20WAF,%20Certificates,%20Vault,%20Cloud%20Guard/mylearn_detect_monitor_respond_diagram.png)

The two diagrams together are the full picture: the original shows

## 6. Recall / design exercises

- [ ] A Compute instance in prod-app needs read-only access to one Object Storage workload. Draft its dynamic-group rule and least-privilege policy. Why is a user/API key worse?
- [ ] A regulated workload must never create a public subnet and must use customer-managed keys. Choose Security Zones versus Cloud Guard, and explain why both may be appropriate.
- [ ] An internet-facing application faces HTTP floods and SQLi. Place WAF, Load Balancer, NSGs, and—if needed—Network Firewall in the design. How does the origin avoid bypass?
- [ ] A secret must rotate safely and survive a regional failure. Explain pending/current/previous secret versions and the source/replica design.
- [ ] Translate “an EC2 application assumes an AWS role” to OCI principals, dynamic groups, and IAM policies. Identify the compartment boundary that limits blast radius.
- [ ] Explain why NSG-to-NSG security rules and IAM dynamic groups are the "same idea" applied to two different domains. What static-trust pattern are both replacing?
- [ ] A lab Terraform config injects an SSH public key via instance metadata. A teammate asks if the database password should go the same way. What's the correct answer and why?
- [ ] Explain why creating an API Gateway and Function via Terraform (under an Administrators identity) succeeded, but the Gateway calling the Function at runtime failed with a 500 — what two separate principals are involved, and what closes the gap?
- [ ] Write the dynamic-group matching rule and policy statement needed for a Compute instance (not a Gateway) to invoke a Function in the same compartment. What resource.type value changes?
- [ ] A policy accidentally grants `manage` instead of `use` on `functions-family` to a dynamic group. What additional actions does that dynamic group now have that it shouldn't, given the verb hierarchy?
- [ ] A newly created dynamic group and policy match documented syntax exactly, but a service call in a non-home region keeps failing with an authorization error. Before assuming the policy is wrong, what should you check first, and why might the fix simply be time rather than a config change?
