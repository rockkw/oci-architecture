## All OCI database (and related) offerings — granular reference

| Category | Service | What it is | When to use it |
| --- | --- | --- | --- |
| Oracle Database | **Base Database Service** | VM DB Systems (single-instance or 2-node RAC); AMD/Intel/Ampere shapes; LVM or ASM storage. | Need full OS/DB admin control (e.g., custom init parameters, OS-level tooling) but still want OCI-managed VM infra; lift-and-shift of an existing on-prem Oracle DB with minimal re-architecture. |
| Oracle Database | **Exadata Database Service** | Oracle Database on Dedicated Exadata infrastructure. | Large-scale, high-performance OLTP/DW workloads needing Exadata-specific acceleration (Smart Scan, Hybrid Columnar Compression) with full customer control over the database layer. |
| Oracle Database | **Autonomous Database — Serverless** | Oracle-managed, auto-scaling; OCPU/ECPU compute models. | Fast provisioning with minimal ops overhead for new apps, dev/test, or variable-traffic workloads (e.g., a SaaS app needing auto-scaling without a DBA team). |
| Oracle Database | **Autonomous Database — Dedicated** | Customer-owned Exadata infra (5-layer architecture: Exadata Infra → AVM Cluster → ACD → ADB → Backup). | Multi-tenant consolidation at scale with strict resource isolation, custom patch scheduling, or regulatory requirements needing dedicated (not shared) infrastructure. |
| Oracle Database | **Autonomous Database — Exadata Cloud@Customer** | Autonomous Database deployed on customer premises. | Data must stay physically on-premises (sovereignty/latency/regulatory) but still want Autonomous's managed-service model. |
| Oracle Database | **Autonomous Database — Dedicated Region Cloud@Customer** | Full OCI region deployed on customer premises. | Government/regulated entities needing an entire OCI region on-prem — full service parity with public OCI regions under strict data-residency mandates. |
| Oracle Database | **Globally Distributed Autonomous Database** | Automated sharding service built on Autonomous Database Dedicated. | Multi-region apps needing horizontal write scale (billions of rows) or hard data-sovereignty requirements (e.g., EU customer data must stay in the EU shard). |
| Non-Oracle | **MySQL HeatWave** | OCI's managed MySQL service; a genuinely separate category, not an Oracle-engine variant. | Existing MySQL-based apps (e.g., WordPress, common web-app stacks) or workloads needing combined OLTP+analytics without a separate data warehouse (HeatWave's in-memory analytics engine). |
| NoSQL | **Oracle NoSQL Database Cloud Service** | Not a DynamoDB drop-in — model/API/consistency design must be reassessed. | Key-value/document workloads needing single-digit-millisecond latency at scale — e.g., session state, user profiles, IoT device data. |
| External | **External Database service** | Registers/manages an Oracle Database running outside OCI (on-prem, another cloud, self-managed compute) through OCI's tooling — the database itself doesn't migrate. | Hybrid/multicloud scenarios where a database can't move yet (compliance, migration timeline) but you still want unified OCI monitoring/management across your estate. |
| Backup/DR | **Autonomous Recovery Service (ARS)** | Centralized backup for Base DB, Exadata Database Service, Autonomous Database Dedicated, and multicloud (Oracle Database@Azure, @Google Cloud). | Standardizing backup/recovery across a mixed fleet of Oracle databases (multiple services and/or clouds) under one policy-driven, ransomware-resistant backup solution. |
| Backup/DR | **Zero Data Loss Autonomous Recovery Service (ZRCV)** | Extra-cost, real-time-protection tier of ARS; sub-second RPO. | Mission-critical databases where even a few minutes of data loss is unacceptable (e.g., financial transaction systems). |
| Backup/DR | **Autonomous Data Guard** | Autonomous Database-specific DR (Serverless and Dedicated variants); local/cross-region standby, RTO/RPO-defined. | Production Autonomous Database workloads needing near-zero RPO/RTO DR, with automatic (local) or manual (cross-region) failover. |
| Backup/DR | **Backup-Based DR** | Lower-cost, higher-RTO alternative to Autonomous Data Guard for Autonomous Database; local peer always on by default. | Non-production or less-critical Autonomous Database workloads where a lower-cost DR posture is acceptable and hours-scale RTO is tolerable. |
| Tooling | **Database Actions** | Preconfigured web tool suite per Autonomous Database instance (SQL Developer Web, Data Pump, Data Modeler, APEX, REST, etc.). | Quick, no-install access to SQL development, data loading, modeling, or low-code app building (APEX) directly against an Autonomous Database instance. |
| Caching | **OCI Cache** | Managed distributed in-memory caching; non-shard (1–5 nodes) or shard cluster types. | Reducing repeated read latency/DB load for hot data — e.g., session storage, leaderboard data, frequently-read reference data in front of any backend database. |

### Translation from AWS database notes

| AWS memory anchor | OCI service/pattern | OCI distinction |
| --- | --- | --- |
| RDS | Base Database Service | OCI choice begins with Oracle Database control/operations, licensing, HA, and recovery—not merely managed-service similarity. |
| Aurora / Aurora Serverless | Autonomous Database, Base Database, or Exadata Database Service | There is no direct Aurora equivalent. Choose based on engine requirement, autonomy, isolation, scale/performance, and Oracle licensing. |
| Aurora Global Database + DynamoDB Global Tables (no single match) | Globally Distributed Autonomous Database | **No direct AWS equivalent** — this is Oracle's managed/automated version of a pattern AWS customers typically hand-roll themselves (app-level sharding across RDS/Aurora instances). Aurora Global Database covers only the replication half (one-writer-region + cross-region read replicas, not true multi-shard active-active writes); DynamoDB Global Tables covers the active-active multi-region-write half but is NoSQL/eventually-consistent, not relational/ACID. Neither gives you a managed Shard Catalog, Sharding Director, or automated rebalancing. |
| Read Replica / Multi-AZ | Data Guard, RAC, read replicas/features by database service | Separate read scale, local HA, and DR. Data Guard protection mode and failover design matter. |
| DynamoDB | Oracle NoSQL Database Cloud Service | NoSQL model/API/query/consistency design must be reassessed; it is not a DynamoDB drop-in replacement. |
| DAX / ElastiCache | OCI Cache or application/database caching pattern | Cache choice depends on supported engine, topology, TTL, invalidation, and HA; cache is not a durable database. |
| RDS Proxy | Database connection pool/proxy pattern | Choose driver, pool, proxy, or service feature based on application connection behavior; no blanket one-service mapping. |

## Four supported database service categories

MyLearn frames the whole OCI Database module around four categories, not
a flat service list — worth knowing this taxonomy before the per-service
detail:

1. **Oracle Database** — the Oracle-engine services covered below (Base
   Database, Autonomous Database, Exadata Database Service).
2. **Non-Oracle — MySQL** — OCI's own managed MySQL service (HeatWave),
   a genuinely separate category from the Oracle-engine services, not a
   variant of them.
3. **NoSQL Database** — Oracle NoSQL Database Cloud Service (see the
   DynamoDB-is-not-a-drop-in-replacement warning already in this note).
4. **External Database** — Oracle Database running **outside** OCI
   (on-premises, another cloud, or self-managed compute) but **registered
   with and managed/monitored through OCI's Database service tooling**.
   A distinct category from "migrate it to OCI" — the database itself
   stays wherever it is; only its management plane integrates with OCI.
   Worth remembering as a real option for a hybrid/multicloud scenario
   question, not just Base/Autonomous/Exadata as the only three answers.

## Select the database from requirements

- **Autonomous Database:** choose when Oracle-managed automation, rapid provisioning, and reduced administration meet the workload/control requirements.
- **Base Database Service:** choose when you need more traditional Oracle Database administration/control than Autonomous Database provides.
- **Exadata Database Service:** choose for workload/performance, scale, and isolation needs that justify Exadata architecture.
- **Oracle NoSQL Database Cloud Service:** choose for NoSQL data-model/access requirements after validating APIs, consistency, indexing, and operational behavior.
- A non-Oracle engine requirement may need a marketplace/partner/self-managed design; do not claim OCI Database services are universal RDS engine replacements.

**Base Database Service — a real architectural ceiling, not just "less
managed than Autonomous."** Runs as **single-instance or 2-node RAC virtual
machines** — that 2-node cap is the concrete distinction from Exadata (which
scales RAC further, see below): if a scenario needs more than 2 RAC nodes,
Base Database Service is architecturally the wrong answer regardless of
licensing/control preferences. Cloud automation (provisioning, patching,
backup, DR) stays under customer control here — three named benefits:
improved availability via RAC, faster admin task execution, and secure
isolated environments. Runs all supported Oracle database versions — engine
compatibility isn't the differentiator versus Autonomous/Exadata, node
count and management model are.

**Exadata Database Service — positioning, not just "the high-end option."**
MyLearn's own framing: "the highest-performing and most-available platform
for running Oracle Database," explicitly for mission-critical OLTP *and*
Analytics workloads (not one or the other). Two concrete, named guarantees
worth remembering verbatim: **100% compatibility with on-premises
applications and Oracle database** (a real migration-risk-reduction claim,
not marketing fluff — directly relevant to a "minimize app-compatibility
risk during Oracle migration" scenario), and **infrastructure deployed and
managed by Oracle** even though the workload/data stays under customer
control — paired with **monthly subscription, no capital expenditure**,
i.e. Exadata's on-OCI value prop is explicitly OpEx-vs-CapEx framed, not
just performance.

## Autonomous Database — Overview: the shared-responsibility contrast and concrete numbers

Full lecture transcript captured. The framing worth having precisely:
Base Database Service and Exadata Database Service are explicitly named
**"semi-managed"** — a real shared-responsibility split where the
*customer* triggers patching, upgrades, manual scaling, query tuning,
failure handling, security patching, and HA configuration. Autonomous
Database's whole value proposition is framed directly against that list —
automating every one of those customer-triggered actions away, not just
"being easier to use."

**Concrete, named numbers worth having verbatim:**
- **Provisioning takes 2-3 minutes** — stated as an explicit target for
  rapid production deployment, not a vague "fast" claim.
- **Auto Scale ceiling: up to 3x the provisioned compute**, triggered
  automatically by demand, scaling back down automatically when demand
  falls — **instant, with zero downtime** (contrast this with the general
  "scaling operations usually incur downtime" framing given for
  traditional database systems earlier in this same transcript — Autonomous
  is the explicit exception to that default).
- Storage scaling is **also automated**, separate from compute scaling
  (same independence principle already documented for Base Database
  Service's data/RECO storage above, but here it's automatic rather than a
  manual operation you trigger).

**Security — two facts worth knowing precisely, not just "it's secure":**
- **Database Vault restricts even OCI's own database administrators from
  accessing customer data** — "None of the database admins in OCI can
  check into your database" — a real, named internal-threat-model
  guarantee, not just external-attacker protection.
- **Encryption is mandatory, not optional** — "the biggest concern around
  your data security... is addressed by mandatory data encryption rule
  which encrypts your data, whether at rest or in motion." Ties directly
  to the earlier "encrypted by default, only the key-management choice
  varies" pattern already documented for OCI storage services generally —
  Autonomous Database applies the same non-optional encryption principle.

**Architecture note**: provisioned in a **multitenant architecture**,
**scale-out design** built on **Oracle RAC** and **Exadata** infrastructure
— the underlying HA/scale mechanism is the same RAC+Exadata combination
already covered for Base/Exadata Database Service, just fully automated
rather than customer-configured.

**Automatic failure recovery, stated as a named benefit**: automatic
detection and recovery from physical corruption or infrastructure
failure, removing manual intervention — explicitly framed as avoiding
"chances of human errors and delays," not just faster recovery.

**Ecosystem integration named explicitly**: OCI IAM/authentication,
Oracle Analytics Cloud, OCI Object Storage, SQL Developer, APEX, Oracle
Developer Cloud Service, plus third-party BI/data-integration tools —
worth knowing this is explicitly positioned as broadly integrated, not a
walled-off service.

## Auto Provisioning — RAC node placement is itself automated

Part of Autonomous Database's "Self-Driving" attribute set: Auto
Provisioning creates a **pluggable, multitenant, RAC-enabled** database
automatically, on Exadata hardware, from just compute/storage inputs — no
manual hardware/software configuration. **One genuinely non-obvious
detail**: Autonomous Database itself **automatically decides which node(s)
of the RAC cluster the database resides on** — it "may be open on one or
more nodes" and can add cluster nodes for elasticity, all without the
customer choosing node placement manually. This is the automation layer
sitting underneath the RAC+Exadata architecture already documented for
Autonomous Database generally — here specifically framed as "even RAC node
placement is self-managed," not just "RAC provides HA."

## Autonomous Database Serverless Provisioning — concrete numbers, network access tiers, and auth modes

Full lecture transcript captured. Dense, exam-relevant material — real
numbers and named options worth having precisely, not paraphrased.

**Every real field on the actual Console "Create Autonomous Database"
screen — a full list, since a skill-check question specifically asks
"which three are inputs provided when provisioning" and every option in
that question (including the ones NOT among its intended three) turned
out to be a genuinely real field, not a fabricated distractor:**

- **Display name** — the database's name.
- **Deployment type** — Serverless vs. Dedicated (etc.) — **fixed/read-only
  after creation**, a one-way door.
- **Workload type** — ADW, ATP, AJD, APEX — changes storage min/max limits.
- **Network access type** — the three-tier choice (Secure access from
  everywhere / Allowed IPs & VCNs / Private endpoint only) — the one
  provisioning-time choice that **can** be changed later via "More
  actions," unlike most of the others on this list.
- **Compute model** — OCPU vs. ECPU — **locked in at creation**, cannot be
  changed afterward except via the "Change compute model" link *during*
  the create flow itself.
- **Storage** — size, in TB (OCPU) or GB/TB (ECPU, ATP only).
- **License type** — Bring Your Own License vs. License Included.
- **TDE master key / encryption choice** — Oracle-managed vs.
  customer-managed key.
- **Patch level** — Early vs. Regular — also locked at provisioning.
- **Admin (superuser) password** — a real field you set here too.

**The exam-relevant lesson, not a fabricated-distractor trap this time**:
a MyLearn skill-check question asked "which three are inputs provided
when provisioning an Autonomous Database," offering five real, true
fields as options (deployment type, network access type, workload type,
compute model and shape, name of superuser) and expecting exactly three
of them: **deployment type, network access type, workload type**
(platform feedback verbatim: "you provide the display name, type of
network access, type of workload, the type of deployment, version,
license type, encryption type, etc."). **Compute model and superuser
name are both real provisioning inputs too** — they just weren't among
the three *this specific question* was built around. The trap here isn't
"spot the fake fact," it's narrower: knowing a fact is true doesn't mean
it's part of the specific subset a "pick N" question is asking for —
check the *scope* of the question, not just whether each option is real.

**Availability SLA, stated as a concrete figure**: **99.95%** — the
Serverless deployment adopts Oracle Maximum Availability Architecture
practices to hit this. Always-on encryption at rest and in motion is
**preconfigured**, matching the "mandatory, not optional" encryption
principle already documented for Autonomous Database generally.

**Shared responsibility, stated explicitly for Serverless specifically**:
Oracle owns provisioning, infrastructure management, and meeting the SLA.
The customer owns **provisioning the database itself** (the logical
database, not infrastructure), controlling end-user access, and managing
application data/users — a narrower customer scope than Base Database
Service's shared-responsibility split documented earlier in this note.

**Compute — two pricing models, OCPU vs. ECPU, with real numeric
differences:**
- **OCPU** (legacy model) — one physical core with hyperthreading enabled.
  **Minimum: 1 OCPU.** Storage cost for automatic backup is **bundled
  into** the OCPU price. **Backup retention is fixed at 60 days and cannot
  be changed.**
- **ECPU** (new, **now the default** model) — not a physical core/thread;
  cores are drawn from a shared compute/storage pool, giving a hardware-
  independent, consistent pricing metric. **Minimum: 2 ECPUs**, and "two
  ECPUs cost less than one OCPU." Backup storage is billed **separately**
  from compute. **Backup retention is configurable from 1 to 60 days**
  (real flexibility OCPU doesn't have).
- **Auto Scaling of compute is enabled by default** at provisioning
  (opt-out via unchecking it) — a different default than storage
  auto-scaling, below.

**Storage — min/max depends on workload type AND compute model:**
- **ADW, either compute model**: size specified in **TB**, min **1 TB**,
  max **384 TB**.
- **ATP with OCPU model**: same as ADW — TB, min 1 TB, max 384 TB.
- **ATP with ECPU model**: size in **GB or TB**, min **20 GB** (much
  finer-grained than the OCPU model's 1 TB floor), max 384 TB.
- **Auto Scaling of storage is DISABLED by default** — the opposite
  default from compute auto-scaling above; must be explicitly enabled.

**Auto-scaling mechanics and billing, precisely — both directions are
online, zero-downtime operations, existing connections stay intact
throughout ("scaling in progress" is the lifecycle state, not an
outage):**
- **Compute auto-scale**: when enabled, CPU/IO resources scale up to
  **3x** the currently-allocated value shown in the console — automatic,
  no manual trigger. **Billed on actual usage, averaged over each hour**
  — not flat-rate for the ceiling. **Auto-scale does NOT scale everything
  else** — session count, memory allocation, and the concurrency/
  parallelism settings tied to the predefined consumer-group services
  (see the five-tier consumer group section above) **stay fixed** at
  their configured values regardless of compute auto-scaling. Disabling
  auto-scale reverts the available CPU/IO back to whatever the base value
  was — either the original provisioning value, or a later manual
  scale-up value if one happened before auto-scale was turned on.
- **Storage auto-scale**: when enabled, can use up to **3x the reserved
  base storage** value automatically, no manual intervention needed as
  usage grows. **Billed on allocated storage for the hour, rounded up to
  the nearest TB.** Disabling storage auto-scale sets the reserved base
  storage to the nearest TB **above** whatever was actually allocated at
  that point — not back down to the original provisioning value the way
  compute reverts.

**Live Console demo confirms a real hard floor, not just a stated
minimum**: on an actual `Manage resource allocation` screen for a live
ECPU-model ATP instance provisioned with 2 ECPUs / 20 GB, **the UI itself
would not let ECPU count go below 2 or storage go below 20 GB** — "we
cannot reduce below 2 ECPU count... you cannot reduce below 20 GB." The
per-model/per-workload minimums documented above aren't just provisioning-
time guidance — they're an enforced floor on every subsequent scale-down
attempt too. Concrete 3x example shown live: 2 ECPUs scaled to 3, with
auto-scale then enabled meaning up to **9 ECPUs** (3 × 3) become available
automatically. Scale-up and scale-down (via Shrink first, per the
criteria above) can both be done from the same `Manage resource
allocation` screen, for compute and storage independently or together in
one operation — confirming these aren't two separate workflows.

**Three named network access options, each with different authentication
rules — a real, testable structure:**
1. **Secure access from everywhere** (the **default**) — public endpoint,
   public IP, hostname; internet-accessible. **Enforces mTLS** (mutual
   TLS) — both client and server authenticate each other via certificate;
   requires downloading a **wallet/credential file** to the client.
2. **Secure access from allowed IPs and VCNs only** — still has a public
   endpoint, but access is restricted to an **access control list** of
   allowlisted IPs, or to specific VCNs via their own security rules.
   **Supports both mTLS or TLS** — mTLS is the default (via a "Required
   mutual TLS" checkbox, checked by default), but can be relaxed to allow
   either.
3. **Private endpoint access only** — for the most sensitive data: private
   endpoint, private IP, hostname; only reachable from the specified VCN,
   with NSG ingress/egress rules controlling actual access. Same mTLS/TLS
   flexibility as option 2 (mTLS default, relaxable).

**Client connection mechanics, precisely**: all connections use **TLS
1.2**, **TCPS** transport. **mTLS requires the downloaded credential/
wallet file** on the client; **TLS-only connections don't need the wallet
file**, but require either an access control list or a private endpoint to
already be configured as a network-layer prerequisite. Supported drivers
named explicitly: **JDBC Thin Driver, JDBC OCI, OCI, ODBC, python-
oracledb.**

**TDE master key encryption choice, and patch level, named as required
provisioning inputs** (beyond the compute/storage/network choices above):
Oracle-managed vs. **customer-managed key** (which can live in the *same*
tenancy as the database or a *different* one — a real cross-tenancy
capability worth remembering) for the TDE master key specifically, and a
**patch level** choice of **Early** (patches apply ~1 week before public
release — named use case: validating a test instance against upcoming
patches before they hit production) vs. **Regular** (patches apply on
public release).

## Serverless Provisioning demo — confirmed mechanics plus real new details

Hands-on Console walkthrough, confirming the prior lecture's claims
directly against the real UI, plus several details not covered
conceptually:

**Compute model choice is locked in at provisioning — cannot be changed
afterward.** "Post provisioning, you won't be able to change the compute
model. So that decision you need to take when you are provisioning
Autonomous Database." A real, consequential one-way door — ECPU is the
Console's own default, and switching to OCPU is only possible **during**
the create flow (a "Change compute model" link on the creation form
itself), never after. Confirmed live: switching to OCPU in the demo
immediately updated the minimum from 2 ECPUs to **1 OCPU**, and storage
minimum from 20 GB back to **1 TB** — the OCPU/ECPU minimums interact with
storage minimums exactly as documented in the conceptual lecture, shown
live here.

**Long-term backup scheduling, a real feature not mentioned in the
conceptual lecture**: separate from the 1-60 day automatic backup
retention window, you can schedule a **long-term backup** with its own
retention: **minimum 90 days, maximum 10 years**, on a monthly/weekly/
one-time schedule. A genuinely different backup mechanism/purpose than
the short automatic retention window — long-term archival vs. short-term
operational recovery.

**Storage scale-down requires a Shrink operation first — now with the
real, exact criteria** (a later lecture filled in what this demo only
gestured at): "if you want to scale down, you can first perform the
Shrink operation before doing the scale down operation." Storage can be
increased freely, but decreasing it isn't a direct operation — Shrink is
a separate, named prerequisite step, gated by **two concrete conditions,
both required**: (1) **allocated storage must be greater than the
reserved base storage**, and (2) **allocated storage minus used storage
must be greater than 100 GB**. If usage is much lower than what's
allocated, Shrink reduces the allocated value down before you disable
auto-scaling and set a new (lower) reserved base storage value.

**Data Safe integration, named as a bundled security capability**: "data
security solution for your Autonomous Database" — auditing, activity
monitoring, sensitive-data discovery, and data masking, all available
directly from the database's own details page, not a separately
provisioned add-on you need to configure from scratch.

**Network access type can be changed post-provisioning** — confirmed via
the "More actions" menu's "update the network access" option: unlike the
compute-model lock-in above, network access tier (Everywhere/Allowed-IPs/
Private-endpoint) is NOT a one-way decision.

**A few other real, named "More actions" operations worth knowing exist**:
stop/restart, create a clone, Data Guard switchover (if Autonomous Data
Guard is configured), reset admin password, update license, auto start/
stop scheduling, switching TDE master key from Oracle-managed to
customer-managed **after** provisioning (a real post-provisioning option,
distinct from choosing it upfront), rename, move to a different
compartment, and terminate.

## Connecting to a private-endpoint Autonomous Database — the full Bastion tunnel pattern

A complete, real end-to-end architecture worth having precisely — connects
directly to Note 5's existing OCI Bastion coverage, now applied to a
database-specific scenario: reaching a **private-endpoint** Autonomous
Database from an **external client over the public internet**, without
ever exposing the database itself publicly.

**The six-step pattern, in order:**
1. **Update the Autonomous Database's network access type to Private
   Endpoint** (from whatever it was before — e.g. Secure Access from
   Everywhere). **A Network Security Group is a mandatory input for this
   update** — confirmed via a real, live error: attempting the update
   without one fails with "the Autonomous Database private endpoint VCN
   OCID is not associated with a network security group."
2. **Create a Bastion service** — must be in the **same VCN** as the
   Autonomous Database (not necessarily the same *subnet* — the demo puts
   the Bastion in the VCN's **public** subnet, the database in the
   **private** subnet). CIDR allowlist for the Bastion itself can be
   `0.0.0.0/0` when the actual client will connect from anywhere over the
   internet — the Bastion's own broad allowlist is safe because access to
   the *database* is still gated by the NSG rule in the next step.
3. **Add an NSG ingress rule** scoped to the **Bastion's own private
   endpoint IP** (as a `/32` CIDR) as the source, TCP protocol, destination
   port **1522** (Autonomous Database's listener port) — this is the rule
   that actually restricts database reachability, not the Bastion's own
   broad allowlist.
4. **Create a Bastion session** of type **SSH port forwarding**, targeting
   the Autonomous Database's **private endpoint IP** (not the Bastion's
   own IP) on port 1522, authenticated with an SSH public key (generated
   fresh or reused).
5. **Establish an SSH tunnel from the local client machine** using the
   command the Bastion session itself provides (`ssh -i <private key> -L
   <local port>:<target>:<port> ...` shape) — this creates a local port
   (e.g. 1522) on the client that forwards through the Bastion to the
   database's private endpoint.
6. **Configure the DB client (SQL Developer, or any JDBC-based tool)
   against `localhost`, not the real database host** — the wallet's
   `tnsnames.ora` service-name host is edited to `localhost`, since the
   SSH tunnel is what actually routes that local connection through to the
   real private-endpoint database.

**Two real operational gotchas confirmed live in the demo, not just
theoretical steps:**
- **The SSH tunnel is a live, stateful process — closing it breaks the
  connection.** A connection test failed mid-demo specifically because the
  SSH tunnel session had **already ended** (exit status -1) — re-running
  the tunnel command immediately fixed it. A real, easy-to-hit failure
  mode: the tunnel isn't "set up once," it must be actively running for
  every connection attempt.
- **The wallet's `sqlnet.ora`/`tnsnames.ora` need manual edits** — the
  wallet directory path must be set in `sqlnet.ora`, and the target service
  name's host (e.g. `ouatp_high`) must be changed to `localhost` in
  `tnsnames.ora` — the downloaded wallet isn't usable as-is for this tunnel
  pattern without editing both files first.

**JDBC connection string shape, stated directly**: `jdbc:oracle:thin:@<service_name>?TNS_ADMIN=<path to extracted wallet>` (escape backslashes on Windows paths).

## Autonomous Database Cloning — three types, two sources, real constraints

**Three named clone types, each with a distinct purpose:**
1. **Full clone** — a complete, point-in-time, **read-write** copy of the
   source. Use case: dev/test environments needing real data.
2. **Metadata clone** — schemas only, **no data**. Use cases named
   explicitly: preserving object-structure history before making schema
   changes, or mirroring an application's database structure to stand up
   the same service for a different customer.
3. **Refreshable clone** — a **read-only** copy that can be refreshed
   on-demand or automatically. Detailed further below.

**Two source options, with a real feature-availability split — not every
clone type is available from every source:**
- **Clone directly from the live source database** — all **three** clone
  types available (full, metadata, refreshable).
- **Clone from a backup** (point-in-time, choose a specific backup or use
  the latest) — only **full and metadata** clones available; **no
  refreshable clone from a backup**. Also the automatic fallback: if the
  source database is unavailable during a clone attempt, the operation
  creates the clone from backup instead.

**Real mechanics worth having precisely:**
- **Database properties can be changed during clone creation** — same as
  at provisioning: name, compute, storage size, workload type, network
  access, etc.
- **Console-created clones are same-region only.** **Cross-tenancy and
  cross-region clones require the CLI or REST API** — not available
  through the Console at all, a real tool-capability gap worth
  remembering (same shape as the earlier-documented OKE Console
  limitation for custom-image node pools).
- **Zero impact on the source** — data files are copied without bringing
  the source database down; the application using the source is
  unaffected.
- **Access control lists ARE copied to the clone; private endpoint
  network config is NOT.** A real, asymmetric behavior — if the source
  used a private endpoint (see the three network access tiers documented
  earlier), that specific configuration doesn't carry over to the clone
  automatically.
- **Scheduler Jobs should be disabled before cloning** — a real,
  practical gotcha: source-configured Oracle Scheduler jobs will also run
  on the clone unless disabled first, typically via a trigger using the
  `ON CLONE` clause.

**Refreshable clone — concrete numbers worth memorizing verbatim:**
- **Refresh frequency: configurable from a minimum of 1 hour to a maximum
  of 7 days.**
- **Allowed data lag: configurable from 0 minutes to a maximum of 7
  days.**
- **Automatic refresh is ECPU-only** — not available on the OCPU compute
  model, a real capability gap between the two pricing models beyond the
  billing/minimums differences already documented.
- **Converting to read-write requires a "disconnect" operation** from the
  source — used for validating changes or troubleshooting against
  production-like data without touching production itself.
- **Reconnect must happen within 24 hours of disconnecting**, or the
  clone can never reconnect to the source again — a real, hard deadline.
- **The clone must be refreshed at least every 7 days**, or it becomes
  permanently non-refreshable. Once non-refreshable, three options: keep
  it read-only for query offloading, disconnect it to convert to
  read-write for dev/test use, or terminate it — there's no path back to
  "refreshable" once that window lapses.

**Dedicated-infrastructure-specific cloning rules, distinct from
Serverless:**
- **Metadata clones can only be created from a live instance, never from
  a backup** — full clones can come from either. A stricter rule than the
  general Serverless source-type split above.
- **You select a different target Exadata Infrastructure / AVM Cluster /
  ACD during clone creation** — the clone doesn't have to land in the
  same infrastructure stack as its source.
- **Target container database version must be the same or higher** than
  the source's version — never lower.
- **Source and target must use the same keystore type.**
- **The clone's admin password must differ from the source's** — a real,
  enforced security requirement, not just a suggestion.
- **If Autonomous Data Guard is enabled on the source, the clone must be
  initiated from the primary** — unless the source of the clone is a
  backup, in which case that backup can come from either the primary or
  the standby.

**Demo: Autonomous Database Cloning — live confirmations and console-flow
details:**
- **Create Clone is reached via More Actions on the source ADB's details
  page** — same entry point regardless of which of the three clone types
  you pick next.
- **Clone from Database Instance vs. Clone from Backup is the first
  choice, and it visibly gates the Refreshable clone option in the
  Console UI** — selecting "clone from backup" greys out/disables
  Refreshable clone; switching to "clone from database instance"
  re-enables it. Confirms the type/source split above isn't just
  documentation — the Console itself enforces it at selection time.
  Clone-from-backup offers point-in-time, a specific backup from a list,
  or the latest backup timestamp.
- **Restore vs. clone-from-backup for logical corruption (practice exam
  attempt 2, Q5, missed):** an in-place point-in-time **restore** rewinds
  production and destroys the corrupted state. When the corrupted state
  must be kept for investigation, **clone from a backup/point in time
  before the corruption**, move the app to the clone, and leave
  production untouched. A clone of the *current* database copies the
  corruption.
- **Compute model cannot be changed during cloning, same as the
  provisioning-only restriction already documented** — the Console's
  "change compute model" link, which normally opens a confirmation
  pop-up during provisioning, does nothing (no pop-up) during clone
  creation, a visible UI tell that the option is locked at this stage.
- **Elastic pools can be enabled during clone creation** under Show
  Advanced Options, but only because this example used the ECPU compute
  model — consistent with elastic pools being an ECPU-only feature.
- **Encryption key cannot be altered during cloning** — the clone
  inherits the source's encryption key (Oracle-managed vs. customer-managed,
  per the one-directional migration rule already documented) with no
  Console option to change it at clone-creation time.
- **Refreshable clone setup fields, confirmed live:** refresh frequency
  and data lag are both set as a number + unit pair (e.g., frequency = 2
  hours, data lag = 60 minutes) — both editable later from the clone's
  own details page under Clone Information, not fixed at creation.
- **Attempting a DML/DDL statement against a still-connected refreshable
  clone returns a real, specific Oracle error**: *"the database or
  pluggable database is open for read-only access"* — the read-only
  enforcement isn't just a documented restriction, it's an actual open-mode
  restriction at the pluggable-database level, the same mechanism as a
  manually opened READ ONLY PDB elsewhere in Oracle Database.
- **Disconnect/Reconnect both require re-typing the source database's
  name as a confirmation step** — not a single-click action, an explicit
  named-source confirmation each time, in both directions.
- **Disconnect and Reconnect both transition the clone into an
  intermediate "Updating" lifecycle state** before landing back on
  Available — a real, observable state transition (not instantaneous),
  consistent with [[OCI propagation delays]] applying broadly across the
  service, not just to network/IAM resources.
- **The 24-hour reconnect deadline is surfaced as a live banner on the
  clone's details page** while disconnected — it names the exact
  cutoff timestamp by which reconnection must happen, and the banner
  disappears immediately once Reconnect completes. A real, visible
  countdown, not just a background enforcement rule.
- **After reconnect, Clone Information again shows only Refresh and
  Disconnect links** — the same two-link pattern as when the clone was
  first created, confirming the refresh/disconnect/reconnect cycle is
  fully repeatable rather than a one-time operation.

## Autonomous Database Backup and Recovery — Serverless vs. Dedicated

**Serverless — automatic backups:**
- **Pre-configured, fixed schedule** — runs at a specific hour of the day
  that you **cannot disable and cannot reschedule**.
- **Oracle-managed and immutable** — cannot be changed or deleted by the
  customer.
- **Runs even if the database is stopped** — a real, easy-to-miss
  exception to "stopped means no activity."
- **Incremental backup strategy, exact cadence:** a **level 0 full backup
  every 60 days**, **daily incremental level 1** backups, and **weekly
  cumulative level 1** backups.
- **Visible in the Console** under Resources → Backups on the database
  details page.
- **Storage durability**: triple-mirrored in Object Storage. Multi-AD
  regions replicate backups across all three ADs; single-AD regions
  replicate across all three fault domains instead — same triple-copy
  guarantee either way, just at a different failure-domain granularity.
- **Retention depends on compute model** — a real, concrete split:
  - **OCPU model**: fixed **60-day retention**, storage cost **included**
    (no separate backup-storage billing).
  - **ECPU model**: **configurable 1–60 days**; if unset, **defaults to
    60**. Backup storage is **billed separately** under this model — a
    real cost-model difference between the two compute models, not just
    a retention-window difference.
- **Long-term backup** — a distinct, separate backup type:
  - **On-demand, full backup**, one-time or **scheduled (weekly, monthly,
    or yearly)**, running automatically once scheduled.
  - **Retention: 90 days to 10 years** — matches the number already
    documented for Dedicated infrastructure backup retention choices, but
    here it's a continuous range, not four fixed choices.
  - **Cannot restore/recover a long-term backup onto the same database it
    was taken from** — the only path to use it is **cloning** a *new*
    database from it, point-in-time.
  - **Prerequisite**: at least one automatic backup must already exist
    before a long-term backup can be taken.
- **Restore mechanics**: restore to a point in time (per the retention
  window) or from a specific backup in a list — the Console can
  auto-identify which backups are needed for the operation. Restoring
  also restores the **data pump directory and other user-defined
  directories** up to that point in time, not just table data.
- **During restoration, the database is in an "Unavailable" state** — no
  connections possible. **The only lifecycle operation permitted during
  restoration is Terminate.**

**Dedicated infrastructure — automatic backup:**
- Also Oracle-managed, stored in Object Storage in an **Oracle-managed
  tenancy** (not the customer's own Object Storage).
- **Can be disabled — but only at Autonomous Container Database (ACD)
  provisioning time.** Once provisioned, it can later be **re-enabled
  from the Console, but that re-enable is irreversible** — a real
  one-directional switch, worth having verbatim for the exam.
- **Cannot disable automatic backup if Autonomous Data Guard is
  enabled** — a real, enforced dependency between the two features.
- **Backup cadence**: daily incremental + weekly (full) — a coarser,
  ACD-level cadence than Serverless's 60-day-level-0/daily/weekly split.
- **Retention is set at ACD provisioning time**: **default 15 days**,
  configurable **7–95 days** via Console — a distinct range from
  Serverless's ECPU 1–60-day range; don't conflate the two.
- **Manual (on-demand) backups** are also available on Dedicated —
  cumulative incremental from the last full backup, and their retention
  follows the ACD's own configured retention period (no separate
  retention setting for manual backups).
- **Long-term backups** are also available on Dedicated, same **90
  days–10 years** range as Serverless.

**Restore mechanics on Dedicated — the details that differ from
Serverless:**
- Same two restore paths (point-in-time or from a backup list); database
  goes **Unavailable** during restoration, and **Terminate is again the
  only permitted operation** during that window — consistent behavior
  across both deployment types.
- **Post-restoration, the database reopens in the same state it was in
  before restoration started** (e.g., started stays started).
- **Restore resets the admin password to the password captured in the
  backup being used** — a real, concrete side effect worth remembering:
  restoring doesn't preserve whatever password was set *after* that
  backup was taken.
- **All backups taken between the start and completion of the
  restoration operation are invalidated** — a real, narrow window of
  backup loss caused by the restore operation itself.
- **Data Guard interaction on restore**: only the **primary's** backup
  can be restored. **If the standby is in snapshot standby role,
  restoration is not possible at all** — a hard block, not just a
  primary-only preference.

## Autonomous Database Patching — Serverless vs. Dedicated

**Serverless — patch mechanics:**
- **Applied automatically** — quarterly per the release cycle, or
  **on-demand** for a critical-vulnerability security patch outside the
  normal cycle.
- **Two patch scopes**: **infrastructure patches** (firmware, hypervisor,
  OS) and **database patches** (security/bug patches, or release
  update/release update revision patches).
- **Applied in rolling fashion** — because Autonomous Database is
  **RAC-enabled**, patches apply one node at a time without a full
  database shutdown. Applications may see a **momentary disconnect**
  during service relocation; **Application Continuity** can prevent that
  disconnect entirely.
- **Patch level: Early vs. Regular**, set only at **provisioning or
  cloning time** — **cannot be changed after provisioning.**
  - **Early**: patch applied **one week before** the official release
    date.
  - **Regular**: patch applied on the official release date.
- **Maintenance scheduling**: Oracle manages the schedule and sends
  advance notification to preset contacts. **Changing the assigned
  maintenance window requires a Service Request with Oracle Cloud
  Support** — not self-service in the Console. **Query the
  `DB_NOTIFICATIONS` view** to check maintenance status notifications.
- **Database version upgrades** are entirely Oracle-managed, with
  **minimal downtime** and advance notification.
- **Patch level rules specific to cloning:**
  - If the **source** is at **Regular**, the **clone** can be set to
    **Early** — but **not the reverse** (an Early source cannot produce a
    Regular clone... i.e., you can only move toward Early, never back to
    Regular from Early).
  - **Refreshable clones cannot have their own patch level set** — they
    always **follow the source's** setting.
  - **Autonomous Data Guard cannot be enabled if the source database's
    patch level is Early** — a real, hard restriction tying two features
    together.

**Dedicated infrastructure — patch mechanics (more layers, more
categories):**
- Oracle patches **every layer**: Exadata Infrastructure, Autonomous
  Exadata VM Cluster (AVM), Autonomous Container Database (ACD), and
  Autonomous Database (ADB) itself.
- **Quarterly maintenance patches** — Oracle schedules and performs
  fleet-wide maintenance spread across the quarter, applied to Exadata
  Infrastructure, AVM Cluster, and ACD. **Release updates are applied by
  default to ACD and ADB together with** the quarterly maintenance patch
  cycle.
- **Two update methods:**
  - **Rolling**: ACD updates one node at a time while the ADB instance
    keeps running on another node in the cluster — no full outage.
  - **Non-rolling**: requires **minimal downtime** of both ACD and ADB
    instances. Release updates (the quarterly maintenance patches) may
    include a **time zone file update**, which requires **complete ACD
    downtime** to apply — a real, specific exception to "minimal
    downtime."
- **Scheduling customization at provisioning**: choose month-in-quarter,
  week(s) within the month, day(s) within the week, and lead time for
  advance notification — a genuine, granular self-service scheduling
  option (contrast with Serverless, which requires a Support SR to
  change).
- **Skip rules**: you can **skip a quarter's patch**, but **cannot skip
  two consecutive quarters** — a real, hard rule. You can also patch
  immediately, skip an ACD's patch for the quarter, or choose a specific
  release-update or release-update-revision version to apply instead of
  the default.
- **Monthly infrastructure security patching — a separate cadence from
  quarterly maintenance:**
  - Applied only in months where a **critical security update exists**
    (defined as **CVSS score ≥ 7**) — not every month automatically.
  - Updates **both** database servers (fixing vulnerabilities/product
    issues) and storage servers (to a patched Exadata storage software
    image).
  - **21-day supply window**: begins **the 18th–21st of the month** and
    ends **the 9th–12th of the following month** — a real, memorizable
    date range.
  - **7 days advance notification** before the window starts, with the
    option to **reschedule within that same window** — but it **cannot
    be skipped, and cannot be rescheduled beyond the 21-day window.**
  - **No impact on the Autonomous Database or connected applications**
    during this specific patch type — database updates apply online via
    **Ksplice technology**, and storage servers update in rolling
    fashion.
- **One-off patches — a third, distinct patch category:**
  - Generated by Oracle for **critical issues raised via My Oracle
    Support**, made available for the customer to apply.
  - **Default schedule: applied within 72 hours** of becoming available.
    Can be rescheduled (only within the same quarter it was released) or
    applied immediately via the Console's maintenance view.
  - **Cannot skip applying a one-off patch.**
  - **Forward-merged into the next release update** — meaning a one-off
    patch not yet applied individually will still arrive automatically
    once the next release update (which includes it) is applied.

## Autonomous Data Guard in ADB-Serverless — DR, RTO/RPO numbers

**What it is:** an Oracle-managed disaster-recovery layer built on Data
Guard, automating standby database creation for extreme availability with
**zero or least data loss**. **Highly recommended for production.**
Protects against Exadata server/storage hardware failure, full AD
failure, regional disaster, control-file corruption, dictionary
corruption, and data file write errors.
- **Workload support**: **ATP and ADW only** — not named for AJD or APEX
  in this lesson, a real scope limitation worth flagging.
- Supported operations, via **both Console and API**: enable, disable,
  switchover, failover.
- **Switchover** = planned role transition (no downtime, validated
  maintenance path) — standby becomes primary and vice versa, same
  connection string, no application-side change needed.
- **Failover** = unplanned role transition after primary failure.
- **You can never directly access or view details of a *local* standby**
  from the Console — it's invisible/unreachable by design (contrast with
  cross-region standby below).
- Compute/config changes on primary (CPU count, autoscale) **replicate
  automatically** to standby.

**Local standby:**
- Same region as primary. **Multi-AD region** → standby lands in a
  **different AD**. **Single-AD region** → standby lands in a **different
  fault domain** instead — same pattern already seen for backup
  replication.
- **Automatic failover** happens only if the configured **data loss
  limit** can be guaranteed; otherwise a **manual failover** is required.
- After any failover, Autonomous Data Guard **automatically creates a new
  standby** at the (new) primary — self-healing topology.

**Cross-region (remote) standby:**
- Requires **subscribing to the paired region** first — cannot provision
  without that subscription.
- **Display name suffix pattern**: `_<region-code>` (e.g., `_PHX` for
  Phoenix, `_IAD` for Ashburn) — a real, concrete naming convention.
- **Standby count depends on compute model** — same OCPU-vs-ECPU
  single-vs-multiple split already seen elsewhere: **OCPU model → only
  one** cross-region standby allowed; **ECPU model → multiple**, one per
  separate paired region.
- **No automatic failover for cross-region** — always manual.
- After a manual failover to remote standby, Autonomous Data Guard
  **does NOT auto-create a new local standby** in that new-primary
  region — a real asymmetry vs. local standby's self-healing behavior. A
  **cross-region switchover** (not failover) does recreate the standby
  back in the original primary region.
- **Unlike local standby, remote standby details ARE visible in the
  Console** — needed for configuring its VCN/networking — but it still
  **cannot be queried/read** unless it has taken over the primary role,
  or been manually converted to a **snapshot standby**.
- **Backup/restore rules specific to cross-region standby:**
  - Automatic backup only happens **in the region currently holding the
    primary role.**
  - **Cannot restore from backup, or clone from backup, while a database
    is in the standby role.**
  - Restoring the primary from backup **causes Data Guard to recreate the
    remote standby** from that restored primary.
  - Automatic backups **can be replicated** to the remote standby — **up
    to 7 days** retained there by default, **configurable to less than 7
    days** (not more). Once that window elapses, replicated backups on
    the standby side are deleted.
- **Private-endpoint-specific operational gotcha**: network config is
  **not replicated** to standby — you must manually configure/update the
  private endpoint on standby **before** switchover/failover, including
  VCN peering and domain forwarding for wallet usage. **Always use the
  wallet downloaded from the region currently holding the primary
  role** — and note **all Autonomous Database tool URLs change** after a
  role transition, so always use the URL from the current primary
  region.

**RTO / RPO — concrete numbers to memorize verbatim:**
- **RTO** (Recovery Time Objective) = time to restore database access
  after failover. **RPO** (Recovery Point Objective) = max tolerable data
  loss during failover.
- **Local standby data loss limit** (the automatic-failover trigger
  threshold): **configurable 0–3,600 seconds**, **default 0**, but
  **Oracle recommends setting it to 60 seconds.** Automatic failover only
  fires if actual data loss is within this configured limit; otherwise
  it's a manual failover.
- **Local standby — automatic failover or switchover: RTO = 2 minutes**,
  **RPO = 0 or the configured data-loss-limit value.**
- **Local standby — manual failover: RTO = 2 minutes, RPO = 10
  seconds.**
- **Cross-region standby — manual failover: RTO = 15 minutes, RPO = up
  to 1 minute.**
- **Cross-region standby — switchover: RPO = 0 minutes** (switchover is
  planned, so no data loss either way).

**Snapshot standby (cross-region only):**
- Converts a remote standby into a **read-write** database, like
  primary, for analytics/long-running queries or validating app changes
  against live data — **without** applying production redo logs.
- Instead, redo logs are **archived and stored locally** at the snapshot
  standby's own data center while it's in this mode.
- **Hard 48-hour limit**: must be converted back to physical standby
  within 48 hours, or **Autonomous Data Guard auto-converts it back** —
  a real, enforced deadline, same "live countdown banner" UX pattern
  already seen for refreshable-clone reconnect (Console shows the
  cutoff date/time on the Snapshot Standby Database Details page).
- **All changes made while in snapshot-standby mode are discarded** once
  converted back — this is a disposable read-write sandbox, not a
  durable state.
- After conversion back, **archived primary redo logs are applied** to
  resync the (now physical again) standby.
- **Cannot terminate a snapshot standby directly** — must convert back to
  physical standby first, then terminate.

## Autonomous Data Guard in ADB-Dedicated — real contrasts with Serverless

**Configured at the Autonomous Container Database (ACD) level** — not
per-ADB like Serverless. Enabling it requires specifying the existing
Autonomous Exadata Infrastructure and AVM Cluster.
- **Automatic (fast-start) failover is NOT enabled by default** — a real,
  opposite-of-expected default; must be explicitly enabled when
  configuring Autonomous Data Guard at the ACD level.
- **If automatic failover fails, manual failover is required.** A failed
  standby that gets fixed comes back with a **"Disabled Standby" role**
  — you must run a **reinstate** operation to bring it back into active
  standby duty.
- **Cannot disable automatic backups on the ACD** while Data Guard is
  configured (consistent with the earlier-documented rule that Data
  Guard blocks disabling automatic backup).
- **Termination asymmetry**: terminating the **primary** ACD also
  terminates the **standby** ACD. Terminating the **standby** ACD only
  removes it — the primary survives, with its Data Guard configuration
  details simply removed.
- **RTO ≈ 2 minutes, RPO ≈ zero** during failover — matches Serverless
  local-standby automatic-failover numbers closely, though phrased here
  as "nearly zero" rather than a hard 0.
- **Placement options**: same-AD (single-AD region), separate AD
  (multi-AD region), or **cross-region** for higher protection — a
  superset of Serverless's local/cross-region split, framed as a single
  continuum here.
- **Two protection modes** — a genuinely new axis not present in the
  Serverless lesson:
  - **Maximum Availability mode**: **zero data loss** during automatic
    failover.
  - **Maximum Performance mode**: automatic failover triggers only when
    RPO matches the **fast-start failover lag limit** — **default 30
    seconds**, configurable **5–3,600 seconds**. Note this range and
    default differ from Serverless's local-standby data-loss-limit
    (0–3,600 seconds, default 0, Oracle-recommended 60).
- **Standby is READABLE on Dedicated** — a genuine capability Serverless
  does not have for local standby. Connect using the service name
  suffixed **`_RO`** (read-only) instead of the primary's service name.
- **Maintenance ordering is fixed and sequenced**: standby is patched
  **before** primary, with primary maintenance following **7 days
  later by default** — but that gap is **configurable from 1 to 7
  days.**
- **Read-write access to standby requires converting it to a snapshot
  standby ACD** — same pattern as Serverless's cross-region snapshot
  standby, but here it's blocked outright if automatic failover is
  configured: **you cannot convert to snapshot standby while automatic
  failover is enabled.**
- **Snapshot standby connection uses a separate service name suffix**:
  **`_SS`**, requiring its own wallet download — a third distinct
  suffix pattern alongside the primary and `_RO` names.
- **Snapshot standby hard deadline: 7 days** (not 48 hours like
  Serverless) — after which Data Guard auto-converts it back to a
  regular standby ACD.
- **While in snapshot standby mode, several operations are blocked at
  the ACD/primary level**: cannot create a new Autonomous Database,
  cannot terminate an existing one, cannot restore any Autonomous
  Database, and cannot scale up/down the primary — a real, broad
  operational freeze during this window, broader than anything called
  out for Serverless's snapshot standby.

## Autonomous Database Disaster Recovery — Backup-Based (the second DR option)

**What it is**: a **low-cost** alternative DR mechanism to Autonomous
Data Guard, using **backup of the database plus redo** to fully
instantiate a new Autonomous Database from scratch during a disaster —
not a live, continuously-synced standby.
- **Trade-off is explicit**: lower cost, but **higher RTO** than Data
  Guard — so it's recommended for **non-production or less-critical**
  databases, not mission-critical production.
- **Workload support: ALL four types** — ADW, ATP, AJD, and APEX — a
  real, broader scope than Autonomous Data Guard's ATP/ADW-only support
  documented above.
- **Console labeling quirk worth knowing verbatim**: in the Disaster
  Recovery menu, DR Type shows **"Backup-based"** and State shows
  **"Standby"** — but this "Standby" does **not** mean a live standby
  database the way it does for Data Guard; it's just a status label. The
  **Peer Role** value is **"Backup copy"** (vs. Data Guard's "Standby"
  peer role) — the terminology distinction the Console actually
  displays.
- **During switchover/failover, the peer is instantiated fresh from the
  primary's most recent backup available in that region** — not a
  pre-existing running database.

**Combining DR types — a real, flexible rule:**
- You can run **backup-based AND Autonomous Data Guard simultaneously**,
  mixed across local/remote — e.g., a local backup-based peer **plus** a
  cross-region Data Guard standby, or vice versa.
- **Hard limit regardless of combination: at most one local peer and one
  remote peer at any time** — you cannot stack multiple peers of the
  same locality.
- **You can convert/update a backup-based DR configuration to Autonomous
  Data Guard** — a real, one-directional upgrade path.

**Placement rules** — same AD/fault-domain pattern already seen
elsewhere: multi-AD region → local peer in a different AD; single-AD
region → local peer in a different fault domain; cross-region peer →
provisioned in the remote (paired) region's own AD topology.

**Local peer backup copy:**
- **Enabled by default, always present, and cannot be disabled** — a
  real, mandatory baseline DR posture for every Autonomous Database.
- **Switchover is always initiated from the PRIMARY database's own
  details page** — there is **no separate details page for the local
  peer** (contrast with cross-region peer below).
- **Switchover only succeeds if no data loss can be guaranteed** — same
  "guarantee-gated" logic as Data Guard's automatic failover trigger.
- **No automatic failover exists for backup-based DR at all** — local or
  cross-region, always manual — a real, absolute contrast with
  Autonomous Data Guard, which does support automatic failover for local
  standby.
- **Connection string and database tools URL do NOT change** after a
  local peer switchover/failover — no wallet re-download or app
  reconfiguration needed. This is a genuine advantage over cross-region
  peer behavior (below).
- **Adding/configuring a peer causes zero primary downtime** — the
  primary keeps serving read-write traffic throughout, even while a
  cross-region peer's backup/redo copy is being transferred remotely.

**Cross-region peer backup copy:**
- **NOT enabled by default** — unlike the local peer, must be explicitly
  added.
- Requires **subscribing to the paired region** first — same
  prerequisite already documented for Data Guard cross-region standby.
- Backups are **automatically copied** to the paired region once
  configured, for use instantiating the peer during switchover/failover.
- **Switchover is always initiated from the cross-region peer's OWN
  details page** (opens as a separate Console tab) — the opposite
  pattern from the local peer, and matches Data Guard's cross-region
  behavior.
- **Failover is manual only**: attempt switchover first from that page;
  if it doesn't succeed, the Console then surfaces a separate
  **Failover** link.
- **Connection string AND database tools URL DO change** after a
  cross-region switchover/failover — a real, direct contrast with the
  local peer's zero-reconfiguration behavior. **Requires downloading a
  new wallet** from the cross-region peer's details page once it
  assumes the primary role.
- **Can be converted to a snapshot standby and opened in "redirect
  mode"** for evaluating application changes — usable for **up to 2
  days**, then reverted — a shorter window than Data Guard's 48-hour
  (Serverless) / 7-day (Dedicated) snapshot standby limits; don't
  conflate the three.

**RTO / RPO for backup-based DR — concrete numbers, applies to both
local and cross-region peer during manual failover:**
- **RTO = 1 hour, PLUS 1 additional hour for every 5 TB** of database
  size — a real, size-scaling RTO formula, unlike Data Guard's flat
  RTO numbers.
- **RPO = 1 minute** — same order of magnitude as Data Guard's
  manual-failover RPO figures, despite the much larger RTO gap.

**Demo: Autonomous Data Guard in ADB-Serverless — live confirmations:**
- **Every Autonomous Database starts with the default local backup-based

- **The Data Guard upgrade form is where the data-loss-limit (fast-start

- **Console field label confirms the terminology split**: after
  upgrading, the Disaster Recovery panel's Peer Role changes from

  one overall.

## Database Actions — the preconfigured tool suite

**What it is**: a group of **self-service, web-based tools**, built on
**Oracle REST Data Services (ORDS)**, preconfigured into every
Autonomous Database deployment — no client install or manual
configuration needed. Reached from the Autonomous Database details page.
- **Tool categories span multiple user roles**: development tools,
  database-specific tools, and administration/monitoring tools — serving
  developers, data analysts, data architects, and DBAs from one page.
- **Named tools, each with a distinct purpose**:
  - **SQL Developer Web** — run queries, develop packages/procedures.
  - **Data Pump / Data Load** — data loading activities.
  - **Catalog** — harvests object metadata, finds object lineage.
  - **Data Modeler** — create application data models, generate DDL,
    export diagrams.
  - **Data Insights** — generates insights on a table: pattern
    detection, anomaly identification.
  - **Data Analysis** — build analytical views over data.
  - Also present: monitoring tools, user management, JSON collection
    management, **REST** (build RESTful services), and **APEX** for
    rapid application development.
- **Access is granted at the schema level** — a schema must be
  explicitly enabled via **`ords_admin.enable_schema`**. The **admin
  user has access to all tools** by default, without this step.
- **Connections are stateless — a real, easy-to-miss architectural
  detail**: each HTTP request maps to a new database session, which
  **terminates immediately after the SQL statement or script finishes
  executing.** Session attributes do **not** persist across requests as
  a result.
  - **Concrete consequence**: a successful DML triggers an **implicit
    commit** (no manual COMMIT needed, and none possible to defer,
    since the session is gone right after).
  - **Workaround for session-scoped attributes**: use a **PL/SQL block**
    to send all needed session attributes to the database within that
    single stateless session/request.
- **The Monitoring page is Dedicated-only, and admin-only**: available
  **only for Autonomous Database on Dedicated infrastructure**, and
  **only when logged in as the admin user** — not available at all on
  Serverless, and not available to non-admin users on Dedicated.
  - Sub-pages include: **Monitoring Overview** (storage, users,
    sessions, waits), **Performance Hub** (ASH analytics, SQL
    monitoring — cross-references the Performance Hub tiers already
    documented for Base Database Service), **Alerts** (alert log
    messages), **Sessions** (currently open sessions), **Storage** (used
    storage, drill-down capable), and **Parameters** (initialization
    parameters).

## Oracle Database Autonomous Recovery Service (ARS) — centralized backup, not Autonomous-Database-specific

**Important scope note**: despite the "Autonomous" name, this service is
**NOT limited to Autonomous Database** — it's a centralized backup
solution for **multiple OCI Oracle database services**, and Autonomous
Database is just one of several supported targets (see supported
services list below). Don't confuse it with the Autonomous Data
Guard/backup-based DR features documented above, which are Autonomous
Database-specific.

**What it is**: a **fully-managed, centralized backup management
service**, based on the same technology as the on-premises **Zero Data
Loss Recovery Appliance (ZDLRA)**. Removes the need to plan a recovery
strategy or configure backups manually.
- **Forever-incremental backup strategy** — faster backups, reduced
  CPU/memory/IO overhead during the backup window (vs. traditional
  periodic full+incremental strategies).
- **Backups are fully encrypted and immutable**, and **each backup piece
  is validated for data-block correctness/anomalies** — ensuring
  point-in-time recoverability and real protection against ransomware.
  **Validation runs offloaded to the recovery service itself, with zero
  overhead on the database server.** If an anomaly is found, a fresh
  copy of the affected data blocks is created automatically.
- **Centralized dashboard**: backup health, recoverable point-in-time
  range, space utilization, retention policy status — all in one place.
- **Enhanced tier: Zero Data Loss Autonomous Recovery Service (ZRCV)** —
  an **extra-cost option** providing **real-time protection**: protected
  databases continuously ship redo logs to the service, enabling
  **recovery to within sub-second RPO** — a genuine, near-zero-data-loss
  guarantee against unplanned outages or ransomware, distinct from the
  base service's point-in-time-only recovery.
- ⚠ Trap: block-volume replication ≠ near-zero data loss — see [[OCI Architect Professional Tips]] §4.
- **Recommended as the backup destination** for all OCI Oracle Database
  automatic backups.

**Supported database services and environments:**
- **OCI-native**: Autonomous Database on Dedicated infrastructure,
  Exadata Database Service on Dedicated infrastructure, Exadata Database
  Service on Exascale infrastructure (formerly "Exadata Service"), and
  **Base Database Service** — a real, concrete confirmation that ARS
  reaches Base Database Service, not just Autonomous/Exadata.
- **Multicloud**: Oracle Database@Azure, Oracle Database@Google Cloud.
- **Storage location differs by environment**: OCI-native databases
  always use **OCI as the default/only storage location**. Multicloud
  databases get a **choice** — store in OCI, or store in the **same
  cloud environment** where the database itself resides.
- **ARS itself runs in an Oracle-managed service tenancy**, which can
  live in OCI or in the multicloud environment (Azure, Google Cloud,
  etc.) depending on deployment.
- **Monitored via OCI Monitoring Service** for alarms on protection
  status/storage utilization events, even for multicloud-hosted
  databases.

**Supported database versions — concrete, exam-worthy numbers:**
- **19c**: ARS supports **19.16+**; **Zero Data Loss (ZRCV) requires
  19.18+** — a stricter floor than the base service.
- **21c**: ARS supports **21.7+**; ZRCV requires **21.8+**.
- **23ai**: ARS supports **23.4+** (no separate ZRCV floor called out in
  this lesson).

**Network prerequisites for configuration — concrete, memorizable:**
- Requires a **dedicated private subnet in the database's VCN**,
  **IPv4-only**, sized **/24**, in the customer's own tenancy — reserved
  specifically for ARS backup/recovery traffic.
- **Ingress security rules required on the database subnet for ports
  8500 and 2484** — to let the recovery service reach the Oracle
  Database in the VCN. Both specific port numbers are worth having
  verbatim.
- That private subnet must then be **registered as a "recovery service
  subnet"** within Autonomous Recovery Service itself — a distinct
  registration step beyond just creating the subnet.
- Enabling auto-backup this way provides **high availability of the
  backup within a region**, restorable to any AD/region/zone (multicloud
  context) as needed.

**Backup mechanics once configured:**
- Setting ARS as backup destination for Oracle-managed automatic backups
  creates an associated **"protected database"** resource representing
  that database inside ARS.
- **First backup is a level 0 (full)**; all subsequent backups are
  **RMAN level 1 incrementals** — consistent "forever incremental"
  terminology with the strategy described above.
- Every backup reaching ARS is **automatically validated for Oracle
  block correctness** — concrete ransomware/malware protection built
  into the ingestion pipeline itself, not a separate scheduled job.
- **Backups are space-optimized and compressed** — genuinely less
  storage than a traditional weekly-full on-prem strategy.
- **Unencrypted backups are rejected outright** — encryption is
  mandatory, not optional. **Encryption keys are stored/managed within
  the source database itself, NOT by the recovery service** — a real,
  specific separation-of-duties detail.

**Long-term retention backups via ARS:**
- On-demand, retainable **up to 10 years** — independent of the regular
  automatic-backup chain, stored in **Object Storage, Infrequent...
  actually Frequent Access tier** (confirmed: **frequent access tier**,
  not archive).
- **Can only be used to create a NEW database** — cannot restore onto an
  existing database, same restriction pattern already documented for
  Autonomous Database's own long-term backups.
- Must restore **within the backup's retention period.**

**Protection policies — retention rules, concrete numbers to memorize:**
- Defined via the Console; control retention, protection, and storage
  location rules. Can be applied **per individual protected database**,
  or as **one shared policy across all protected databases in a VCN.**
- **Regular (non-long-term) backup retention range: 14 days minimum, 95
  days maximum.**
- **Four predefined policy tiers, exact day counts**:
  - **Platinum = 95 days**
  - **Gold = 65 days**
  - **Silver = 35 days**
  - **Bronze = 14 days**
- **Custom/user-defined policies** are also allowed, within that same
  **14–95 day** range.
- **Long-term backups**: same **90 days–10 years** range already seen
  for Autonomous Database's own long-term backups.

**Retention Lock — a real, hard governance feature:**
- Locks a protection policy's retention period against modification or
  deletion — protects against both accidental changes and malicious
  attacks (e.g., an attacker trying to shorten retention before deleting
  backups).
- **Does not take effect immediately** — you set a future effective
  date, and ARS enforces a **minimum 14-day delay** before the lock
  actually engages. Any changes to retention (increase, decrease, or
  disabling the lock) must happen **before** that effective date.
- **Once locked**: you can only **increase** retention (up to the 95-day
  ceiling), **never decrease** it; you **cannot switch to a different
  protection policy**; and you **cannot disable the lock** — all
  enforced until the locked retention period naturally expires.
- **Lock applies at the policy level** — every protected database
  attached to that policy is bound by the same restriction.

**What happens to backups when a protected database is terminated:**
- Two retention choices at termination: keep backups per the **policy's
  normal retention period**, or retain them for just **72 hours** post-
  termination before deletion — **this same 72-hour rule also applies to
  long-term retention backups**, a real, easy-to-miss detail (long-term
  backups don't survive termination indefinitely even though their own
  retention window might be years).
- Whichever option is chosen, deletion is scheduled accordingly and the
  protected database resource enters a **"Delete Scheduled"** state.
- **Disabling automatic backup** (without terminating the database)
  triggers the **same 72-hour delayed deletion** of the protected
  database resource and its backups, also landing in "Delete Scheduled."

## Globally Distributed Autonomous Database — sharding architecture

**What it is**: a **distributed-database service built on Autonomous
Database on Dedicated infrastructure** — automated sharding at cloud
scale. Applications see **one logical database**; under the hood, data
lives across multiple independent physical databases called **shards**.
- **Two primary use cases**: (1) **scalability + survivability** — scale
  compute/storage/performance horizontally, with data replicated across
  ADs/regions for fault tolerance; (2) **data sovereignty** — place
  customer data in specific countries/regions via **customer-defined
  data placement policies** to satisfy residency regulations.
- **Select AI integration**: lets you query distributed data using
  **natural language**, without needing to know where the data actually
  lives or how it's structured across shards.

**Architecture components — real, named terms worth having verbatim:**
- **Shard** — an independent physical database holding a subset of the
  logical database's data. **Shared-nothing architecture**: each shard
  is fully independent, individually scalable, and individually
  replicated for HA.
- **Shard Catalog** — automates shard deployment; acts as the
  **centralized administrative server**. Stores shard configuration and
  the **"gold copy"** of the database schema.
- **Query Coordinator** — manages **multi-shard queries**, distributing
  query workload for requests that span more than one shard.
- **Sharding Director** — maintains the **topology map**; a network
  listener that **routes connections to the correct shard based on the
  sharding key.**
- **Shard Space** — a shard (or set of shards) storing a specific
  range/list of key values under a **user-managed** data-distribution
  configuration; includes its own replica.
- **Global Service** — the access layer applications use to connect —
  again, with zero visibility into the underlying shard topology.

**Data distribution methods — two real, distinct strategies:**
1. **Automated (system-managed) distribution** — uses **partition by
   consistent hash**; data spreads evenly and randomly across shards
   with no manual placement control.
2. **User-managed distribution** — customer explicitly controls
   placement, for performance tuning, regulatory/data-sovereignty
   requirements, or business rules dictating a specific shard.

**Runtime behavior:**
- **Active-active symmetric configuration** — every shard can process
  application requests; requests are transparently routed to whichever
  shard actually holds the relevant data.
- **Cross-shard requests are automatically split** into per-shard
  sub-requests and **committed atomically** — a real, ACID-preserving
  guarantee across shard boundaries.
- **Queries parallelize both within a shard and across shards** —
  enabling massively parallel analytics over the whole distributed
  dataset.

**Deployment topology options:**
- **Independent standalone servers** — simplest, lowest-cost option, one
  shard per commodity server.
- **Fault-tolerant, scalable clusters** — using **Exadata scale-out
  clusters** for faster in-region data access; server/database
  failure or maintenance inside the cluster does **not** require an
  application failover to a replica (the cluster absorbs it).
- **Mixed deployment locations**: on-premises, OCI, or multicloud — and
  the deployment option/location can be chosen **independently per shard
  or per country.**
- **Shard placement strategy driven by goal, a real decision matrix**:
  - **Maximize performance** → multiple shards within **one AD.**
  - **High availability** → shards spread **across ADs or regions.**
  - **Data sovereignty** → shards deployed **across specific OCI
    regions** matching where the data is legally required to reside.

**Replication — two distinct mechanisms, with different version
floors:**
1. **Shard-level (site-level) replication via Oracle Data Guard** —
   supported on Autonomous Database Dedicated **Exadata infrastructure,
   19c and 23ai.** Creates a **physical standby** of each individual
   shard (since each shard is itself a full Oracle database) —
   **automatically configured when the shard is created**; standby
   copies can be local or remote.
2. **Chunk-set-level replication via Raft Replication** — supported
   **beginning with 23ai only** (not available on 19c, unlike Data
   Guard replication). Splits each shard's data into **chunks**,
   automatically distributing/rebalancing them across shards as scaling
   or availability events occur.
   - **Consensus-based**, high-performance, low-overhead.
   - **Fast failover with zero data loss.**
   - **Replication factor** = number of participants in a raft group —
     automatically maintained even after a shard failure.
   - **Low management overhead** — no manual reconfiguration needed when
     shards are added or removed, and replication itself requires no
     active/ongoing management.

**Demo: Globally Distributed Autonomous Database — live console
confirmations:**
- **Deployment type is currently fixed** (read-only in the Console) —
  only one deployment flavor is offered today; the UI has room reserved
  for more in the future. **Database version choice is 19c or 23ai** at
  creation — this single field is what determines which replication
  strategies are even offered later in the wizard (see below).
- **Map view vs. List view**: the Console offers a genuine infrastructure
  map showing every eligible Exadata cluster the tenancy has access to
  (discovered via a live API call against Exadata) — confirmed to
  include **any N-series Exadata**, from small quarter-rack/2-node
  clusters up to full racks, and both bare Exadata and VM clusters.
- **Per-shard configuration is fully independent** — confirmed live:
  each shard gets its own cluster selection, its own **ECPU count**, its
  own **autoscaling toggle**, its own **storage sizing**, and its own
  **Data Guard enable/disable choice with an independently chosen target
  region/cluster** for that shard's standby. One shard can have Data
  Guard pointed at a different region while a sibling shard has Data
  Guard disabled entirely — real, granular, per-shard control, not a
  single global HA setting.
- **The Shard Catalog's configuration form reuses the first shard's
  settings as a starting default** — you can override any of them
  (including disabling Data Guard on the catalog independent of the
  shards) rather than configuring it from scratch.
- **Two-stage validation, confirmed explicitly**: a shallow **"Validate"**
  step before Create checks for port conflicts, capacity, and cluster
  availability; a **second, deeper check happens at actual Create
  time**, re-verifying live cluster state immediately before
  provisioning starts — because capacity/config can change between
  validation and creation (a real race condition the two-stage check
  exists to catch).
- **23ai unlocks a replication-strategy choice screen 19c does not
  offer**: choosing 23ai adds a step to pick between **Raft Replication**
  (new in 23ai) and **Data Guard** (available in 19c and still supported
  in 23ai) — confirming Raft Replication is NOT available at all for a
  19c-versioned Globally Distributed Autonomous Database, consistent
  with the "23ai-only" rule already documented above.
- **Raft Replication's replication factor is a concrete pickable value:
  3, 5, or 7** — not an arbitrary number; e.g., factor 3 means 3 copies
  of the data distributed across shards.
- **Raft Replication benefits stated directly in the Console UI copy**:
  fast failover with **zero data loss**, active-active symmetric
  configuration, and **fully transparent to applications** — explicitly
  called out as needing **no Oracle GoldenGate and no Oracle Data Guard
  configuration** to get this HA behavior.
- **Shards can be added or terminated after creation**, with the service
  **automatically redistributing data** on either operation — confirmed
  live for both an automated-distribution scale-down (removing
  under-utilized shards) and a user-managed-distribution scale-out
  (adding a new region, e.g., Tokyo, to an existing US/Europe/India
  data-sovereignty setup) using the same Add Shard workflow as initial
  creation.
- **Performance Hub for this service shows a combined distributed view**
  — catalog metrics plus per-shard metrics side by side, explicitly
  framed as how you'd spot a "hot" shard (heavier storage/compute
  utilization) needing rebalancing.
- **Standard lifecycle actions available**: Move Resource (change
  compartment), Update Display Name, Stop/Start, Manage Certificates,
  Add Tags, Terminate — the same action set as other OCI database
  services, plus Work Requests for tracking provisioning/config issues.

## Autonomous Database deployment options — four, not two

**Correction/extension**: the Serverless-vs-Dedicated split documented
above is only *half* the real deployment taxonomy — there are **four**
deployment options total, and the full lecture transcript names the
decision factors driving the choice explicitly: internet access vs.
enterprise-datacenter-only access, how much operational/cost control is
needed, data-sovereignty/residency requirements (data allowed to leave the
customer's own datacenter or not), whether only the DB service is needed
vs. a broader integrated cloud-native platform, and cost.

1. **Serverless** (public cloud) — already documented above: simplest/
   fastest, Oracle-managed Exadata infra (shared, not overprovisioned),
   Vault-integrated isolation. **Concrete minimum commitment: one hour of
   usage.** Patches apply automatically, in a **rolling fashion**, no
   downtime — but because it's shared infrastructure, **you cannot
   schedule/delay maintenance activities yourself** (only get advance
   notice). Data still resides in Oracle's datacenter and travels over the
   internet to/from the customer.
2. **Dedicated** (public cloud) — already documented above: exclusive
   Exadata infrastructure, hardware-enforced VCN isolation from other
   customers. Real, concrete advantage over Serverless: **you CAN set your
   own schedule for applying software updates** (the direct inverse of
   Serverless's constraint). Can host **both** ADW and ATP workloads in the
   *same* deployment. Requires subscribing to dedicated Exadata
   infrastructure in OCI first. Same manual/auto storage+compute scaling
   as Serverless.
3. **Exadata Cloud@Customer** — the **entire Exadata infrastructure runs
   inside the customer's own datacenter firewall**, not Oracle's. Solves
   data sovereignty/GDPR/data-residency requirements, network-latency
   concerns from being geographically far from the database, and legacy-
   app-migration technical constraints — cases where data legally or
   practically cannot leave the customer's own datacenter. Provisioned on
   **Exadata Cloud@Customer Gen2** infrastructure with elastic
   provisioning. Oracle performs the deployment and plugs it into the
   customer's network, configuring it to communicate back to the **Oracle
   Cloud control plane** (so it's still Oracle-managed, just physically
   on-premises). **Backup destination choice, specific to this
   deployment**: local NFS storage, OCI public cloud Object Storage, **or
   Zero Data Loss Recovery Appliance** — a named backup target not
   mentioned for any other deployment option in this note.
4. **Dedicated Region Cloud@Customer** — the most extreme option: **the
   entire OCI public cloud region itself, deployed inside the customer's
   own datacenter** — brings the complete OCI public service portfolio
   (Autonomous Database included) on-premises, not just the database
   service.

**Stated constant across all four**: "irrespective of the deployment type,
you get the same fully featured autonomous database" — same security,
scalability, availability, and performance guarantees regardless of which
of the four you choose; the decision is about *where* and under *whose
operational control*, not a functionality tradeoff.

## Autonomous Database Dedicated — five-layer architecture and real limits

Full lecture transcript captured. Dedicated infrastructure's whole value
proposition, stated directly: higher control/customization, governance,
cost management, and compliance — **without giving up any of Autonomous
Database's automation benefits**. Named customization capabilities:
per-department/per-criticality licensing model separation (e.g. Sales, HR,
Marketing, Finance each with their own), customizable **software update
schedule and upgrade policy** (push updates to a later date, validate
non-production first — the real, named advantage over Serverless's
forced/notification-only maintenance model), customizable HA/DR posture
per container database (e.g. cross-region Autonomous Data Guard where
SLA demands it), fractional OCPU allocation and resource-management-plan-
based throttling control for non-critical workloads, and clean **role
separation** between operators and database users (detailed below).

**Five-layer architecture stack, bottom to top — worth knowing by name and
what each layer actually controls:**
1. **Exadata Infrastructure (EXA)** — the physical hardware layer. Latest
   generation named directly: **X8M-2 and X9M-2**, available in quarter/
   half/full rack sizes. **Elastic**: starts with **2 database servers and
   3 storage servers**, expandable by adding more of either within the
   same rack.
2. **Autonomous Exadata VM Cluster (AVM)** — sits above Exadata Infra,
   the link between it and the container database layer. **4 symmetrical
   VMs across all compute nodes.** This is the layer where **networking,
   licensing, and certificate management** are controlled. **Inherits its
   maintenance schedule from Exadata Infrastructure** below it — not
   independently schedulable at this layer.
3. **Autonomous Container Database (ACD)** — a multitenant Oracle Database
   container; one or more ACDs can exist within a single AVM.
4. **Autonomous Database (ADB)** — the actual database, application data
   lives here, hosted inside an ACD. **A real, concrete node-placement
   rule**: **≤16 OCPUs → single node** of the AVM cluster; **>16 OCPUs →
   split across multiple nodes** automatically.
5. **Autonomous Backup** — Oracle auto-configures backup, runs it
   automatically, but the **customer controls when it runs** (schedule
   control, not full manual operation).

**Real, concrete resource limits — worth memorizing verbatim:**
- **Maximum 12 Autonomous Container Databases per AVM cluster.**
- **Maximum 200 Autonomous Databases per Container Database** — normally.
- **Maximum 25 Autonomous Databases per Container Database when that ACD
  is configured with Autonomous Data Guard** — a real, much lower ceiling
  specifically when Data Guard is in play, not the same 200 limit.

**Two named roles, a genuine operational separation — not just an IAM
policy detail:**
- **Fleet Administrator** — the IT/infrastructure role. Engages with the
  business on requirements/compliance/budget, sets governance policies
  (operational, SLA, compliance, resource isolation, cost model),
  **provisions and manages the Exadata Infrastructure, the AVM cluster,
  and the Autonomous Container Databases** — i.e., owns layers 1-3 of the
  five-layer stack above.
- **Database Administrator / Developer** (self-service user) — provisions,
  monitors, and manages the **Autonomous Database** itself (layer 4) —
  needs IAM privileges scoped to use the ACD and its networking, and to
  manage backups/databases within it. Explicitly includes developers who
  "may not have a Cloud account" but use the database via the DBA-
  provisioned access. **This role never touches Exadata Infra, AVM, or
  ACD provisioning** — a real, clean separation of concerns baked into the
  service's own role model, not just a suggested IAM pattern.

**Simple vs. sophisticated deployment patterns, both real and named**:
Simple = one AVM cluster, one ACD, all databases share one service level
and one maintenance schedule. Sophisticated = multiple ACDs, each isolated
by purpose (e.g. one ACD for all test workloads across teams — with
overprovisioning allowed there — separate ACDs per production application
team, each with its own update/backup schedule and SLA; the example given
has a production ACD specifically configured with Autonomous Data Guard
for maximum availability, while the test ACD isn't).

## Dedicated Provisioning demo — the real prerequisites and workflow, confirmed live

Hands-on demo confirming the five-layer architecture applies in this exact
create order: **Exadata Infrastructure → Autonomous Exadata VM Cluster →
Autonomous Container Database (ACD) → Autonomous Database (ADB)** — each
step consumes the one before it as a real Console dependency, not just a
conceptual layering.

**IAM/compartment prerequisites, stated as a real, named setup pattern**
(matches this vault's own established convention of two-compartment,
two-group separation — directly comparable to `lab-mymagnet-stack`'s own
dynamic-group patterns elsewhere in this repo): create **two
compartments** (e.g. `FleetCompartment` for Exadata Infra/AVM/ACD,
`ADBCompartment` for the actual autonomous databases) and **two IAM
groups** (`Fleet-Administrators`, `ADB-Administrators`) with privileges
scoped to their respective compartments/resource types — directly
operationalizing the Fleet Admin vs. DBA role split documented in the
conceptual lecture above. A VCN with **both a private subnet (for
Exadata) and a public subnet (for compute/database resources)** is also a
named prerequisite.

**Concrete provisioning details confirmed live, not just conceptual:**
- **Exadata Infrastructure**: choose a system model (demo used **X8M-2**,
  the flex model), starting **2 database servers + 3 storage servers**
  (matching the elastic-scaling numbers documented conceptually above),
  plus a maintenance schedule (custom month/week/day/hour, or "no
  preference" — defaults to **once per quarter** when unset).
- **Autonomous Exadata VM Cluster**: consumes the Exadata Infra just
  created, needs the VCN + **private** subnet, and a license type.
  Resulting cluster shows **total vs. available OCPUs and storage** — the
  real capacity pool subsequent ACDs/ADBs draw from.
- **Autonomous Container Database (ACD)**: **Autonomous Data Guard is an
  enable/disable choice made at the ACD level**, not the ADB level — "if
  you need to enable Autonomous Data Guard... provide the region... peer
  Exadata Infrastructure... peer AVM Cluster" at ACD creation. A real,
  stated operational rule: **"while provisioning a production container,
  you must enable Autonomous Data Guard"** — framed as a hard requirement
  for production, not just an option. **Backup retention is a fixed
  choice among four values specifically: 7, 15, 30, or 60 days** (not a
  free-form range like Serverless's 1-60 day ECPU-model flexibility) —
  chosen at the ACD level, inherited by ADBs within it. Encryption
  (Oracle-managed vs. customer-managed via Vault) is also chosen here,
  at the container level.
- **A real, non-obvious capacity concept: "Reclaimable OCPUs."** OCPUs
  freed by terminating an instance or scaling down **are not immediately
  returned to the available pool** — they only become reclaimable "after
  you restart your container database." A genuine capacity-planning trap:
  scaling down doesn't instantly free capacity for a *different* ADB in
  the same ACD to consume.
- **Creating the actual ADB**: **inherits Data Guard eligibility from its
  parent ACD** — the create-ADB screen only lets you select a container
  database that already has Data Guard enabled; if none exists, ADB-level
  Data Guard simply isn't offered. Minimum storage for a Dedicated ADB is
  **32 GB** (a different minimum than either Serverless model's storage
  floor documented above — worth noting Dedicated has its own distinct
  minimum). **Network access control is disabled by default** — you must
  explicitly build an access control list (CIDR blocks or individual IPs)
  to restrict ADB reachability on Dedicated infrastructure, a different
  default posture than Serverless's "Secure access from everywhere" being
  the out-of-the-box default there.

## VM DB Systems storage architecture — LVM vs. ASM

A real, named choice for how a VM DB System manages its underlying block
storage — not an implementation detail to skip past:

- **LVM (Logical Volume Manager)** vs. **ASM (Automatic Storage
  Management / Grid Infrastructure)** — the two supported storage
  management options.
- **ASM specifically uses DATA and RECO disk groups** — a named,
  standard Oracle ASM pattern (DATA for datafiles, RECO for recovery-
  related files like archived redo/backups), shown as `+DATA`/`+RECO` ASM
  Disk Groups sitting on top of Block Storage.
- **Block Storage provides triple mirroring** underneath either LVM or
  ASM — the storage-layer redundancy exists regardless of which volume
  manager is chosen on top of it.
- **ASM redundancy is set to `external`** — meaning ASM itself does *not*
  add its own additional mirroring/redundancy layer on top, since Block
  Storage's triple mirroring already provides it. (`external` is Oracle
  ASM's own standard terminology for "redundancy handled by the storage
  layer beneath ASM, not by ASM itself" — distinct from ASM's `normal`/
  `high` redundancy modes, which *would* add ASM-level mirroring on
  storage that doesn't already provide it.)
- **DB System clones are also supported** — ties into the "BaseDB
  Cloning" material later in this module; cloning works regardless of
  which storage management option (LVM/ASM) was chosen.

## Autonomous Database — two independent axes, not one choice

A real, easy-to-conflate structure: **deployment model** and **workload
type** are two separate, orthogonal decisions — Autonomous Database is
described as "fully managed database with two workload types," and
Serverless/Dedicated is a distinct axis layered on top, not a third
workload type alongside them.

**Deployment model (Serverless vs. Dedicated):**
- **Serverless** — "allows provision and management of *only* the
  Autonomous DB"; **Oracle handles Exadata infrastructure deployment and
  management** entirely — the customer never touches or sizes the
  underlying Exadata hardware.
- **Dedicated** — "allows exclusive use of the Exadata hardware" — the
  customer gets a dedicated Exadata infrastructure footprint (closer in
  spirit to Exadata Database Service's isolation model, but still running
  as Autonomous Database's automated management layer on top).

**Workload type — CORRECTED: four types, not two.** Independent of the
Serverless/Dedicated choice above. The full lecture transcript (captured
directly from MyLearn's Transcript panel) names **four** supported
workload types, not just the two shown on the earlier slide — ATP/ADW are
the two "traditional" database workload types, but two more exist,
oriented at developers specifically:
- **Autonomous Data Warehouse (ADW)** — analytical workloads: data
  warehouses, data marts, data lakes, machine learning use cases.
- **Autonomous Transaction Processing (ATP)** — optimized for transaction
  processing, but explicitly **supports mixed workloads** too (can also
  serve analytical queries against the same database, not OLTP-only).
- **Autonomous JSON Database (AJD)** — for JSON-centric application
  development. Natively stores JSON documents, NoSQL-style APIs for
  store/retrieve. **Built on ATP under the hood**, with a **20 GB limit**
  on non-JSON-collection data specifically — when that limit becomes a
  problem, **AJD can be promoted to full ATP** (a real, named upgrade
  path, not a dead end).
- **Oracle APEX (Application Express) Service** — for APEX developers to
  rapidly build/deploy low-code applications; browser-based dev
  environment for data loading, schema management, and app building.

## Autonomous Database — workload-specific storage and optimization internals

**Storage format is workload-driven, not a uniform default:**
- **ADW stores data in columnar format, compressed** — analytical queries
  typically touch few columns across many rows, so columnar storage
  fetches only the needed column data; Exadata flash cache accelerates
  this further via in-memory columnar processing.
- **ATP stores data in row format** — transactional queries typically
  touch few rows but need all/most columns of those rows, so row storage
  fits the access pattern better.

**Index/summary strategy differs too**: ADW leans on Exadata's automatic
**storage indexes** (disk + flash) to prune unnecessary scans for large
analytical queries; ATP relies on actual **indexes** — created manually or
via Autonomous Database's **automatic indexing** feature.

**Memory allocation purpose differs by workload**: in ADW, most memory
goes toward **join and aggregation performance** (the full warehouse
dataset is too large to fit in memory wholesale, so memory optimizes the
expensive operations instead); in ATP, most memory goes toward **caching
data to avoid disk I/O**, since transactional working sets are typically
much smaller and more selective.

**Statistics gathering timing differs**: ADW gathers optimizer statistics
automatically **as part of bulk load operations** (with histograms
auto-generated alongside); ATP updates statistics **during DML operations
themselves** — different triggers for the same underlying "keep the
optimizer's stats current" goal.

**Supported external data sources for direct load, named explicitly**:
**OCI Object Storage, AWS S3, Azure Blob, and GitHub repository** — a
one-time source configuration, then load via the available APIs. Worth
knowing this list includes competitor cloud storage (S3, Azure Blob)
directly, not just OCI's own Object Storage — relevant for a migration/
multicloud-data-ingestion scenario question. Auto-Configuration then
automatically builds the access structures for that loaded data (indexes
for ATP, data summaries for ADW, per the storage-format section above) —
the customer's job is limited to loading the data, not partitioning/
indexing/statistics/query tuning.

**Two additional, more precise optimizer statistics mechanisms — beyond
the bulk-load/DML summary above:**
- **High-frequency automatic optimizer statistics collection** —
  **enabled by default**, runs every **15 minutes**, lightweight (only
  gathers stats for objects with genuinely stale statistics), and is
  **mutually exclusive from, and doesn't affect**, the standard automatic
  optimizer stats job that runs in the fixed maintenance window. Solves a
  real problem the standard job doesn't: high-volume data changes between
  maintenance windows can leave statistics stale long before the next
  scheduled run. Run interval and max runtime are configurable via
  `DBMS_STATS.SET_GLOBAL_PREFS`. Also automatically triggered by direct-
  load operations specifically — named examples: `CREATE TABLE AS SELECT`,
  `INSERT` with `APPEND` hint, Data Pump direct-path load, and
  `DBMS_CLOUD` data-load APIs.
- **Real-time statistics for conventional DML** — **NOT enabled by
  default**; requires setting `OPTIMIZER_REAL_TIME_STATISTICS = TRUE`.
  Gathers only a lightweight subset (row counts, min/max column values),
  in real time, specifically for objects whose stats would otherwise go
  stale from ordinary (non-direct-load) DML — a gap the two automatic jobs
  above don't cover, since both of those focus on direct-load/bulk
  operations rather than routine transactional DML.

**Initialization parameters — restricted by design, not just
conventionally discouraged.** Autonomous Database preconfigures optimal
init parameter values per workload type (ADW vs. ATP), and — unlike
standard/Base Database Service provisioning — **restricts changing most
parameters outright**, specifically to protect performance and security
guarantees. A limited, named set of parameters remains changeable for
valid reasons — the example given: `DBTIMEZONE`, for an application that
genuinely requires a specific database time zone. **Best-practice
framing stated directly**: even for the parameters you're allowed to
change, don't do it routinely — evaluate carefully and test before ever
altering one in production. This is a real governance-model difference
from Base Database Service, where the customer has full init-parameter
control by default.

**Consumer groups — concurrency/resource control, a real five-tier
system**: Autonomous Database uses predefined **consumer groups**
(services applications connect through) to control concurrency and CPU/IO
priority. **ATP and AJD get all five tiers; ADW gets only three** (High,
Medium, Low — no TPURGENT or a fifth tier). Named tiers, highest priority
first:
1. **TPURGENT** — highest priority, for critical transaction processing;
   the only tier where you can **manually set query parallelism**.
2. **High** — maximum resources per query, but **least concurrency**
   (queries run in parallel, fewer of them at once).
3. **Medium** — fewer resources than High, but **higher concurrency**.
4. **Low** — **highest concurrency, least resources** — queries are
   **serialized**, not run in parallel, at this tier.
- **Concrete resource-share ratio, stated directly**: **High can use up to
  2x the resources of Medium, and 4x the resources of Low.**
- **Autoscale multiplies concurrency, not just compute**: with autoscale
  **enabled** (either OCPU- or ECPU-based compute model), the concurrency
  ceiling for the High and Medium tiers is **multiplied by 3** — the same
  "up to 3x" figure already documented for Autonomous Database's general
  auto-scale behavior, now shown to apply specifically to per-tier
  concurrency limits, not just raw compute.

**Idle/runaway session controls, stated as real defaults/configurable
limits**: idle sessions holding resources for **more than 5 minutes** are
automatically timed out, freeing resources for active sessions. Runaway
SQL statements can be configured (per consumer group) to auto-terminate
based on **runtime seconds and I/O thresholds** you set.

**What "fully managed" concretely automates, named explicitly**: Backup,
Patching, Upgrading, Tuning — the same four-item list worth citing verbatim
if a scenario asks what operational burden Autonomous Database actually
removes versus Base Database Service (which leaves all four under customer
control, per the Base Database Service section above).

## BaseDB Managed Features — prerequisites, scaling, cloning, Performance Hub

Full lecture transcript captured directly (MyLearn's Transcript panel), not
just slide screenshots — a few things worth having verbatim that don't show
up on the slides:

**Prerequisites, precisely:**
- Public key (OpenSSH format) + IAM policies — the public key authenticates
  future connections (private key held by you); IAM policies gate access to
  the cloud resources themselves. **Tenancy service limits** are named as a
  separate prerequisite check from IAM policy — having policy access to
  create a DB System doesn't guarantee the tenancy's quota allows it.
- **A VCN must already exist in the region** before launch — the DB system
  needs it for connectivity; gateways/route tables/security lists must
  already be configured. At least one subnet required (public or private),
  though **Oracle explicitly recommends a private subnet** for security.
- **Real, concrete gotcha for 2-node RAC specifically**: port 22 must be
  open **both ingress and egress**, and the security rule **must be
  stateful** (the default) — "otherwise the database system might fail to
  provision successfully." This is provisioning-time SSH connectivity
  between the RAC nodes themselves, not end-user access — a real, named
  failure mode if security rules are set stateless on a RAC subnet.
- Object Storage needs a path to reach it (Internet Gateway on a public
  subnet, or Service Gateway on a private subnet) — used for backups and
  for staging patches.

**Scaling — two genuinely different models depending on shape type:**
- **Flex shape**: OCPU scales in increments of 1, up to 64 OCPUs, at any
  time — no shape change required.
- **Fixed shape**: OCPU scaling requires an actual **shape change**, which
  **reboots the VM**. For 2-node RAC specifically, both VMs' shapes change
  and reboot **in a rolling manner** (one at a time, not simultaneously) —
  the mechanism that keeps RAC available through a fixed-shape resize.
- **Storage scaling is fully independent of OCPU scaling** — resizing one
  never requires resizing the other. Block storage can be increased **at
  any time with zero impact** to the running system. Data storage and
  Recovery (RECO) storage areas scale **independently of each other** too.
  One-directional constraint worth remembering: **neither data storage nor
  recovery storage can ever be decreased**, only grown.

**Backup/recovery, one detail the slides didn't state**: with Local
Storage backups specifically, "all backups are encrypted with the same
master key that is used for the TDE wallet" — ties Local Storage backups
directly to whatever TDE wallet key configuration was chosen at creation
(see the admin-password/TDE-wallet checkbox documented above). Also: **automatic
backups are deleted when the database is terminated** (reinforcing the
"backup unavailable if the DB System is gone" trap already documented for
Local Storage — but stated here as a general automatic-backup lifecycle
rule, not Local-Storage-specific) and failed automatic backup attempts are
**retried on the next scheduled backup window**, not immediately retried.

**Cloning — a real, easy-to-miss operational requirement**: a clone needs
its **own separate SSH keypair** (not reused from the source) and its
**own new admin password** — "because that clone is really a new
database," not a linked copy of the original's credentials.

**Cloning demo, confirming the mechanics concretely**: the Clone dialog
surfaces the source system's own config read-only for reference (node
count, software edition, storage management type) before asking for the
clone's own new identity — display name, SSH key (upload an existing
public key file or have the console generate a fresh pair), license
(bring-your-own or new), network (the demo reused the **same VCN** as the
source, just picked a subnet), a unique hostname, and a new admin password
for the `sys` user. Practical naming convention shown: appending a suffix
like "CLN" to distinguish the clone's resources from the source's in the
console listing — not an OCI requirement, just a sane habit demoed.
Provisioning a clone takes real time, same as an initial DB System launch
— not an instant operation.

**Connecting to a DB System — the real two-hop identity pattern, worth
knowing precisely (applies to any BaseDB system, not just clones)**:
1. **Note the clone's own private IP** — even though it shares the
   source's configuration, a clone gets its own distinct IP; the demo
   explicitly warns to capture it before disconnecting from the creation
   screen.
2. **SSH in as the OS user `opc`**, authenticating with the private key
   matching the public key supplied at creation — this lands you on the
   **operating system** prompt of the host the database runs on, not the
   database itself.
3. **Switch OS user to `oracle`** via `sudo` — "in order for me to perform
   administrative tasks... switch user to the user of Oracle." Still the
   same SSH session, just a different OS-level user context.
4. **Only then connect to the database itself**, e.g. via `sqlplus`,
   authenticating as a database user like `sysdba` with its own separate
   password (the database admin password set at creation, not the SSH
   key). **Three distinct identity layers in sequence**: SSH/OS-user
   identity (`opc`, key-based) → OS-user-switch (`oracle`, via `sudo`,
   no separate credential) → database-user identity (`sysdba`,
   password-based) — conflating any of these three is a real source of
   "why can't I connect" confusion for someone expecting a single login
   step the way a managed PaaS connection string might imply.

**Performance Hub and Database Management — a real two-tier structure**:
Performance Hub works for Base Database Service, Exadata Cloud Service,
**and external databases** (ties back to Note 6's "External Database"
category above) but requires **Database Management** to be explicitly
enabled first — it's not automatically available. Two named tiers once
enabled:
- **Basic Management** — Performance Hub shows only **ASH Analytics** and
  **SQL Monitoring** tabs.
- **Full Management** — shows **all** Performance Hub tabs.
A named IAM/Identity Cloud Service policy must grant users access to
Performance Hub itself, separate from Database Management being enabled.

## BaseDB Maintenance — upgrades, shape changes, and encryption key rotation

Full lecture transcript captured (MyLearn's Transcript panel). Three
distinct maintenance-time considerations, each with a real, testable
constraint:

**Database version upgrades — not rolling, real downtime, even on RAC.**
"Database upgrades are not rolling and does require downtime. This is true
for even a two-node RAC database environment" — a real, stated exception
to the general pattern of RAC/multi-node architectures absorbing

section above — **upgrade and shape-change maintenance are not the same
operation and don't share the same downtime profile**, worth keeping
distinct). One concrete named upgrade path (19c → 23ai): provision a new
23ai DB System, move the 19c pluggable database over via a **refreshable
clone**, then use the **Auto Upgrade tool**. **Real, easy-to-miss backup
gotcha**: automatic backups taken *before* the upgrade **cannot be used to
restore to a pre-upgrade point in time** after the upgrade completes — the
backup chain doesn't bridge the version boundary. A real 23ai feature
example given as motivation for checking release notes before upgrading:
**schema-level grants** (`GRANT SELECT ON SCHEMA hr TO bob` — grants
visibility into every table in that schema, including ones added *after*
the grant, automatically) — a genuinely new privilege-grant capability,
not previously possible at this granularity.

**Shape changes — storage is unaffected, but cross-processor-family
changes have real side effects.** Changing shape after provisioning
doesn't touch the storage already allocated to the DB System. But
**switching processor family** (e.g. Intel → AMD) changes memory and
network bandwidth characteristics along with it — "you might need to
reapply some of the customization" when crossing families, not a
transparent swap. This is the mechanism referenced (but not detailed) in
the "BaseDB Managed Features" section's flex-vs-fixed-shape scaling
discussion above — shape *migration* generally, described here in more
depth.

**Encryption key rotation and the Oracle-managed ↔ customer-managed
transition — a genuinely one-directional door.** Both Oracle-managed and
customer-managed encryption keys should be **rotated periodically**
regardless of which you use — named triggers: routine security-compliance
practice, a personnel change, or wanting to revoke a specific user's
database access. **The directional constraint, stated explicitly**: you
*can* switch **Oracle-managed → customer-managed** on an existing
database, but switching **customer-managed → Oracle-managed is NOT
supported** — once you've moved to customer-managed keys, there's no
documented path back. A real prerequisite for the switch: the database
(including all its pluggable/container databases) **must be open, with
all tablespaces in read/write mode** — cannot be performed against a
closed or read-only database.

## Base Database Service backup destinations — three named options, one real trap

MyLearn names three distinct backup storage destinations for a VM DB
System — worth knowing as three genuinely different failure-mode profiles,
not interchangeable "backup options":

1. **Recovery Service** — backups stored as **protected databases in
   Recovery Service** (a separate, dedicated OCI service for this — not
   plain storage). Stated benefit: high durability, performance, and
   availability.
2. **Object Storage** — backups stored directly in Object Storage. Same
   stated benefit (high durability/performance/availability) as Recovery
   Service.
3. **Local Storage** — backups stored **locally in the Fast Recovery Area
   of the DB System itself**. Stated benefit: optimized backup and fast
   point-in-time recovery — genuinely faster for routine operations. **The
   real trap, stated explicitly**: "If the DB System becomes unavailable,
   the backup is also unavailable." A Local Storage backup doesn't survive
   the failure of the very system it's protecting — it solves fast local
   point-in-time recovery, not disaster recovery, and is not a substitute
   for Recovery Service or Object Storage in a scenario requiring resilience
   to DB System failure/loss, not just fast rollback to an earlier point in
   time on a still-healthy system.

## Availability, read scale, and recovery

| Requirement | OCI starting pattern | Critical distinction |
| --- | --- | --- |
| Local database HA | RAC/service HA architecture where supported | HA is not automatically geographic DR. |
| Cross-region database DR | Data Guard / cross-region recovery pattern | Define protection mode, replication lag, switchover/failover, RPO, and RTO. **Physical Standby vs. Active Data Guard — a real licensing distinction, not just naming**: a physical standby is a Data Guard replica that can be opened read-only, but only if redo apply (replication) is **stopped** first. **Active Data Guard** is a licensed add-on option that specifically permits the standby to be open read-only **while redo apply keeps running** — simultaneous replication and read access, not one or the other. Verified directly against Oracle's docs. |
| Read scaling | Service-supported read replicas/read-only endpoints | Confirm feature and write/read routing for the selected database service. |
| Application-stack recovery | Full Stack DR where appropriate | Orchestrates a stack recovery plan; it is not a database backup feature. |
| Migration with minimal downtime | Database Migration / Zero Downtime Migration | Choose source/target compatibility, replication/cutover, validation, and fallback plan. |

## OCI Cache — the managed distributed caching service

**What it is**: a **fully-managed, distributed caching service** — build
and manage memory-based cache clusters to speed up application data
access. Positioned as a way to get "lightning fast" response times by
avoiding repeat trips to the database for the same data.

**Query mechanics — with vs. without cache:**
- **Without caching**: every query executes fully against the database
  (SQL parse, execution plan, data retrieval) every single time, even
  for a repeated identical query.
- **With caching**: before hitting the database, the app checks whether
  the requested data is already cached. **Cache miss** → query executes
  normally against the database, and the result is **stored in the cache
  location** before being returned. **Cache hit** → the cached copy is
  returned directly, with **no database access at all** for that
  request.

**Key features, named explicitly:**
- **Full manageability**: automated cluster creation, resizing, high
  availability, patching, and security updates — all handled by Oracle.
- **"Unparalleled simplicity"**: the only inputs you provide are **amount
  of memory** and **number of nodes** — no need to overprovision beyond
  actual workload requirements.
- **Scalability — concrete numbers worth memorizing**: **2 GB up to 500
  GB per node**, and **up to 5 nodes per cluster.** **Scaling is
  dynamic — no downtime required** to resize.
- **Automated HA**: deploying **2 or more nodes** causes OCI to
  automatically spread them across **multiple ADs or fault domains** —
  the same AD/fault-domain HA pattern already seen elsewhere in this
  note (backups, standby placement).
- **"Powerful Insight" monitoring**: out-of-the-box metrics for cluster
  health/performance — **CPU utilization, memory utilization,
  transmitted and received network bytes** — without any manual
  monitoring setup.

**Request flow**: application receives a user request → checks OCI
Cache → **cache hit**: served directly from cache memory, no database
call; **cache miss**: falls through to the backend database, and
(implicitly, per the cache-mechanics description above) the result gets
cached for next time.

**Concrete value drivers, named explicitly in the lesson:**
- **Increased application responsiveness** — lower latency for repeat
  data requests.
- **Reduced network load on the database** — fewer repetitive calls
  reaching the DB tier at all.
- **In-memory access beats disk access** — faster than even solid-state
  drive (SSD) retrieval, reducing disk operations and improving overall
  system performance.

**Named example industries/use cases** (illustrative, not technical
requirements): e-commerce (real-time customer-behavior/market-trend
data, e.g., connecting to Apache Spark for near-instant job launches),
gaming (faster response for cached game data → better player
experience), IoT (real-time sensor/industrial device data for business
efficiency), social media/marketing (fast access to trending
product/behavioral data for targeted campaigns).

## Implementing OCI Cache — prerequisites and cluster creation

**Prerequisites — real resources needed before creating a cluster:**
- An **OCI account with administrative privileges**, and confirmed
  access to **OCI Cache from the navigation menu.**
- Access to a **compartment** to organize the cache cluster and its
  related resources.
- An existing (or newly created) **VCN**, plus a **subnet within that
  VCN** for the cluster to live in.
- **IAM groups and policies** granting the right users access to both
  **network resources** (VCN/subnet) AND **OCI Cache resources** — a
  real, two-part permission requirement: a user managing a cluster needs
  permission on the *network* side as well as the *cache service* side,
  not just one or the other.
- **The OCI Cache service itself needs permission to manage the VCN and
  subnet** you designate for it — a service-level permission
  requirement, separate from the user's own IAM permissions.

**Cluster creation — two cluster types, concrete configuration
options:**
- **Non-shard cluster**: **1–5 nodes**, each independently configurable
  for node count and memory (GB) per node.
- **Shard cluster**: configurable **number of shards per cluster** and
  **number of nodes per shard** — a genuinely different scaling axis
  from the non-shard type.
- **Conceptual distinction worth having verbatim**: a **cluster** uses
  multiple servers to store data (replication-style); a **shard**
  horizontally **splits** data and distributes it across multiple
  servers (partition-style) — the same cluster-vs-shard vocabulary
  already seen for Globally Distributed Autonomous Database, but applied
  here to the cache service.
- **Total memory is a simple product of node count × per-node memory**
  — confirmed live via a 2-node example: 2 nodes × 8 GB each = 16 GB
  total.
- **Network configuration**: choose an existing VCN/subnet, create a new
  one, or supply an existing subnet's **OCID** directly.
- Cluster is reachable via **Console, CLI, or REST APIs** once created —
  not Console-only.

**Post-creation administrative operations, confirmed available on the
Cluster Details page:**
- Rename the cluster, change node count, change memory per node, move
  the cluster to a different compartment, or delete it.
- **Node count resizing range: 2 to 500 nodes per cluster** — note this
  is a much larger practical ceiling than the 5-nodes-per-cluster figure
  quoted in the OCI Cache overview lesson; that 5-node figure describes
  the *non-shard* cluster type specifically, while this 2–500 range
  applies to resizing an existing cluster more broadly. Don't conflate
  the two numbers.
- **Memory resizing works both up and down** — but **decreasing memory
  requires confirming actual current usage is already below the new
  target**, or **data loss can occur.** A real, concrete operational
  gotcha, not just a general warning.
- **Endpoints**: one connection endpoint is exposed per node — confirmed
  live with a 2-node cluster showing exactly 2 endpoints.
- **Live HA warning, confirmed verbatim**: creating a cluster with only
  1 or 2 nodes triggers an explicit Console warning — *"Using only one
  or even a two-cluster node may cause data loss."* **Oracle's own
  stated recommendation is 3 or more nodes** for genuine high
  availability — with only 2 nodes, losing a single node drops you to 1,
  which isn't meaningfully HA at all.

**Demo: Create OCI Cache Cluster — live confirmations and refined
numbers:**
- **IAM prerequisite chain, stated precisely**: an **identity domain**
  (container for security resources) holds **groups** (one or more
  users), and **policies attach to groups, never directly to
  individual users** — even a single-user group is still the correct
  pattern, not a direct user-to-policy assignment. This matches the
  IAM group/policy pattern already documented elsewhere in this repo's
  notes, now confirmed specifically for OCI Cache.
- **Non-shard cluster architecture, precisely defined**: **one primary
  node plus up to 4 replica nodes** — confirming the "1–5 nodes" figure
  from the previous lesson actually decomposes into 1 primary + up to 4
  replicas, not 5 undifferentiated peers. **Automatic backups are
  included** with the non-shard type.
- **Non-shard cluster defaults to 3 nodes** when created via the
  Console wizard — explicitly chosen by Oracle as a sensible HA-ready
  default (1 primary + 2 replicas), not the 1-node minimum.
- **Concrete sizing example confirmed live**: 3 nodes × 16 GB per node =
  **48 GB total memory**; bandwidth is **5 Gbps per node** (a specific,
  fixed-at-this-tier bandwidth figure not mentioned in the conceptual
  lesson).
- **Post-creation node-count resize range for an EXISTING cluster is 1
  to 5** — confirmed live on the Cluster Details page — which is
  **narrower** than the 2–500 range documented in the implementation
  lesson. Resolving the apparent conflict: **1–5 applies specifically to
  non-shard clusters**; the 2–500 range applies more broadly (shard
  clusters, or node count in a different context) — don't assume a
  single universal node-count ceiling across both cluster types.
  **Regardless of the technical ceiling, Oracle's live guidance
  reiterates: never drop below 3 nodes**, to preserve HA.
- **Memory resize range for an existing cluster, confirmed live: 2 to
  500 GB per node** — matches the implementation lesson's number
  exactly, and resizing is dynamic (just change the value and click
  Resize, no separate maintenance window).
- **Cluster Details page surfaces**: compartment, network/subnet used,
  the cluster's own **OCID**, total memory, OCI Cache engine version,
  total node count, and both **primary and replica endpoints**
  separately listed.
- **Each individual node exposes its own private endpoint** — confirmed
  live with 3 distinct per-node endpoints (labeled node indices like
  0-1, 1-1, 1-2) — the actual connection strings used to reach that
  specific node, copyable like a URL.
- **Built-in Metrics page, per-node granularity**: CPU utilization,
  memory utilization, used memory, and network transferred — each
  configurable by **time range** (last hour/6 hours/24 hours/week, or a
  custom start/end), **refresh interval** (e.g., every 1 or 5 minutes),
  and **aggregation function** (sum, min, max, count, etc.) — a fully
  self-service monitoring surface without needing a separate OCI
  Monitoring Service dashboard.

## SLA — Autonomous Database, DB System, NoSQL Database

Three separate OCI database SLAs worth keeping distinct — don't
conflate them, and don't assume a flat "OCI database SLA" exists.

| Database Type | Base SLA | Max SLA (with HA add-on) | What raises it |
| --- | --- | --- | --- |
| **Autonomous Database** | **99.95%** (single instance) | **99.995%** | Adding **Autonomous Data Guard** (local or cross-region standby) |
| **DB System** (VM/BM, RAC, Exadata) | **99.9%–99.95%** (single instance / compute-tied) | **99.995%** | 2-node **RAC** and/or **Data Guard**; Exadata Cloud Service/Cloud@Customer with Data Guard reaches the top tier |
| **NoSQL Database** | **99.9%** | **99.9%** (flat — no upgrade tier) | None — multi-AZ replication is handled internally by the service; SLA doesn't change with table config |

**Exam-relevant pattern**: the jump from **99.95% → 99.995%** consistently
correlates with adding **Data Guard** (Autonomous or standard) across the
DB-focused services — that's the testable pattern, not raw SLA
memorization. NoSQL Database is the outlier: it has no tiered HA
upgrade path the way Autonomous Database and DB System do.

**Distinguish SLA from SLO**: Autonomous Database also carries **SLO**
(Service Level Objective) commitments for performance and manageability
— e.g., automated patching/scaling/backup completion targets. SLOs are
best-effort targets, not the financially-backed availability guarantee
an SLA is — don't treat the two as interchangeable in a scenario
question.

## Caching and connection design

- Use a cache to reduce repeated read latency and database load; define cache-aside/write-through behavior, TTL, invalidation, warm-up, and failure behavior.
- Avoid using a cache as the source of truth unless its product/design explicitly provides persistence semantics required by the workload.
- Connection storms are solved with application connection management/pooling and database sizing, not merely with read replicas.
- Keep credentials in Secret Management and use private subnets/NSGs; do not expose database listener endpoints publicly.
