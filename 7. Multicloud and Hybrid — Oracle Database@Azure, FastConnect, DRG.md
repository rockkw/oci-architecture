### AWS-to-OCI multicloud/hybrid translation

| AWS memory anchor | OCI service or pattern | OCI-specific distinction |
| --- | --- | --- |
| Direct Connect | FastConnect | Private, dedicated connectivity to OCI, bypassing the public internet. Public and private virtual circuits are separate options — public reaches OCI public services, private reaches your VCN directly. |
| Transit Gateway | Dynamic Routing Gateway (DRG) | A virtual router attaching VCNs, FastConnect virtual circuits, Site-to-Site VPN, and remote peering connections — DRG is the hub multiple hybrid/multicloud paths converge on, not just a VPN endpoint. |
| No direct equivalent — AWS doesn't natively host another vendor's managed database service | **Oracle Database@Azure / @AWS / @GCP** | Oracle Exadata infrastructure, physically colocated in the *other* cloud's datacenter, managed by Oracle, but provisioned/billed/networked as a first-class resource inside that other cloud's console and VNet/VPC — not cross-cloud VPN-connected from a separate Oracle tenancy. |
| VMware Cloud on AWS | Oracle Cloud VMware Solution (OCVS) | Run VMware workloads on OCI without re-architecting; a lift-and-shift bridge, not a redesign requirement. |

## 1. Oracle Database@Azure — what makes this different from "just connect two clouds"

The diagram below is **not** a VPN/peering diagram between two separately-managed
clouds — that's the easy mental model to default to, and it's wrong for this
service specifically. Oracle Database@Azure places real Oracle Exadata
infrastructure inside Microsoft's own datacenter, exposed as a resource type you
provision directly from the **Azure** console/CLI, inside your **Azure**
subscription and VNet. You are not separately logging into an OCI tenancy to spin up
the database — the OCI-side pieces (Object Storage for backups, Vault for key
management) are reached over a **carrier-grade, OCI-managed private network** that
Oracle provisions and operates on your behalf, invisible as a "connection you set
up," unlike a customer-managed FastConnect/VPN circuit you'd build yourself for a
generic hybrid workload.

**Why this matters for the exam:** a scenario naming "Oracle Database@Azure" is
testing whether you know this is a *managed, embedded* service inside the other
cloud — not whether you can design a cross-cloud VPN. If a question's answer
choices include "set up Site-to-Site VPN between Azure and OCI" as the mechanism
for reaching Database@Azure, that's the distractor — the managed network is
part of the product, not something you architect yourself.

### Diagram: Oracle Database@Azure with cross-AZ Data Guard

![](7.%20Multicloud%20and%20Hybrid%20—%20Oracle%20Database@Azure,%20FastConnect,%20DRG/mylearn_database_at_azure_architecture.png)

**Reading the diagram, layer by layer:**

- **Azure-native app tier stays entirely in Azure:** DNS → Load Balancer → AKS
  (Azure Kubernetes Service), with a Container Registry — none of this touches OCI
  at all. The application layer is a normal Azure deployment; only the *database*
  layer is Oracle-managed.
- **Two Availability Zones, each with its own VNet Database, connected by VNet
  peering:** Primary VNet Database (AZ1) and Secondary VNet Database (AZ2), each
  containing a Client subnet with an Oracle Database@Azure instance. This is
  standard AZ-level HA placement — the same physical-isolation principle as OCI's
  own availability domains, expressed in Azure's terminology since the compute/app
  tier is Azure-native.
- **Data Guard runs between the primary and secondary database instances** —
  exactly OCI's own Data Guard mechanism (see [[6. Databases — OCI Database, NoSQL, Caching, DR]]
  for Data Guard fundamentals), just deployed across two Azure AZs instead of two
  OCI ADs. The "Standby" dashed line on the AKS side and the "Data Guard" labeled
  arrow on the database side show the same failover relationship at two different
  layers: application-level standby routing and database-level replication,
  working together, not redundant with each other.
- **OCI managed services are reached over the OCI managed network, not a
  customer-built connection:** both database instances send **Automatic backup**
  to **OCI Object Storage**, and both reach **OCI Vault** for key management,
  crossing from "Azure Region" into "OCI Region" through a box explicitly labeled
  "OCI managed network" — this is the detail that distinguishes Database@Azure from
  a generic hybrid design: the cross-cloud network path is part of what you're
  buying, not a FastConnect circuit you provision and maintain yourself.
- **No IAM/VCN-equivalent boundary is drawn on the OCI side** — notice there's no
  compartment, VCN, or subnet shown inside "OCI Region." That's consistent with the
  managed-network framing above: you're not managing OCI-side network topology for
  this traffic the way you would for a normal OCI workload.

## 2. FastConnect and DRG — the general-purpose hybrid connectivity this is *not*

Distinct from Database@Azure's embedded managed network above — this is the
customer-architected hybrid connectivity pattern for everything else (on-premises
data centers, other workloads, other multicloud designs that aren't a managed
database product).

- **FastConnect:** private, dedicated connectivity to OCI, bypassing the public
  internet. **Public virtual circuit** reaches OCI public services (Object Storage,
  etc.) without traversing the internet; **private virtual circuit** reaches your
  VCN directly, as if it were an extension of your on-prem network. Choose based on
  what you're actually connecting to — public services vs. private VCN resources —
  not just "more private is always better."
- **Partner vs. dedicated FastConnect:** dedicated is a direct physical cross-connect
  Oracle provisions for you (higher effort, no intermediary); partner FastConnect
  goes through a FastConnect partner's existing network (faster to provision, no
  direct physical link to manage yourself). The trade-off is provisioning
  speed/effort vs. directness of the physical path.
- **Site-to-Site VPN:** IPSec over the public internet — the lower-effort, lower-cost
  alternative to FastConnect when dedicated bandwidth/latency guarantees aren't a
  hard requirement. Often used as a FastConnect backup path, not just a standalone
  choice.
- **DRG (Dynamic Routing Gateway):** the virtual router hub that FastConnect virtual
  circuits, Site-to-Site VPN, and remote VCN peering all attach to. A DRG's
  **attachment route tables** and **route distributions** determine which attached
  networks can actually reach each other — attaching two things to the same DRG
  does not automatically mean they can route to each other; that's still a routing
  policy you configure, the same "attachment alone changes nothing, the route table
  does the work" principle already covered for gateways generally in
  [[9. Networking — OCI VCN, DRG, Gateways, Load Balancers]].
- **Local vs. remote peering:** Local Peering Gateway (LPG) connects two VCNs in the
  **same region**; Remote Peering Connection (RPC) connects VCNs across
  **different regions**, and both must attach through DRGs for the remote case. CIDR
  ranges cannot overlap for either.

## 3. Oracle Cloud VMware Solution (OCVS)

- Runs existing VMware-based workloads on OCI bare metal without redesigning them
  for OCI-native compute — a lift-and-shift bridge for organizations with a large
  existing VMware estate, not a permanent target architecture.
- Positions against AWS's VMware Cloud on AWS the same way — "run what you have,
  migrate later if it makes sense," not a redesign requirement up front.

- [ ] A scenario names "Oracle Database@Azure" and one answer choice is "configure
      Site-to-Site VPN between the Azure VNet and an OCI VCN to reach the database."
      Why is this the wrong mechanism, and what's actually providing that
      connectivity instead?
- [ ] Explain what Data Guard is doing at the database layer in the diagram above,
      versus what "Standby" is doing at the AKS/application layer. Are these the
      same failover mechanism at two layers, or two independent mechanisms?
- [ ] A design needs private, dedicated, guaranteed-bandwidth connectivity from an
      on-prem data center directly into a VCN — not to OCI's public services. Which
      FastConnect virtual circuit type, and why does the public-vs-private choice
      matter here?

      isn't flowing between them. What's the first thing to check, given that
      attachment alone doesn't grant routing?
- [ ] Contrast why Oracle Cloud VMware Solution is a bridge/migration tool rather
      than a long-term target architecture recommendation on the exam.
