### Translation from AWS management notes

| AWS memory anchor | OCI service/pattern | OCI distinction |
| --- | --- | --- |
| CloudFormation | Terraform with Resource Manager | Resource Manager is managed Terraform: stacks, plans, applies, state, source control, and drift detection. It is not CloudFormation syntax. |
| Systems Manager | OS Management Hub, Bastion, Compute management/automation, Fleet/operations tooling | No single SSM equivalent. Choose OS patching, remote access, command automation, and inventory capabilities separately. |
| Session Manager | Bastion | Bastion provides managed, temporary private SSH access; it is not a general command-execution platform. |
| Patch Manager | OS Management Hub | Manages updates at scale across supported OCI, third-party-cloud, and on-prem environments. |
| Parameter Store / Secrets Manager | Configuration management pattern / Secret Management + Vault | Secret material belongs in Secret Management; ordinary config has different lifecycle/access needs. |
| Trusted Advisor | Cloud Advisor, Cloud Guard, budgets, quotas, Cost Analysis | OCI governance is composed of distinct services; distinguish cost advice, security posture, and preventive controls. |

## Infrastructure as code

- **Resource Manager** runs Terraform stacks. Store configuration in approved source control, use plans for review, control state access, and run drift detection.
- Separate environments with compartments, Terraform variables/state boundaries, IAM policies, and promotion workflows.
- Terraform code can change infrastructure broadly; use least-privilege execution principals, approvals, and a tested rollback/recovery plan.
- Do not hand-convert CloudFormation templates into assumed OCI equivalence; redesign resource and IAM/network semantics.
- **Drift Detection, named precisely** (a MyLearn skill check question tested
  this exact term): a Resource Manager stack feature that compares the
  **real-world current state of provisioned infrastructure** against the
  **stack's last-executed Terraform configuration**, surfacing any manual/
  out-of-band changes made outside Terraform (e.g., someone edits a security
  rule directly in the Console). Distinct from Resource Manager's other
  state-related actions — **Apply** (runs the config forward) and **Import
  State** (brings existing, non-Terraform-managed resources under Terraform
  management) — drift detection specifically diagnoses divergence, it
  doesn't fix it on its own.

**Hands-on HCL syntax, provider config, stack job types, schema.yaml, and state file mechanics live in a dedicated note:** [[8.1 Terraform & OCI Resource Manager - Hands-On Reference]]. This note stays the governance/policy layer; that one is the lab reference for your first plan item (OKE, Functions, API Gateway, DevOps/OCIR, Terraform, Resource Manager).

**Two real distinctions a MyLearn skill check tested, both true fundamentals:**
- **Terraform is IaC, not IaaS.** Terraform is tooling that calls a
  provider's APIs to create/manage infrastructure — it hosts no
  infrastructure of its own. IaaS (e.g. OCI Compute) means the provider
  hosts infrastructure you consume; stopping Terraform never removes
  anything it created, since Terraform was never the thing running it.
- **Resource type vs. resource name — only the type is provider-specific.**
  Terraform's `resource "<TYPE>" "<NAME>" {}` syntax has two separate naming
  layers: the **type** (e.g. `oci_core_vcn`, `oci_containerengine_cluster`)
  is genuinely provider-namespaced — every resource in `terraform/` uses the
  `oci_` prefix. The **name** (e.g. `"lab_vcn"`) is an arbitrary local
  identifier you invent to reference the resource elsewhere in config, and
  has nothing to do with the provider at all.

## Operating system and access management

- **OS Management Hub** centrally manages updates for supported Oracle Linux and Microsoft Windows Server environments, including supported OCI, third-party-cloud, and on-premises systems.
- Registration/profile/group/lifecycle-environment design controls what software sources and updates apply to managed instances.
- Use **Bastion** for controlled temporary SSH access to private subnets. Combine it with IAM, NSGs, host controls, and audit logging.
- Automate routine operation safely with Events, Functions, DevOps, or suitable runbook tooling; isolate and audit principals that can change production.

## Governance and observability

- **Cloud Guard** detects risky configuration/activity and can invoke responders.
- **Security Zones** prevent policy-violating resource operations in protected compartments.
- **Cloud Advisor**, Cost Analysis, budgets, quotas, and tags support cost/governance decisions; none replaces IAM authorization.
- **Monitoring**, **Logging**, **Logging Analytics**, **Audit**, and **Service Connector Hub** support metrics, logs, analysis, evidence, and routing to other services/SIEMs.
- Use compartments and tag namespaces to define ownership, chargeback, lifecycle, and policy scope.

### Organization Management — centralized governance across multiple tenancies

The named OCI counterpart to **AWS Organizations** — this is the mechanism
for anything spanning more than one tenancy, which compartments alone
cannot do (compartments only subdivide *within* one tenancy; see
`AWS to OCI Exceptions.md`'s "OCI compartments have no AWS equivalent" gap
the other direction). Structure: one **Parent Tenancy** holds a single
**UCM (Universal Credits Model) Subscription**; peer **Child** tenancies
(shown as Tenancy-A/B/C/D) attach underneath it, each sharing the parent's
subscription rather than carrying its own.

**Parent's role**, stated as three capabilities:
1. Ability to **manage** [member] tenancies.
2. **Centrally report on cost usage** across all of them.
3. **Enforce governance across the organization** as a whole.

**Child's role**, by contrast:
1. **Isolated environment by default** — a child tenancy is not a
   sub-compartment of the parent; it remains its own fully separate IAM/
   identity root, same as any standalone tenancy (matching the
   Exceptions note's existing point that AWS Organizations member accounts
   stay "separately rooted, not nested containers" — OCI's child tenancies
   work the same way).
2. **Shares subscription of parent** — this is the one thing that actually
   changes: billing/UCM credits flow from the parent, not a separate
   subscription per child.
3. **Scalable up to 50 [child tenancies] by default** — a concrete,
   named default limit worth remembering verbatim if a scenario question
   tests organization sizing.

**Governance rules — exactly three enforceable dimensions, named
explicitly:** the parent tenancy sets enforcements on child tenancies
across **service quotas**, **allowed regions**, and **tagging** — "providing
increased control and assurance" per MyLearn's own framing. Not a generic
"policy" mechanism; these three are the closed set of what a parent can
constrain at the organization level. Distinct from ordinary IAM policy
(which governs *access*, not *quota/region/tag* constraints) — this is a
governance-shape restriction layered above IAM, closer in spirit to AWS
Organizations' Service Control Policies (SCPs) than to a regular IAM policy
statement, though OCI's three named dimensions (quotas/regions/tags) are
narrower and more specific than an SCP's general allow/deny-any-action
model.

**Four named benefits of sharing a subscription this way** (the "why
organize tenancies at all" answer): **Data Isolation** (child tenancies
stay fully separate identity/data roots, per the "isolated by default"
point above — sharing billing doesn't mean sharing data), **Ease of
Consolidated Billing**, **Separate Governance and Security** (each child
keeps its own IAM/policy boundary even while the parent enforces the three
governance-rule dimensions above), and **Central Cost Management**. Data
Isolation and Separate Governance and Security are two distinct benefits,
not one — isolation is about identity/data boundaries staying intact,
governance/security is specifically about IAM/policy staying separately
scoped per child even under shared billing and parent-level quota/region/
tag enforcement.

**Console demo confirms two distinct paths to add a child tenancy, not
one:** "Manage tenancies" lets the parent **invite or create new
tenancies** — invite and create are separate mechanisms, per the
Console's own wording. A **separate "Manage invitations" tool** ("Send or
respond to invitations") exists specifically for the invite path — implying
an already-existing, independent tenancy can be invited to *join* an
organization (accept/decline), versus a brand-new tenancy the parent
creates outright already inside it. The Console's five tools altogether:
Manage tenancies, Map subscriptions (attach one subscription to one or more
tenancies), Manage invitations, Create governance rules — plus an Overview/
Tenancies/Invitations/Subscription Mapping/Governance Rules left-nav
mirroring the same five areas.

**A governance rule for the "service quotas" dimension is a real quota
policy, using the same policy-statement syntax as ordinary OCI service
limits** — the Console demo's example: `set compute-core quota
standard2-core-count to 10 in tenancy`. Confirms governance rules aren't a
separate, bespoke policy language — quota-type rules reuse the standard OCI
quota policy grammar, just authored at the parent and attached across
tenancies rather than written per-tenancy locally.

**Attach scope is a real, explicit choice with a consequential difference**:
"Attach to specific tenancies" (named ones only, via a `Tenancies` picker)
vs. **"Attach to entire organization"** — the Console's own description of
the latter: "Attaches the rule to all current **and future** tenancies that
have joined organization governance." The org-wide option is forward-
looking, automatically covering child tenancies that don't exist yet at
rule-creation time — a real design lever (blanket policy that self-extends
to new members vs. a rule you must remember to reattach to each new child
individually).

**The "create" path in the Console, confirming the create-vs-invite
distinction above**: "Create new tenancy" is explicitly framed as creating
a **child** tenancy — "You are about to create a new child tenancy in your
organization. The created tenancy will consume from your subscription."
Real, named constraints on the form: **tenancy name** — lowercase letters
and numbers only, no spaces, max 25 characters, must start with a letter.
**Home region choice is permanent**: "Your home region cannot be changed
after your tenancy is provisioned" — the same one-time, irreversible
home-region commitment already documented for a standalone tenancy's own
IAM writes (see [[OCI propagation delays]]) applies identically to a child
tenancy created this way; getting it wrong here isn't a config edit, it's
a new tenancy. **Subscription remapping exists as an escape hatch for the
*billing* dimension, but not the home-region one**: "If you would like the
created tenancy to consume from another subscription, you can re-map the
created tenancy to another subscription on the Subscription Mapping page"
— which subscription a child draws from can be changed after creation, but
which region hosts its IAM resources cannot.

**Governance rule attachment at tenancy-creation time is optional and
fully reversible** — the Console's own wording on the "Governance rules"
step: "Select governance rules to attach to the tenancy, or skip and
attach later. **You can always attach or detach rules, or opt the tenancy
out of organization governance later.**" Three real things confirmed here,
not assumed: (1) attaching rules at creation is a convenience, not a
one-time-only commitment — unlike the home region choice a step earlier;
(2) rules can be filtered by **type** (the demo shows `Quota` and
`Allowed_regions` types, e.g. `Rule-01-Compute`, `GR-Quota-01`, `GR-01`)
and by **targeted tenancy**, implying rules are reusable, named objects you
select from rather than authored fresh per tenancy; (3) a tenancy can
**opt entirely out of organization governance** — governance isn't a
permanent, unremovable binding once a child joins the org.
