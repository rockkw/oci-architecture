## Infrastructure as code

- **Resource Manager** runs Terraform stacks. Store configuration in approved source control, use plans for review, control state access, and run drift detection.
- Separate environments with compartments, Terraform variables/state boundaries, IAM policies, and promotion workflows.
- Terraform code can change infrastructure broadly; use least-privilege execution principals, approvals, and a tested rollback/recovery plan.
- Do not hand-convert CloudFormation templates into assumed OCI equivalence; redesign resource and IAM/network semantics.
- **Drift Detection, named precisely** (a MyLearn skill check question tested
  this exact term): a Resource Manager stack feature that compares the
  **real-world current state of provisioned infrastructure** against the
  **stack's last-executed Terraform configuration**, surfacing any manual/
  out-of-band changes made outside Terraform (e.g., someone edits a security
  rule directly in the Console). Distinct from Resource Manager's other
  state-related actions — **Apply** (runs the config forward) and **Import
  State** (brings existing, non-Terraform-managed resources under Terraform
  management) — drift detection specifically diagnoses divergence, it
  doesn't fix it on its own.

**Hands-on HCL syntax, provider config, stack job types, schema.yaml, and state file mechanics live in a dedicated note:** [[8.1 Terraform & OCI Resource Manager - Hands-On Reference]]. This note stays the governance/policy layer; that one is the lab reference for your first plan item (OKE, Functions, API Gateway, DevOps/OCIR, Terraform, Resource Manager).

**Two real distinctions a MyLearn skill check tested, both true fundamentals:**
- **Terraform is IaC, not IaaS.** Terraform is tooling that calls a
  provider's APIs to create/manage infrastructure — it hosts no
  infrastructure of its own. IaaS (e.g. OCI Compute) means the provider
  hosts infrastructure you consume; stopping Terraform never removes
  anything it created, since Terraform was never the thing running it.
- **Resource type vs. resource name — only the type is provider-specific.**
  Terraform's `resource "<TYPE>" "<NAME>" {}` syntax has two separate naming
  layers: the **type** (e.g. `oci_core_vcn`, `oci_containerengine_cluster`)
  is genuinely provider-namespaced — every resource in `terraform/` uses the
  `oci_` prefix. The **name** (e.g. `"lab_vcn"`) is an arbitrary local
  identifier you invent to reference the resource elsewhere in config, and
  has nothing to do with the provider at all.

## Operating system and access management

- **OS Management Hub** centrally manages updates for supported Oracle Linux and Microsoft Windows Server environments, including supported OCI, third-party-cloud, and on-premises systems.
- Registration/profile/group/lifecycle-environment design controls what software sources and updates apply to managed instances.
- Use **Bastion** for controlled temporary SSH access to private subnets. Combine it with IAM, NSGs, host controls, and audit logging.
- Automate routine operation safely with Events, Functions, DevOps, or suitable runbook tooling; isolate and audit principals that can change production.

## Compartments

- A **compartment** is a logical grouping/isolation boundary for OCI
  resources — not a network, region, or physical location. Resources
  inside it are unaffected in terms of where they actually run; a
  compartment only controls **organization and access scope.**
- **Primary purposes**: organizing resources by team, project,
  environment, or cost center; and **scoping IAM policies** — policies
  are written against compartments, so which compartment a resource sits
  in determines who can see/manage it.
- **Compartments are hierarchical** — nestable under the tenancy (the
  root compartment) or under other compartments, letting policy
  inheritance and resource organization mirror an org structure.
- **"Move Resource" is a generic, OCI-wide action** — nearly every
  resource type (compute instances, VCNs, DB systems, OCI Cache
  clusters, Autonomous Databases, etc.) exposes the same Move Resource
  operation in its console/API. Confirmed directly against this
  behavior for **OCI Cache clusters** and **Globally Distributed
  Autonomous Database** instances.
- **It is a purely logical move** — the resource itself (its network
  config, subnet, nodes, endpoints, data) does not relocate. Only the
  resource's `compartment_id` metadata changes, which:
  - Reassigns which IAM policies/groups now govern access to it.
  - Changes how it's grouped in compartment-scoped resource listings and
    cost/chargeback reporting.

**Services confirmed (in this course's material) to expose Move
Resource:**
- **OCI Cache** (clusters) — confirmed live in the Cluster Details page
  demo, alongside rename/resize/delete actions.
- **Globally Distributed Autonomous Database** — confirmed live on the
  instance's action menu, alongside Update Display Name/Stop/Start/
  Terminate.

**Services confirmed directly against Oracle's own documentation
(cross-checked beyond this course):**
- **Compute** — a real, specific list, not just "instances": **Instance**,
  **Dedicated Virtual Machine Host**, **Instance Configuration**,
  **Instance Pool**, **Cluster Network**, **Compute Cluster**,
  **Capacity Reservation**, **Custom Image**, and **Autoscaling
  Configuration** all individually support Move Resource. **Attached
  resources (boot volumes, VNICs) do NOT move automatically** with the
  parent instance — a real, documented gap worth remembering.
- **Networking** — **VCNs**, **Subnets**, **Route Tables**, **Security
  Lists**, **Service Gateways**, and **NAT Gateways** all support Move
  Resource (added to the Networking service in a 2019 update — this
  wasn't day-one VCN functionality).
- **Autonomous Database — supported at THREE separate hierarchy
  levels, each independently movable**: the **Autonomous Database**
  instance itself (Serverless or Dedicated), the **Autonomous Container
  Database** (Dedicated only), and the underlying **Exadata
  Infrastructure** resource (Dedicated only) each have their own,
  separate Move Resource operation — moving one level does **not**
  automatically move the others. A real, structurally important
  distinction for Dedicated's multi-layer architecture (see Note 6's
  five-layer Dedicated architecture section).

**General rule beyond the confirmed list**: Move Resource is a
platform-wide IAM/governance primitive, not a per-service feature, so
most OCI resource types expose it — **but not all resources support
it**, and Oracle's own docs are explicit that this is decided
per-service: *"if the resource cannot be moved, the option is not
selectable on the Actions menu."* Always verify against the specific
service's own documentation rather than assuming.

**Documented caveats that apply broadly, not just to one service:**
- **Attached dependencies don't move uniformly** — some move
  automatically with the parent (sometimes **asynchronously**, so they
  may briefly not appear in the new compartment), others must be moved
  independently. This varies per resource type; Compute's boot
  volumes/VNICs are a confirmed example of dependencies that do **not**
  auto-move.
- **Security Zone restriction, confirmed for Compute instances
  specifically**: you cannot move an instance **out of** a security
  zone into a non-security-zone compartment, and you cannot move an
  instance **into** a security zone from a compartment outside that
  security zone — a bidirectional block, not just one direction.
- **Required IAM permissions are two-sided**: you need `manage <resource-family>`
  rights in **both** the source and destination compartments — missing
  either side blocks the move.

**Why you'd actually use it:**
- **Reorganizing after a mistake or an evolving org structure** — a
  resource created in the wrong compartment (e.g., everything dropped
  into the root/default compartment during early setup) can be
  relocated without recreating it.
- **Environment promotion** — moving a resource from a `dev`/`test`
  compartment into a `prod` compartment as part of a promotion
  workflow, without touching the resource's actual configuration.
- **Reorganizing for IAM scope** — narrowing or widening who can manage
  a resource by moving it under a compartment with different attached
  policies, instead of rewriting the policies themselves.
- **Chargeback/cost tracking realignment** — moving resources under a
  team- or project-specific compartment so cost reports and budgets
  reflect actual ownership.
- **Mergers/reorgs or compartment restructuring** — nesting child
  compartments under a new parent as an org structure changes, without
  disrupting running resources.

**A real, confirmed risk to know**: moving a compartment (or a resource
into a different compartment) does **not** automatically move or
recreate IAM policies that referenced the old compartment. A concrete,
documented failure mode: a Volume Group Backup policy scoped to the
original compartment silently stops working after the compartment is
relocated under a different parent, because the backup policy did not
move with it — the fix is to re-verify/re-scope IAM policies after any
compartment reorganization, not assume they follow automatically.

- Compartments and **tag namespaces** work together to define ownership,
  chargeback, lifecycle stage, and policy scope — see below.

## Governance and observability

- **Cloud Guard** detects risky configuration/activity and can invoke responders.
- **Security Zones** prevent policy-violating resource operations in protected compartments.
- **Cloud Advisor**, Cost Analysis, budgets, quotas, and tags support cost/governance decisions; none replaces IAM authorization.
- **Monitoring**, **Logging**, **Logging Analytics**, **Audit**, and **Service Connector Hub** support metrics, logs, analysis, evidence, and routing to other services/SIEMs.
- Use compartments and tag namespaces to define ownership, chargeback, lifecycle, and policy scope.

### Monitoring Service — deep dive

Part of Module 7 (Architect Observability Solutions) — a much deeper pass
than the one-line summary above.

- **Two monitoring modes, both real and distinct**: **Active monitoring**
  — actively probing a resource to assess health/performance (e.g., a
  health check against a web server). **Passive monitoring** — observing
  a data point as it naturally occurs (e.g., CPU utilization emitted by
  an instance). Both are core to the service, not one being the "real"
  monitoring and the other a lesser add-on.
- **Metrics** are what most OCI services emit natively — Monitoring
  **automatically collects and stores** metrics from services like
  Compute instances, Load Balancers, and databases, classified/grouped
  for quick access.
- **Alarms** trigger on a defined condition against metric data (e.g.,
  "CPU utilization > 80%") and **route through the Notifications
  service** to send alerts — alarms don't send notifications directly
  themselves; Notifications is the integration point.
- **Dashboards** are the "single pane of glass" — built from metric
  selections, giving a more user-friendly visualization layer on top of
  raw metric data.
- **Three access paths to monitoring metrics/alarm data**: OCI Console,
  CLI, and APIs — plus **third-party tools like Grafana** can also pull
  aggregated data, not just Oracle's own surfaces.
- **MQL (Monitoring Query Language)** — the service's own flexible
  query language for retrieving, analyzing, and aggregating metric
  data; supports complex queries to filter down to the specific issue
  being troubleshot.
- **OCI Connector Hub** — described explicitly as a **"cloud message
  bus platform"** used to move data between OCI services. Named use
  case: sending metric data to **Object Storage** for historical data
  analysis/retention. This is the mechanism behind "monitoring metrics
  can be transferred to other services" — Connector Hub is the actual
  transport, not a Monitoring-service-native feature.
- **Integrations with other observability pillars, two named examples**:
  (1) **APM** + Monitoring together — compare application performance
  against infrastructure metrics side by side; (2) **Logging + Logging
  Analytics** + Monitoring together — correlate metrics with logs for
  deeper root-cause insight. Monitoring isn't positioned as a
  standalone silo — it's designed to be cross-referenced with the other
  observability services.
- **Extensibility — custom metrics, two ingestion methods**: Monitoring
  isn't limited to OCI-native service metrics. (1) **API-based
  publishing** — post/publish custom metrics directly via API from
  custom applications or resources running anywhere, including outside
  OCI entirely. (2) **Agent-based collection** — deploy/enable an agent
  on the metric source, which then feeds metrics into the Monitoring
  service. A real, exam-relevant point: Monitoring can ingest metrics
  from non-OCI, even non-Oracle-cloud sources, not just OCI's own
  service telemetry.
- **End-to-end workflow, stated explicitly**: resources (OCI-native or
  external) emit **raw metric data points** → Monitoring **aggregates**
  them (aggregation methods covered in a later lesson) → aggregated
  data is accessible via Console/CLI/API/third-party tools → an
  **alarm** with a defined condition evaluates that data → on trigger,
  the alarm sends data to **Notifications** or **Streaming** — two
  named alarm destinations, not just Notifications alone.

### Monitoring Concepts — namespaces, dimensions, intervals/resolution, statistics, alarm states

The deeper terminology layer behind the overview above — this is where
the exam's precise vocabulary lives.

- **Metric**: a measurement of a resource's health, capacity, or
  performance. Metrics are grouped into **metric namespaces** — e.g.,
  the **OCI Compute Agent** namespace contains CPU/memory utilization
  metrics for Compute instances. Also named: **OCI VCN** metrics, **OCI
  Block Storage** metrics, **OCI Object Storage** metrics — each
  service's metrics live in their own namespace.
- **Three metric sources** (restated more precisely than the overview):
  **Service metrics** (native to OCI resources), **Custom metrics**
  (published via the **PostMetricData** API), **Agent-based metrics**
  (an agent enabled on the instance emits metrics into the service).
- **Dimension**: a name/value pair used to **filter** metric data — e.g.,
  filter by a specific resource ID or instance shape. Optional
  component of a metric query.
- **Metric stream**: one individual set of aggregated data for one
  resource. A query across 10 Compute instances produces **10 separate
  metric streams** by default (visually, 10 different-colored lines on
  a graph) — unless combined via **grouping** (see below).
- **Interval vs. Resolution — the two concepts most worth having
  precisely, since they're easy to conflate:**
  - **Interval** = the length of the time window used for each
    aggregation (e.g., "5-minute interval" = each aggregated data point
    summarizes 5 minutes of raw data).
  - **Resolution** = the period **between the start of each aggregation
    window** — i.e., how often a new window begins, which can overlap
    with the previous one. **Resolution is only settable via the API**,
    not through the basic Console UI.
  - **Worked example A** (interval = 5 min, no resolution specified →
    defaults to matching the interval, i.e., 5 min): over a 15-minute
    range, windows are **non-overlapping**: 0–5, 5–10, 10–15 — three
    total data points.
  - **Worked example B** (interval = 5 min, resolution = 1 min):
    windows are **overlapping**, advancing by resolution instead of by
    interval: 0–5, then 1–6, then 2–7, and so on — resolution controls
    how often a new (still 5-minute-wide) window starts, giving a much
    smoother/denser series of data points than example A's three
    discrete windows.
- **Statistic functions (Monitoring Query Language) — six named,
  each with a stated real use case:**
  1. **Sum** — total of all values added together (example given:
     total bytes ingested per day in Logging).
  2. **Mean** — average (sum ÷ count) (example: average CPU utilization
     per hour).
  3. **Count** — total number of observations in the period (example:
     counting Connector Hub errors per 6 hours, with an alarm condition
     of "> 1" — count is explicitly called out as commonly used for
     alarm conditions).
  4. **Max** — highest value observed in the period.
  5. **Min** — lowest value observed in the period.
  6. **Percentile** — the estimated value at a specified percentile
     (example: 90th percentile CPU utilization per minute, used to
     understand the *upper limits* of usage rather than the average).
- **Grouping — two distinct functions, don't conflate them:**
  - **Group By** — aggregate query results **by a dimension category**,
    e.g., group by availability domain or by region.
  - **Grouping** (the other function, separately named) — combine
    **multiple metric streams into a single stream** — e.g., collapsing
    10 individual instance streams into one combined view, useful for
    total utilization across a clustered environment.
- **A full metric query has these required/optional components,
  named explicitly:** metric (from a namespace) + statistic + interval
  are **required**; dimensions and grouping are **optional**; comparison
  operators are used specifically when defining **alarm** conditions.
  Basic mode = UI-driven query building; Advanced mode = writing raw
  MQL yourself.
- **Alarm states — four named, precise definitions:**
  1. **OK** — the alarm is not currently firing.
  2. **Firing** — the alarm's condition has been met; state has
     transitioned from OK to Firing.
  3. **Reset** — the alarm is no longer detecting the firing condition
     (or the underlying metric is no longer being emitted at all) —
     note this is distinct from just "back to OK," it specifically
     covers the metric-stopped-emitting case too.
  4. **Repeat** — the alarm is still in a Firing state and has been
     configured to **repeat notifications** to its destinations rather
     than notifying once and going silent.
- **Suppression**: a separate alarm configuration that **suspends
  notifications for a specified time range** — the named use case is
  pausing alerts during planned system maintenance, so a known,
  expected event doesn't generate alarm noise.
- **Alarm notification destinations, named explicitly**: Email, Oracle
  Functions, HTTPS, **PagerDuty**, **Slack**, and SMS text messages —
  all reached via the Notifications service's topic mechanism, not
  configured per-destination inside Monitoring itself.

### Notifications Service — pub/sub mechanics

- **Publish-subscribe pattern**: **Topics** = communication channels;
  **Subscriptions** = the endpoints a message is delivered to.
  Publishing one message to a topic sends it to **every** subscription
  on that topic — a real fan-out, not a single-recipient send.
- **Delivery retry on failure**: if a subscriber endpoint doesn't
  acknowledge receipt, the service **retries delivery** — the example
  given is an email subscription where the mail server is temporarily
  down; the service doesn't just drop the message on first failure.
- **Setup order, stated explicitly**: create a **topic** first, then
  attach one or more **subscriptions** to it — via Console, CLI, API,
  or SDK.
- **Six named subscription types** (same list as the alarm-destinations
  entry above, now confirmed as literally *the* Notifications
  subscription types, not just alarm-specific options): **Email**
  (sent each time alarm state changes), **OCI Functions** (runs a
  specified function), **HTTPS** (sends to a custom URL/webhook),
  **PagerDuty** (creates a PagerDuty incident on receipt), **Slack**
  (sends to a specified channel), **SMS** (text message).
- **Monitoring is just one integrated consumer of Notifications, not a
  bundled feature of it** — the alarm-to-topic-subscription
  relationship described in the Monitoring Concepts section above is
  Monitoring calling into the separate Notifications service, the same
  way any other OCI service could publish to a topic.

### Monitoring Alarms — thresholds, interval sizing, and tuning best practices

- **Alarm creation requires four components, restated precisely**:
  metric, statistic, interval, and a **trigger condition** (a
  comparison operator against a threshold value). Below threshold =
  **OK** state; threshold met = transitions to **Firing** — same state
  machine already documented, now tied explicitly to these four inputs.
- **Concrete, named threshold bands for resource-utilization alarms —
  worth having verbatim**:
  - **"At risk"**: utilization **> 80%** — the resource could
    eventually become non-functional; example given is a Compute
    instance breaching this being flagged as at risk of failure.
  - **"Non-optimal"**: utilization **60–80%** — above the optimal
    operating range, but not yet critical.
  - Also recommended: separate alarms for simple **resource up/down**
    state, independent of utilization thresholds.
- **Alarm interval sizing rule**: the interval must be **greater than
  or equal to** the metric's own emission frequency — e.g., a metric
  emitted every 5 minutes needs at least a 5-minute alarm interval.
  **Most OCI metrics emit every 1 minute**, meaning most metrics can
  support essentially any alarm interval you choose (the 1-minute
  floor rarely constrains the decision).
- **Suppression best practice, with an explicit warning**: suppress
  alarms during active mitigation/investigation to avoid alert noise —
  but **explicitly remember to remove the suppression once the issue
  is resolved**, called out as a real operational risk (a forgotten
  suppression silently blinds you to a future real recurrence).
- **A named, three-step alarm-tuning checklist for routine review**
  (because environments are dynamic and alarm configs drift out of
  date): (1) reassess each resource's **criticality** for any changes,
  (2) reassess **resource behavior** — review metric value trends/
  fluctuations for drift from when the alarm was first tuned, (3)
  reassess the **notification method** — confirm recipients are still
  correct and the repeat-notification frequency still makes sense.

**Demo: Monitoring Alarms — full live end-to-end confirmation (create
alarm → trigger it → receive notification):**
- **`oci_objectstorage` namespace requires at least one dimension to
  display any data at all** — confirmed live: selecting Object Storage
  metrics with no dimension set showed nothing until a
  `resourceDisplayName` (bucket name) dimension was added. A real,
  specific requirement not shared by every namespace.
- **Object Storage exposes primarily two metrics**: bucket **size (in
  bytes)** and **number of objects** uploaded — a narrower metric set
  than compute/block storage namespaces.
- **The Compute Agent metrics pipeline has a visible, checkable
  on-instance dependency**: metrics like CPU/memory utilization are
  collected via the **Oracle Cloud Agent**'s **Compute Instance
  Monitoring plugin**, viewable/manageable directly on the instance's
  own Console page under an "Oracle Cloud Agent" tab, showing plugin
  running/enabled status. A genuinely useful troubleshooting fact: if
  expected metrics aren't showing up, checking this plugin's status on
  the instance itself is a concrete diagnostic step, not just a
  Monitoring-service-side investigation.
- **Alarm creation fields, confirmed with real example values**: Name
  ("CPU Usage"), **Severity** (Critical — a selectable field, implying
  multiple severity levels exist), custom **Alarm body** text, optional
  Tags, then the metric description (namespace + metric name), interval
  (1 minute), statistic (Max), an optional dimension filter, and the
  **Trigger rule**: operator ("greater than") + threshold value (50%)
  + **Trigger delay** (1 minute — the condition must hold for this
  long before actually firing, not an instantaneous single-sample
  trigger).
- **Repeat notification, confirmed with a concrete example**: if
  enabled, you set a **notification frequency** (example given: 60
  minutes) — meaning if the alarm is still Firing after that interval,
  a repeat notification is sent; leaving it disabled means exactly one
  notification per firing transition, no follow-ups while still firing.
- **An alarm must be explicitly "enabled" as a final, separate save
  step** — not implicitly active just because it was configured; the
  demo explicitly calls out enabling the alarm before saving.
- **Full live trigger confirmed end-to-end**: baseline CPU at 2% → an
  alarm created with threshold "Max CPU > 50%" shows status **OK** →
  artificially loading CPU via a stress tool up to ~84–85% → the
  Service Metrics graph visibly crosses 80%+ → the alarm's own
  **Alarm Definitions** page shows status flip from OK to **Firing** →
  a real email arrives at the subscribed address, showing **Status:
  FIRING**, the alarm's severity, and the query definition itself (max
  CPU utilization, 1-minute interval, threshold > 50) embedded in the
  notification body — confirming the entire pipeline (metric → alarm
  evaluation → Notifications → subscriber delivery) end-to-end, not
  just each piece in isolation.

### Monitoring Access & Limits — CLI syntax, IAM policy patterns, and hard service limits

- **Four access paths, restated**: Console, APIs, SDKs, CLI — Metric
  Explorer specifically is the Console's own query-building UI (Basic
  vs. Advanced mode, same split already documented).
- **CLI command shape, confirmed with real examples**: `oci monitoring
  <resource-type> <action>`, e.g.:
  - `oci monitoring metric list --compartment-id <OCID>` — lists all
    metric definitions in a compartment.
  - `oci monitoring alarm list --compartment-id <OCID>` — lists all
    configured alarms in a compartment.
  - `oci monitoring metric-data post` — publishes custom metric data
    points into the service.
  - `oci monitoring alarm create` — creates an alarm via CLI.
  - `oci monitoring suppression remove --alarm-id <OCID>` — removes a
    suppression to un-suspend a suppressed alarm.
- **IAM policy patterns — five real, concrete example groups and their
  exact policy statements, worth having verbatim as templates**:
  1. **`alarm viewers`** group (e.g., a NOC/first-level ops team):
     `allow group alarm-viewers to read alarms in tenancy` +
     `allow group alarm-viewers to read metrics in tenancy` — read-only
     visibility into alarm status and metric data, tenancy-wide.
  2. **`alarm admins`** group: `allow group alarm-admins to manage
     alarms in tenancy` (the **manage** verb — full lifecycle:
     create/update/delete) + `allow group alarm-admins to read metrics
     in tenancy` (they still only need **read** on metrics themselves,
     since alarm management doesn't require metric-modification
     rights) — plus separate policy grants for managing Notifications
     topics, since alarm management and topic management are distinct
     permission scopes even for the same admin group.
  3. **`metric readers`** group, **compartment-scoped, not
     tenancy-wide**: `allow group metric-readers to read metrics in
     compartment ABC` — demonstrates policies can be scoped down from
     tenancy to a specific compartment when broader access isn't
     needed.
  4. **`metric viewers`** group, using the **inspect** verb
     specifically for confidential/sensitive metric access: `allow
     group metric-viewers to inspect metrics in compartment ABC` — the
     most restrictive verb, used explicitly here for a scenario where
     even read-level metric content is considered too sensitive for
     the group.
  5. **`metric developers`** group, using the **use** verb: `allow
     group metric-developers to use metrics in tenancy` — explicitly
     described as "the next level permission [up] from read," and
     grants the ability to both create metric definitions AND publish
     custom metrics — a concrete example of what "use" actually means
     for the metrics resource family specifically (verb-to-action
     mapping is resource-type-specific, per the IAM verb note in the
     cheat-sheet).
- **Condition-scoped policies — narrowing access further with a
  `where` clause, two real examples**:
  - `allow group metric-readers to read metrics in compartment ABC
    where target.metric-namespace = 'oci_computeagent'` — restricts a
    compartment-scoped read grant down to just one specific metric
    namespace.
  - `allow group metric-developers to use metrics in tenancy where
    target.metric-namespace = 'my_custom_namespace'` — restricts a
    tenancy-wide publish/use grant down to only a specific custom
    namespace, preventing that group from touching OCI-native service
    metrics at all.
- **Hard service limits — concrete numbers worth memorizing verbatim**:
  - **Metric definitions are retained for 90 days**, then deleted.
  - **Alarm history is retained for 90 days**, then deleted.
  - **No limit on the volume of metrics OCI services can emit** into
    Monitoring — services continuously post without a stated ceiling.
  - **Metric stream aggregation has a dynamic limit** — depends on the
    specific query and how many streams it's trying to aggregate
    together; exceeding it throws an exception reporting the actual
    allowed stream count. **The fix is to narrow/update the query**
    (e.g., add a dimension filter or tighten scope) to bring the
    aggregated stream count back under the limit — not a fixed,
    universally-quotable number, since it varies by query.

### MQL syntax and worked query examples

- **Standard MQL syntax order, stated explicitly**: `<metric>
  [interval] <statistic>` is the base pattern — metric first, then
  interval, then statistic.
- **Five worked example patterns, each demonstrating one added
  component:**
  1. **Base query**: `CpuUtilization[5m].max()` — max CPU utilization
     per 5-minute interval.
  2. **With a dimension filter**: add `{availabilityDomain =
     "<AD-name>"}` before the statistic — narrows the same query to
     one specific AD (example given: Melbourne AD 1).
  3. **With the grouping function**: `<metric>[interval]
     .grouping().<statistic>()` — combines multiple metric streams
     (e.g., one per instance) into a single aggregated stream, same
     mechanism as the Metrics Explorer "aggregate metric streams"
     checkbox already documented in the demo notes above.
  4. **With group by**: same shape, but grouping **by a dimension
     category** instead of collapsing to one stream — example given:
     group by instance **shape**, reporting max CPU utilization
     per shape-group rather than one number for everything or one
     number per instance.
  5. **Nested queries**: a query built from two parts — an inner query
     with a **comparison operator** (the alarm-condition part, e.g.
     `CpuUtilization[5m].max() > 80`) wrapped inside an outer
     **grouping** function that **counts** how many streams satisfy
     that inner condition. Concrete example: "number of hosts with CPU
     utilization greater than 80%" — the inner query flags qualifying
     streams, the outer grouping counts them. A second nested example
     uses a **success rate** metric to count "number of availability
     domains with a success rate lower than 0.99" — same nested
     pattern, different metric and threshold direction (below a
     floor, not above a ceiling).
- **Required vs. optional query components, restated one more time for
  precision**: metric, interval, and statistic are the base/required
  three-part pattern; dimensions, grouping, group by, and comparison
  operators are all optional additions layered onto that base,
  each independently combinable — a query can use several of these
  add-ons together (as the nested examples show: grouping AND a
  comparison operator in the same query).

### Logging Service Overview — three log types and the end-to-end workflow

- **What it is**: a highly scalable, fully managed, **single pane of
  glass for all logs** — both OCI-native service logs and logs from
  **external, non-OCI environments** (on-prem, other clouds). A
  centralized, secure log management service, not scoped to OCI-only
  telemetry.
- **Built on open standards**: uses the **Fluentd agent** for log
  ingestion, and is compliant with **CNCF CloudEvents** — the same
  Fluentd/Unified Monitoring Agent referenced for custom log ingestion
  below.
- **Four access paths**: Console, CLI, SDK, REST APIs — same pattern
  as Monitoring's own access options.
- **Rule-based actions on log events are handled by Connector Hub** —
  the same Connector Hub already documented as the transport mechanism
  for Monitoring metrics, now confirmed as the mechanism for Logging
  actions too — a shared, cross-pillar service, not Monitoring-specific.
- **Encryption at three distinct stages, stated explicitly**: **in
  flight** (during ingestion), **at rest via disk-level encryption**
  (once in the system), and again when **archived/stored** — three
  separate encryption touchpoints across the log's lifecycle, not one
  blanket "encrypted" claim.
- **Three log types, exactly — a closed set worth having precisely:**
  1. **Service logs** — emitted by native OCI services (VCN, Object
     Storage, Functions, etc.). Each service has **predefined logging
     categories**, enabled/disabled with a **single click** — no custom
     configuration needed to turn them on.
  2. **Custom logs** — from custom applications on OCI, or workloads
     running entirely outside OCI (on-prem, other clouds). **Two
     ingestion methods**: **API-based** publishing, or the **Unified
     Monitoring Agent** (the Fluentd-based agent referenced above).
  3. **Audit logs** — records of **every API call** made against OCI
     API endpoints (e.g., uploading an object to a bucket triggers a
     backend API call, which generates an audit log event).
     **Available out-of-box with zero configuration** — no setup
     needed to start seeing audit events in the Console's Audit
     section, consistent with audit logs being enabled by default and
     unable to be disabled (matches the "audit logs enabled by
     default, cannot disable" fact already established elsewhere).
- **End-to-end workflow, three stages, stated explicitly:**
  1. **Collect and manage** — configure OCI services/resources
     (service logs, audit logs, custom logs) to actually generate log
     data, including from on-prem sources if relevant.
  2. **Define search criteria** — build **logging queries** to filter
     down to specific log data or keywords.
  3. **Take action on filtered data** — via **Connector Hub**: named
     use cases include invoking an **Oracle Function** to remediate a
     detected error pattern, archiving legacy logs to an **Object
     Storage bucket**, or writing them into the **OCI Streaming**
     service.

### Logging Concepts — log groups, categories, Connector Hub, and the Unified Monitoring Agent

- **Log group**: the core organizational component — a **logical
  container for logs, stored within a compartment**. Think of it like
  a folder holding multiple logs. Enabling a log for any resource
  always requires choosing or creating a log group first.
- **Log group use cases, three named:**
  1. **Segregation by purpose** — e.g., putting all Object Storage
     **write** operations into one log group and all **read**
     operations into a separate log group, for faster targeted
     navigation.
  2. **Bulk transportability** — moving a log group to a different
     compartment moves **every log inside it** along with it, in one
     operation.
  3. **IAM-based access restriction without complex compartment
     hierarchies** — a real, concrete pattern worth having verbatim:
     a tenancy might have a **default log group** with broad access
     granted to all log administrators via IAM policy, but logs
     containing **PII** get split into a **separate log group**,
     scoped via its own IAM policy to only a restricted subset of
     administrators. This means sensitive-log access control is
     achieved through log group structure + policy, not by building
     out a more complex compartment tree just to isolate those logs.
- **Logs and log groups are described as "searchable, actionable, and
  transportable"** — three explicitly named properties: you can search
  across multiple logs within a group, define actions against search
  results, and move the whole group between compartments.
- **Service log categories — concrete named examples**: Load Balancer
  gives **Access log** and **Error log** categories; Object Storage
  gives **Read access events** and **Write access events** categories
  — reinforcing that "service logs" isn't one undifferentiated stream
  per service, but multiple named categories you enable independently.
- **Connector Hub use case tied specifically to Logging**: creating a
  search condition for a specific error-log pattern, then using
  Connector Hub to move matching log data into the **Monitoring**
  service — enabling an alarm to be built on top of a log pattern, not
  just a raw metric. Also named: sending log data into **databases**,
  or archiving into **Object Storage**.
- **Unified Monitoring Agent, restated with more precision**: also
  called the **Fluentd agent**; a **fully managed agent** when
  installed on an OCI instance, but can also be **manually installed
  on external/non-OCI systems** to feed custom logs into OCI Logging —
  the same agent-based custom-log ingestion method already documented,
  now with the "fully managed on OCI, manual elsewhere" distinction
  made explicit.
- **Agent Configuration**: a distinct section of the Logging service
  UI specifically for defining **how** the Unified Monitoring Agent
  should ingest custom logs — a separate configuration surface from
  the log groups/categories themselves.
- **Audit section**: confirmed again as where recorded **API calls**
  to OCI's public API endpoints are located — consistent with the
  "enabled by default, zero configuration" audit log behavior already
  documented.

### Service Logs — log structure and three named service examples

- **Every log line is normalized into a common JSON event format**,
  a real benefit of the open-standards foundation — makes correlation
  across different resources/services straightforward instead of each
  service having its own bespoke log shape.
- **Three sections in every log line, exactly — real field names
  confirmed directly from a console example (DevOps deployment log)**:
  1. **Unified envelope** — `specversion` (the CNCF CloudEvents spec
     version, e.g. "1.0"), `type` (log category, e.g.
     `com.oraclecloud.devops.deployment`), `source` (name of the
     resource that generated the message), `subject` (the specific
     resource OCID the event concerns, e.g. an instance OCID), `id`
     (unique message identifier), `time` (timestamp).
  2. **Oracle-specific metadata**, nested under an `"oracle": {...}`
     key — `logid` (OCID of the log containing this message),
     `loggroupid` (OCID of the log group), `tenantid` (OCID of the
     owning tenancy), `compartmentid` (compartment the log resided in
     at ingestion), `ingestedtime` (a separate timestamp from the
     envelope's `time` — when the platform actually ingested the
     event, not necessarily identical to when it occurred).
  3. **Data section**, nested under a `"data": {...}` key — fields
     vary by log category, but always include a **message** body and
     a **producer** (the OCI service that created the log message);
     the DevOps example specifically showed `deploymentId`,
     `deployPipelineId`, and `deployStageId` as category-specific
     fields.
- **Three named service log examples, each with concrete field
  detail — worth having the vocabulary precisely:**
  1. **Object Storage**: log resource = the bucket. Two categories:
     **Write access events** (bucket changes — e.g., file uploads) and
     **Read access events** (bucket reads). The key filterable field
     is **`data.requestAction`** — write events show **PUT, POST, or
     DELETE**; read events show **GET, LIST, or HEAD**. Other
     searchable fields: bucket name, client IP address, message body,
     status code (e.g., 200 = successful upload).
  2. **Load Balancer**: two categories. **Access logs** — request
     receipt timestamp, client/intermediate-proxy addresses, and
     processing time at both the LB and the backend. **Error logs** —
     detailed troubleshooting info; the worked example is a **health
     checker** event showing backend status transitioning **healthy →
     unhealthy**, backend IP/port, failure count, and a "connection
     timed out" message.
  3. **VCN Flow Log**: log resource = the **subnet** (not the VNIC or
     instance directly — enabling it on a subnet covers **existing
     AND future VNICs** attached to that subnet automatically). Used
     for **security monitoring and network troubleshooting** — records
     **accept and reject** traffic decisions, tied directly to
     whatever **Security Lists / NSGs** actually allowed or blocked
     that traffic. Key searchable field: **`data.Action`** — search
     for the literal string **"REJECT"** to find all blocked traffic
     matching that criterion, a real, concrete troubleshooting pattern
     for diagnosing connectivity problems.

**Demo: Service Logs Logging — full live workflow enabling VCN flow
logs, with concrete field values:**
- **Workflow order confirmed live**: create/select a **log group**
  first, *then* enable the service log into it — matches the "always

- **Live "Explore Log" confirms the JSON structure exactly as

  capture filter/log name/compartment/log group/retention) is the same
  general pattern across services, not VCN-specific.

### Custom Logs — the Unified Monitoring Agent in depth

- **Sources**: custom applications running on OCI Compute instances,
  or workloads in an external/on-premises environment — same scope
  already documented, now with the deployment mechanics.
- **The Unified Monitoring Agent (Fluentd-based) uses CNCF
  specification version 1** — an open-source data collector providing
  a unified logging layer between the data source and backend systems.
- **Two deployment methods for the agent, with a real shape
  restriction on one of them:**
  1. **Oracle Cloud Agent plugin** — enabled through the same
     Oracle Cloud Agent UI already referenced for the Compute Instance
     Monitoring plugin; here it's called the **Custom Logs Monitoring
     plugin**. **Real, confirmed limitation: NOT supported on ARM-based
     Ampere A1 compute shapes** — a concrete architecture-specific gap
     worth remembering, not a generic "some shapes might not support
     it" hand-wave.
  2. **Manual installation** — used specifically for instances the
     plugin doesn't support (including Ampere A1), or for genuinely
     external/non-OCI systems. **Supported OSes, named explicitly**:
     Oracle Linux 7/8, CentOS 7/8, Ubuntu (various versions), and
     various Windows Server versions.
- **Enabling custom logs is a two-step process, stated explicitly:**
  1. **Install/enable the agent** on the source instances (via plugin
     or manual install) — the agent fetches log data as instructed by
     its configuration.
  2. **Create an Agent Configuration** within OCI Logging itself,
     specifying: which hosts/instances to collect from, which specific
     logs to collect (syslogs, application logs, etc.), and optional
     **parsers**.
- **Log parsing**: splits large log volumes into structured, easily
  interpretable data. **Named parser types**: XML, syslog, JSON, CSV,
  and **auditd**.
- **Agent Configuration — Host Groups component**: if the source is a
  set of Compute instances, you select via a **Dynamic Group** that
  defines the target instance list.
- **A real, required IAM pattern for dynamic groups accessing log
  content — exact policy syntax worth having verbatim**: `allow
  dynamic-group <group-name> to use log-content in tenancy` — the
  dynamic group's own matching rule defines its membership by listing
  specific instance OCIDs or compartment OCIDs. This is the log-content
  equivalent of the dynamic-group-for-resource-principal pattern
  already documented elsewhere in this repo's notes (e.g., the
  Certificate Authority dynamic-group pattern in Note 5) — dynamic
  groups aren't just a security-service concept, they're the general
  mechanism any OCI resource uses to authenticate itself for API calls.
- **Log input types, named**: **Windows Event Log** (with selectable
  event channels — Application, System, Security), or a **log
  directory path** (typically for Linux systems — example given:
  `/var/log/messages`).
- **Log destination fields, same pattern as service logs**:
  compartment, log group, and the specific log object to write into.

### Access & Explore Logs — IAM policy ladder, search, and visualization

- **Two suggested role archetypes, matching the general Monitoring
  pattern already documented**: **Log Administrators** (decide which
  logs are enabled, manage log groups) vs. **Log Viewers** (read-only
  search/view access).
- **Four-level IAM verb ladder for log groups, concrete policy
  examples worth having verbatim:**
  1. **Inspect**: `allow group log-admins-A to inspect log-groups in
     compartment XYZ` — view log group existence only.
  2. **Read**: `allow group log-admins-B to read log-groups in
     compartment XYZ` — read log/log-group **metadata**.
  3. **Use**: `allow group log-admins-C to use log-groups in
     compartment XYZ` — **update** log groups or the logs within them.
  4. **Manage**: `allow group log-admins-D to manage log-groups in
     compartment XYZ` — full lifecycle: create/update/delete log
     groups and logs — the highest tier, strictly superset of the
     other three.
- **A distinct, separate policy for actually reading log content
  (not just log-group metadata)**: `allow group log-viewers-A to read
  log-content in compartment XYZ` — a real, important distinction:
  reading log **group** metadata (the four-tier ladder above) is a
  different permission scope than reading the **content** inside those
  logs.
- **Agent Configuration provisioning needs its own separate policy**:
  `allow group log-admins-E to use unified-configuration in
  compartment XYZ` — a distinct resource type from log groups/log
  content, confirming Agent Configuration is its own IAM-governed
  resource, not implicitly covered by log-group management rights.
- **Dynamic group access for pushing custom logs, restated with a
  named example**: `allow dynamic-group production-fleet to use
  log-content in compartment XYZ` — same `use log-content` pattern
  already documented, now shown at compartment scope rather than
  tenancy-wide, and with `log-content` (not `log-groups`) as the
  resource type — the instances need content-level access to actually
  push log entries, not just log-group-level access.
- **Search — three access paths**: Console, CLI, APIs. **Two Console
  modes**: Basic (simpler queries) and Advanced (complex queries) —
  same Basic/Advanced pattern already established for Monitoring's
  Metric Explorer.
- **Search filtering options, named**: filter by specific **log
  fields**, free-text **string/keyword** search, or **time interval**
  filtering — combinable criteria, not mutually exclusive filter
  types.
- **Log entry exploration features**: expanding a log line shows the
  **full JSON payload**; a **before/after log view** shows the
  immediately preceding and following log lines in sequence — useful
  for understanding an event's surrounding context, not just the
  single matching line in isolation.
- **Search results are exportable to JSON.**
- **Log retention — a real, concrete ceiling worth having precisely**:
  service logs and custom logs share a **maximum retention of 6
  months** — consistent with the "up to 6 months" option already
  documented for individual log retention settings, now confirmed as
  the actual platform-wide ceiling, not just one selectable option
  among many. **Audit log retention is different** — covered in a
  later lesson (flagged as a genuine gap to fill once that lesson is
  reached).
- **Visualization — named chart types**: stacked bar chart, pie chart,
  donut chart, line chart — all built directly from filtered/searched
  log data.
- **Auto-refresh for visualized/filtered log data — two named
  intervals**: **every 5 minutes or every 15 minutes**, for
  near-real-time viewing of the most recent logs without manually
  re-running the search.

### Logging Query Language — components, syntax, and operators

A dense but real, exam-relevant vocabulary layer — the actual query
language behind the search interface already documented above.

- **Access paths**: Console (Basic/Advanced mode, same pattern already
  established), the **Search Logs API**, and **CLI**. Search spans
  **multiple logs and data sources across multiple regions** — not
  scoped to a single log or region by default.
- **CLI syntax, concrete example**: `oci logging-search search-logs
  --search-query "<query>" --time-start <start> --time-end <end>` —
  running a query across the entire tenancy for a given time window.
- **Queries follow a data-flow model**: a query references one or more
  logs, applies filter criteria, and produces a final result set —
  each stage feeding the next, not a single monolithic filter.
- **Five named query components**: log streams, log fields, data
  types, operators, expressions.
- **Log streams — defines WHAT is being searched, three scoping
  levels, syntax confirmed:**
  1. **Compartment-wide**: `search "<compartment-OCID>"`.
  2. **Log group-scoped**: `search "<compartment-OCID>/<log-group-OCID>"`.
  3. **Log object-scoped**: `search
     "<compartment-OCID>/<log-group-OCID>/<log-object-OCID>"`.
  - **Multiple streams can be searched together**, separated by
    commas — e.g., one log object in one compartment/log group PLUS
    an entire different log group in a different compartment, in the
    same query.
- **Log fields — case-sensitive, used to filter within a stream.**
  Ties directly back to the three-section log structure (envelope,
  Oracle metadata, data) already documented: you can filter on the
  envelope's `type` field (e.g., filtering to just VCN flow log
  events), or on `data.*` fields specifically — concrete examples:
  `data.action != 'ACCEPT'` (returns only rejected traffic — same
  REJECT-filtering pattern already documented for VCN flow logs, now
  shown as a not-equal condition against ACCEPT rather than a direct
  match on REJECT), `data.message` (filter by message body content),
  `data.resourceId` (filter to a specific resource's OCID).
- **Data types, four named**: **String** (quoted in single quotes,
  taken literally; supports **wildcard** searches using `*` for
  prefix/partial matching), **Integer** (commonly used for
  timestamps — start/end time), plus Boolean and array/interval types
  referenced more briefly.
- **Tabular operators — six named, each with a specific function:**
  1. **search** — constructs the log stream itself (the entry point
     operator).
  2. **where** — filters the stream using scalar operators (see
     below).
  3. **top** — returns only a specified number of rows.
  4. **sort** — orders the stream by column(s), ascending or
     descending.
  5. **dedup** — removes duplicate rows based on specified columns.
  6. **select** — applies named scalar expressions to shape/project
     the output.
  - **Operators chain together using the pipe (`|`) symbol** — e.g.,
    `search "<compartment>" | where data.level = 'ERROR'` (filter to
    error-level entries), `... | top 3` (last/first 3 rows), `... |
    sort by <field>` (ordering), `... | select <fields>` (projecting
    specific fields only).
- **Scalar operators — four named categories, used inside `where`
  clauses and expressions:**
  1. **Arithmetic** — add/multiply/divide values.
  2. **Boolean — `and`** (all conditions must match) **and `or`**
     (any condition matches).
  3. **Comparison operators** — for comparing values (e.g., `!=`, `=`).
  - **Two full worked examples, concrete syntax:**
    - Search all log objects in a compartment, filter to content
      containing a specific IP address (`10.50.220...`), sort by
      date/time **descending**.
    - Search all logs in a compartment where `data.requestAction`
      equals **DELETE OR PUT** (via `or`), **AND** the target is
      specifically an Object Storage bucket named "production bucket"
      (via `and`), sorted by date/time **ascending** — a real,
      concrete example combining both Boolean operators and a
      comparison operator in one query.

### Connector Hub — core concepts and named use cases

- **What it is**: a fully managed service that **orchestrates data
  movement between a source and a target OCI service**, via configured
  connectors.
- **Three configuration parameters, exactly:**
  1. **Source** — the service holding the data to move (e.g.,
     Logging, when moving log data elsewhere).
  2. **Target** — the destination service that receives, processes,
     and stores the data.
  3. **Task** — an **optional filter** applied to the data before it
     moves from source to target (e.g., only move log data containing
     a specific value) — **multiple filters can be added** to one
     task.
- **End-to-end workflow with Logging specifically, three stages**:
  (1) OCI services emit logs (service/custom/audit) → (2) search and
  analyze via Console/CLI/API using Logging Query Language → (3)
  **take action via Connector Hub**, moving data to one of several
  named targets.
- **Named target services for log data, explicitly listed**: **Object
  Storage**, **Streaming**, **Logging Analytics**, **Monitoring**,
  **Oracle Functions**, **Notifications** — a concrete, closed list of
  what Connector Hub can route Logging data into.
- **Four named use cases, each tied to a specific target:**
  1. **Archival** — transition log data into **Object Storage buckets**
     for long-term storage.
  2. **Metrics integration** — emit log-derived metrics into
     **Monitoring**, enabling dashboards and alarms built on log data,
     not just native service metrics.
  3. **Automated remediation + alerting** — a concrete example: an
     error detected in application logs triggers an **Oracle Function**
     to spin up a standby instance, while **Notifications** separately
     emails the relevant team — two named services working together
     from one triggering log pattern.
  4. **Deeper analysis** — transfer log data into **Logging
     Analytics** for advanced analysis beyond what the base Logging
     search/query interface provides.
- **Third-party integration**: Connector Hub can also route data
  through **Streaming** or **Object Storage** into **Kafka-compatible
  third-party monitoring tools** — a real, named interoperability path
  beyond pure-OCI destinations.

### Audit Logs — retention, structure, and IAM policy scope

- **What it tracks**: all **security-related events** and every **REST
  API call** executed against OCI public API endpoints — automatically
  recorded, no configuration required (consistent with the
  enabled-by-default, cannot-disable behavior already documented).
- **Retention — a real, fixed, non-configurable number worth having
  precisely**: **365 days**, and it **cannot be changed**. This is a
  genuine contrast with service/custom logs' configurable
  30-day-default/up-to-6-month retention already documented — audit
  logs are on a completely separate, fixed retention policy.
- **Retention scope**: a **tenancy-level** setting — applies uniformly
  across **all regions and all compartments**, not configurable
  per-compartment or per-region.
- **Sources of recorded API calls, named explicitly**: OCI Console,
  CLI, SDKs, custom clients, and calls triggered by other **OCI
  services themselves** (service-to-service API calls are captured
  too, not just human/tool-originated ones).
- **Audit log structure, named fields**: header ID, timestamp (when
  the API call was recorded), **source** of the activity, **target
  resource**, **action type** (GET/POST/DELETE/etc.), request
  parameters, response type, and response parameters.
- **A real, concrete processing-delay number worth remembering**: new
  audit events can take **up to 15 minutes** from actual API call
  execution to actually appear in the audit log — not instantaneous,
  a genuine detail for any exam scenario asking about audit-log
  freshness or near-real-time monitoring expectations.
- **Access paths**: Console (as part of the Logging service), APIs,
  and **Java SDK** specifically named (not just "SDKs" generically).
- **Searchable/filterable the same way as other log types**: by user
  account, resource, API action, time range, or custom filters — same
  underlying search mechanism already documented for service/custom
  logs, and displayable in the same JSON format.
- **Named use cases**: diagnostics/troubleshooting (correlating audit
  trails), tracking **resource usage/consumption**, **compliance
  monitoring** (explicitly framed as a top security-operations
  priority for maintaining business standards/reputation), and
  general **security event monitoring** (tracking user activity and
  API-level actions).
- **Two-level IAM policy pattern for viewing audit logs, exact syntax
  worth having verbatim:**
  1. **Tenancy-wide**: `allow group auditors to read audit-events in
     tenancy`.
  2. **Compartment-scoped**: `allow group auditors to read
     audit-events in compartment project-A` — same
     tenancy-vs-compartment scoping pattern already established for
     every other log-related IAM policy in this note.

### OCI Search with OpenSearch — a distinct, new service

**What it is**: a fully managed **OpenSearch** search-and-analytics
service running on OCI — genuinely different from Monitoring/Logging's
own query capabilities; this is a full search engine + visualization
platform, not just log/metric filtering.

- **OpenSearch itself, background**: a community-driven, open-source
  search-and-analytics suite derived from Apache-licensed
  Elasticsearch, created after **Elastic changed its license away
  from open source (April 2021)**. **Oracle partners with AWS** as a
  contributing member of the OpenSearch project — a real,
  cross-vendor collaboration worth noting (not an Oracle-only fork).
- **OpenSearch family has two components**: the **search engine**
  itself (OpenSearch) and **OpenSearch Dashboard**, a data
  visualization/UI layer for exploring search results.
- **Query DSL**: OpenSearch's own search/query language — a flexible,
  **JSON-based** query interface, distinct from Monitoring's MQL or
  Logging's Logging Query Language (three genuinely separate query
  languages across three separate OCI observability services — don't
  conflate them).
- **What OCI Search with OpenSearch manages for you**: deployment,
  provisioning, patching, backups (scheduled to Object Storage),
  resizing, security updates, and reprovisioning on detected
  infrastructure issues — the standard "fully managed" feature set.
- **Ingestion**: via APIs, OpenSearch plugins, or connections; can
  ingest data from **on-premises, cloud, or both**.
- **Named advanced capabilities**:
  - **Semantic search** using a **vector database** — interprets
    language nuance/relationships, not just literal keyword matching.
  - **Vector search at scale**: managing **billions of vectors with
    sub-second query time**, positioned for AI/ML-powered search
    applications.
  - **ML framework integration**: streamlines model management,
    supports **text and image multimodal search**.
  - **Observability use case**: correlates logs, metrics, and tracing
    telemetry for faster incident resolution.
  - **Security use case**: real-time threat detection with
    prepackaged or customizable detection rules, generating alerts for
    incident response teams.
  - **Integration with OCI Generative AI / Generative AI Agent
    services** for natural-language search.
- **Security posture**: role-based access control integrated with
  **OCI IAM** (fine-grained authorization); **data encrypted at rest,
  and backup data encrypted in transit.**
- **Automated HA — concrete number worth having precisely**: HA is
  achieved by deploying **3 or more nodes**, automatically spread
  across **multiple ADs and fault domains** — same
  AD/fault-domain-spread HA pattern already seen for OCI Cache and
  other services in this note set.
- **Built-in monitoring**: out-of-box metrics for CPU/memory
  utilization and network bytes transmitted/received — same "Powerful
  Insight" framing already used for OCI Cache's own monitoring
  section.
- **Core architectural concepts, named explicitly:**
  - **Cluster** — a collection of nodes sharing the same cluster name;
    always has **at least one primary node**, automatically elected
    and automatically replaced if the current primary fails.
  - **Node types, three named**: **Data node** (stores data, handles
    search/aggregation operations), **Leader node** (manages
    cluster-wide operations — monitors node status, routes network
    traffic, handles index creation/deletion, tracks cluster
    membership), **OpenSearch Dashboard node** (serves the dashboard
    UI itself).
  - **Index — three related concepts, don't conflate them**:
    (1) the **index** itself is a sorted data structure pointing to
    where specific data values live, letting OCI Search avoid scanning
    the entire dataset; (2) **index population** is the process of
    actually loading data into that structure — without it, content
    can't be queried at all; (3) indexing **reduces resource
    consumption** (lower CPU/memory) versus an unindexed search
    process.
  - **Dashboard** — the visualization tool and UI surface for
    OpenSearch plugins, enabling real-time interactive dashboards.
  - **Private endpoints** — automatically created per cluster to
    provide access to both the cluster and its dashboard, ensuring all
    network traffic **stays within the cluster's own VCN** — no
    public exposure by default.

### Implementing OCI Search with OpenSearch — prerequisites, IAM setup, and cluster creation

- **Prerequisite resources, same pattern already established for OCI
  Cache**: OCI account with admin privileges, a compartment, a VCN,
  a subnet, and IAM policies — plus a real, service-level requirement
  that **OCI Search must itself have permission to manage the VCN/
  subnet** you designate for it.
- **A real, blocking prerequisite confirmed at cluster-creation time**:
  the Create Cluster wizard's first step explicitly states that on
  first use, you **must create the required IAM policies before the
  service will function at all** — not a suggestion, a hard
  precondition surfaced directly in the Console flow.
- **Full IAM setup chain, confirmed as a real multi-step process (not
  just "create a policy")**:
  1. **Create an Identity Domain** — a container for managing users,
     groups, roles, and security config. **Domain types confirmed
     live**: Free (limited resources — used in this demo), one
     for applications, Premium, or external-user access — a real,
     named tier choice at domain creation.
  2. **Creating a domain auto-creates two default groups**: one for
     **all users**, one for **administrators** — a real, easy-to-miss
     side effect worth remembering; you don't start from zero groups.
  3. **Create a Group** (or use an auto-created one) — a collection of
     users needing the same access.
  4. **Create/assign Users** to that group — confirmed as two separate
     paths: assign a user at group-creation time, or add users
     afterward via the group's own "Assign users to groups" flow.
  5. **Create the Policy**, attached to the **group**, never to
     individual users directly — same "policies attach to groups"
     principle already documented for OCI Cache's IAM setup. The
     Console's **policy builder offers a "Show Manual Editor"** option
     for typing raw policy statements directly, rather than
     constructing them through the guided UI.
- **Cluster creation wizard, five confirmed steps:**
  1. **Configure Cluster** — name, compartment, OpenSearch software
     version, and an administrator contact.
  2. **Configure Security** — create the OCI Search administrator's
     own username/password (distinct from the OCI/IAM administrator
     used to set everything up).
  3. **Configure Nodes** — choose a **node profile**: **Development**,
     **Application Search**, or **Analytics** — a real, named
     three-way choice depending on business need (Development was used
     here specifically to "become familiar with indexing and
     visualization" at low cost/scale). Then configure **each of the
     three node types separately** (data, leader, dashboard) — node
     count, OCPU count, memory, and storage **per node type**, all on
     one scrollable screen.
  4. **Configure Network** — select an existing VCN/subnet (matches
     the pre-created prerequisite) or create new ones.
  5. **Review** — a summary showing combined totals across all three
     node types: total node count, total OCPU, total memory, total
     storage — plus the network selection — before final creation.
- **Post-creation Cluster Details page — real, confirmed
  capabilities**:
  - Administrative actions: **resize, backup, restore**, and others.
  - **RAG pipeline creation** — a genuinely notable, AI-adjacent
    capability built directly into cluster administration. **RAG =
    Retrieval Augmented Generation** — described as providing accurate,
    relevant content to **augment an LLM's** (Large Language Model's)
    output, rather than relying on the LLM's training data alone. This
    positions OCI Search with OpenSearch as infrastructure for

### Organization Management — centralized governance across multiple tenancies

The named OCI counterpart to **AWS Organizations** — this is the mechanism
for anything spanning more than one tenancy, which compartments alone
cannot do (compartments only subdivide *within* one tenancy; see
`AWS to OCI Exceptions.md`'s "OCI compartments have no AWS equivalent" gap
the other direction). Structure: one **Parent Tenancy** holds a single
**UCM (Universal Credits Model) Subscription**; peer **Child** tenancies
(shown as Tenancy-A/B/C/D) attach underneath it, each sharing the parent's
subscription rather than carrying its own.

**Parent's role**, stated as three capabilities:
1. Ability to **manage** [member] tenancies.
2. **Centrally report on cost usage** across all of them.
3. **Enforce governance across the organization** as a whole.

**Child's role**, by contrast:
1. **Isolated environment by default** — a child tenancy is not a
   sub-compartment of the parent; it remains its own fully separate IAM/
   identity root, same as any standalone tenancy (matching the
   Exceptions note's existing point that AWS Organizations member accounts
   stay "separately rooted, not nested containers" — OCI's child tenancies
   work the same way).
2. **Shares subscription of parent** — this is the one thing that actually
   changes: billing/UCM credits flow from the parent, not a separate
   subscription per child.
3. **Scalable up to 50 [child tenancies] by default** — a concrete,
   named default limit worth remembering verbatim if a scenario question
   tests organization sizing.

**Governance rules — exactly three enforceable dimensions, named
explicitly:** the parent tenancy sets enforcements on child tenancies
across **service quotas**, **allowed regions**, and **tagging** — "providing
increased control and assurance" per MyLearn's own framing. Not a generic
"policy" mechanism; these three are the closed set of what a parent can
constrain at the organization level. Distinct from ordinary IAM policy
(which governs *access*, not *quota/region/tag* constraints) — this is a
governance-shape restriction layered above IAM, closer in spirit to AWS
Organizations' Service Control Policies (SCPs) than to a regular IAM policy
statement, though OCI's three named dimensions (quotas/regions/tags) are
narrower and more specific than an SCP's general allow/deny-any-action
model.

**Four named benefits of sharing a subscription this way** (the "why
organize tenancies at all" answer): **Data Isolation** (child tenancies
stay fully separate identity/data roots, per the "isolated by default"
point above — sharing billing doesn't mean sharing data), **Ease of
Consolidated Billing**, **Separate Governance and Security** (each child
keeps its own IAM/policy boundary even while the parent enforces the three
governance-rule dimensions above), and **Central Cost Management**. Data
Isolation and Separate Governance and Security are two distinct benefits,
not one — isolation is about identity/data boundaries staying intact,
governance/security is specifically about IAM/policy staying separately
scoped per child even under shared billing and parent-level quota/region/
tag enforcement.

**Console demo confirms two distinct paths to add a child tenancy, not
one:** "Manage tenancies" lets the parent **invite or create new
tenancies** — invite and create are separate mechanisms, per the
Console's own wording. A **separate "Manage invitations" tool** ("Send or
respond to invitations") exists specifically for the invite path — implying
an already-existing, independent tenancy can be invited to *join* an
organization (accept/decline), versus a brand-new tenancy the parent
creates outright already inside it. The Console's five tools altogether:
Manage tenancies, Map subscriptions (attach one subscription to one or more
tenancies), Manage invitations, Create governance rules — plus an Overview/
Tenancies/Invitations/Subscription Mapping/Governance Rules left-nav
mirroring the same five areas.

**A governance rule for the "service quotas" dimension is a real quota
policy, using the same policy-statement syntax as ordinary OCI service
limits** — the Console demo's example: `set compute-core quota
standard2-core-count to 10 in tenancy`. Confirms governance rules aren't a
separate, bespoke policy language — quota-type rules reuse the standard OCI
quota policy grammar, just authored at the parent and attached across
tenancies rather than written per-tenancy locally.

**Attach scope is a real, explicit choice with a consequential difference**:
"Attach to specific tenancies" (named ones only, via a `Tenancies` picker)
vs. **"Attach to entire organization"** — the Console's own description of
the latter: "Attaches the rule to all current **and future** tenancies that
have joined organization governance." The org-wide option is forward-
looking, automatically covering child tenancies that don't exist yet at
rule-creation time — a real design lever (blanket policy that self-extends
to new members vs. a rule you must remember to reattach to each new child
individually).

**The "create" path in the Console, confirming the create-vs-invite
distinction above**: "Create new tenancy" is explicitly framed as creating
a **child** tenancy — "You are about to create a new child tenancy in your
organization. The created tenancy will consume from your subscription."
Real, named constraints on the form: **tenancy name** — lowercase letters
and numbers only, no spaces, max 25 characters, must start with a letter.
**Home region choice is permanent**: "Your home region cannot be changed
after your tenancy is provisioned" — the same one-time, irreversible
home-region commitment already documented for a standalone tenancy's own
IAM writes (see [[OCI propagation delays]]) applies identically to a child
tenancy created this way; getting it wrong here isn't a config edit, it's
a new tenancy. **Subscription remapping exists as an escape hatch for the
*billing* dimension, but not the home-region one**: "If you would like the
created tenancy to consume from another subscription, you can re-map the
created tenancy to another subscription on the Subscription Mapping page"
— which subscription a child draws from can be changed after creation, but
which region hosts its IAM resources cannot.

**Governance rule attachment at tenancy-creation time is optional and
fully reversible** — the Console's own wording on the "Governance rules"
step: "Select governance rules to attach to the tenancy, or skip and
attach later. **You can always attach or detach rules, or opt the tenancy
out of organization governance later.**" Three real things confirmed here,
not assumed: (1) attaching rules at creation is a convenience, not a
one-time-only commitment — unlike the home region choice a step earlier;
(2) rules can be filtered by **type** (the demo shows `Quota` and
`Allowed_regions` types, e.g. `Rule-01-Compute`, `GR-Quota-01`, `GR-01`)
and by **targeted tenancy**, implying rules are reusable, named objects you
select from rather than authored fresh per tenancy; (3) a tenancy can
**opt entirely out of organization governance** — governance isn't a
permanent, unremovable binding once a child joins the org.
