Note 8 covers *why* and *when* to govern IaC. This note is the mechanics you actually need mid-lab: syntax, provider auth, stack lifecycle, state, and the gotchas that trip up AWS/CloudFormation muscle memory. ## Mental model reset from CloudFormation

CloudFormation is AWS-native JSON/YAML with intrinsic functions (`!Ref`, `!GetAtt`, `!Sub`). Terraform is HCL (HashiCorp Configuration Language) — a **third-party, multi-cloud tool** that OCI wraps as a managed service (Resource Manager). Key differences that will trip you up:
- No `!Ref` — Terraform uses direct resource attribute references: `oci_core_vcn.my_vcn.id`
- No native "stack outputs" concept baked into the template — outputs are explicitly declared in `outputs.tf`
- State is an explicit file/concept you manage (`terraform.tfstate`), not something CloudFormation hides from you
- Terraform is declarative but resource-graph-based — it computes a dependency graph and plans changes; CloudFormation does this too, but Terraform's plan output is more granular per-resource

## The OCI Terraform provider

```hcl
terraform {
  required_providers {
    oci = {
      source  = "oracle/oci"
      version = ">= 5.0.0"
    }
  }
}

provider "oci" {
  tenancy_ocid     = var.tenancy_ocid
  user_ocid        = var.user_ocid
  fingerprint      = var.fingerprint
  private_key_path = var.private_key_path
  region           = var.region
}
```

**Auth methods** (know all four, exam likes scenario-based auth selection):
1. **API key auth** — the block above; user OCID + API key fingerprint + private key. Standard for local/external Terraform runs.
2. **Instance principal** — the running compute instance itself authenticates, no embedded credentials. Use for Terraform running from an OCI compute instance.
3. **Resource principal** — used when Terraform runs *inside* Resource Manager itself (Resource Manager's job execution has its own identity). This is the default and preferred auth when running via Resource Manager rather than CLI.
4. **Security token / session token** — short-lived, from `oci session authenticate`, good for interactive CLI use.

**Exam trap:** when a scenario says the code executes *inside* Resource Manager, the answer is resource principal, not API keys — don't default to the API key pattern just because it's the most commonly documented one.

**Important for the walkthrough below:** when Resource Manager runs your stack, it auto-injects resource principal credentials — your `provider "oci"` block only needs `region`, not `tenancy_ocid`/`user_ocid`/`fingerprint`/`private_key_path`. Those four fields are only needed for the **local CLI setup** path at the end of this note.

## Resource Manager stack lifecycle

A **stack** = one Terraform configuration + its variables + its state, managed as a unit in Resource Manager.

**Configuration source options** (exam tests choosing the right one for a scenario):
- **Folder upload / .zip** — one-time or manual upload, no version control tie-in
- **Git repository** (GitHub, GitLab, Bitbucket) — recommended for team workflows; supports branch/tag selection, enables CI/CD triggers
- **Object Storage bucket** — useful when configuration is generated by a pipeline and stored as an artifact

**Job types:**
- **Plan** — dry run, shows what would change, no infrastructure modified
- **Apply** — executes the plan, modifies real infrastructure
- **Destroy** — tears down everything the stack manages
- **Import** — brings existing, manually-created resources under Terraform management without recreating them (critical for "we built this by hand, now formalize it" scenarios)

**Drift detection** — Resource Manager can detect when real infrastructure has diverged from the last-known state (someone made a console change out-of-band). Running drift detection doesn't fix it; you still need a plan/apply (or import) to reconcile.

## schema.yaml — the Resource Manager UI layer

Unique to OCI (no CloudFormation equivalent in this exact form): a `schema.yaml` file alongside your `.tf` files lets you define a guided, form-based UI in the OCI Console for the stack — grouping variables, adding descriptions, dropdowns, and validation, so someone can run your stack without hand-editing `.tfvars`. Relevant when a scenario mentions self-service infrastructure requests or a "big red button" deployment experience for non-Terraform-fluent teams.

## Variables, state, and secrets

- `variables.tf` — declares inputs; `terraform.tfvars` — supplies values; `outputs.tf` — declares what the stack exposes after apply
- **Sensitive variables**: mark with `sensitive = true` in the variable block — Resource Manager masks these in the Console and job logs. Combine with Vault references rather than hardcoding secrets in `.tfvars` committed to Git.
- **State file access control**: state can contain sensitive data (sometimes including secrets in plaintext depending on resource type) — restrict who can read a stack's state via IAM policy on the stack resource, same principle as restricting S3 backend state access in AWS, but enforced through OCI IAM policies on the Resource Manager stack itself rather than a bucket policy.

## Private network access

If your Terraform code needs to reach resources in a **private subnet** (e.g., a private DB endpoint, an internal load balancer) during apply, Resource Manager needs a **Private Endpoint** configured for the stack — otherwise the job runs in Oracle-managed space with no route to your private VCN resources. This is a common "why did my apply fail to reach X" exam scenario.

## Cost estimation

Resource Manager can show an estimated cost for a plan before you apply it — useful to mention in cost-optimized architecture answers, analogous to (but less mature than) AWS Cost Explorer's what-if tooling.

## Full walkthrough: your first stack, end to end

This deploys the VCN/subnet example entirely through Resource Manager in the Console — no local Terraform install required. It's the fastest path to a real rep in your tenancy.

### Step 0 — IAM check (do this first, or the stack creation will silently fail on permissions)

You need a policy allowing your user/group to manage Resource Manager stacks and jobs, plus manage the actual resources being created. If you're using an admin-equivalent account this is likely already covered; if not, ask whoever owns IAM to confirm a policy along these lines exists for your group:

```
Allow group <YourGroup> to manage orm-stacks in compartment <compartment-name>
Allow group <YourGroup> to manage orm-jobs in compartment <compartment-name>
Allow group <YourGroup> to manage virtual-network-family in compartment <compartment-name>
```

(The third line is specific to this VCN/subnet example — for other labs, swap in the resource family you're creating: `instance-family`, `functions-family`, `cluster-family` for OKE, etc.)

### Step 1 — Get your compartment OCID

Console → Identity & Security → Compartments → click your target compartment (or root/tenancy compartment for a first test) → copy the OCID. You'll paste this in as a variable value in Step 4.

### Step 2 — Prepare the configuration files

Create a local folder, e.g. `first-stack/`, with three files:

**`main.tf`**
```hcl
terraform {
  required_providers {
    oci = {
      source  = "oracle/oci"
      version = ">= 5.0.0"
    }
  }
}

provider "oci" {
  region = var.region
}

resource "oci_core_vcn" "lab_vcn" {
  compartment_id = var.compartment_ocid
  cidr_blocks    = ["10.0.0.0/16"]
  display_name   = "lab-vcn"
  dns_label      = "labvcn"
}

resource "oci_core_subnet" "lab_subnet" {
  compartment_id = var.compartment_ocid
  vcn_id         = oci_core_vcn.lab_vcn.id
  cidr_block     = "10.0.1.0/24"
  display_name   = "lab-subnet"
  dns_label      = "labsub"
}
```

**`variables.tf`**
```hcl
variable "compartment_ocid" {
  description = "Compartment to deploy into"
  type        = string
}

variable "region" {
  description = "OCI region"
  type        = string
  default     = "us-ashburn-1"
}
```

**`outputs.tf`**
```hcl
output "vcn_id" {
  value = oci_core_vcn.lab_vcn.id
}

output "subnet_id" {
  value = oci_core_subnet.lab_subnet.id
}
```

Zip the folder contents (not the folder itself — the `.tf` files should be at the root of the zip) into `first-stack.zip`.

### Step 3 — Create the stack

Console → Developer Services → Resource Manager → Stacks → **Create Stack**.
- **Origin**: "My Configuration"
- Upload `first-stack.zip` (drag-and-drop or folder upload both work; zip is simplest for a first pass)
- **Name**: something identifiable, e.g. `lab-vcn-stack`
- **Create in compartment**: choose where the *stack itself* lives (can be the same compartment as the resources, or a dedicated "infra-stacks" compartment if you want to separate stack management from workload resources)
- **Terraform version**: pick the version matching your `required_providers` block (1.5.x is a safe current default unless your provider needs newer)
- Click **Next**

### Step 4 — Configure variables

Resource Manager auto-detects the variables from your `variables.tf` and prompts for values:
- `compartment_ocid` → paste the OCID from Step 1
- `region` → confirm or override the default

No `schema.yaml` needed for this simple case — Resource Manager builds a basic form automatically from the variable declarations. Click **Next**, review, then **Create**.

### Step 5 — Run Plan

On the stack's detail page: **Terraform Actions → Plan**. This kicks off a job — click into it to watch the log stream live. You'll see Terraform's plan output: `2 to add, 0 to change, 0 to destroy`. Nothing is created yet. Read the plan output before moving on — this is the review gate that replaces "hope it works."

### Step 6 — Run Apply

Same menu: **Terraform Actions → Apply**. Confirm. Watch the job log — you'll see the same two resources actually get created this time, with real OCIDs appearing in the output. When the job finishes with `Succeeded`, go to the stack's **Outputs** tab to see `vcn_id` and `subnet_id` populated.

### Step 7 — Verify in the Console

Networking → Virtual Cloud Networks → confirm `lab-vcn` exists with the subnet inside it. This closes the loop: code → plan → apply → real resource.

### Step 8 — Test drift detection (do this, it's a real exam scenario)

Manually edit something outside Terraform: open `lab-vcn` in the Console and add a freeform tag, or change its display name. Then go back to the stack → **Drift Detection** (under Terraform Actions or a dedicated action depending on Console version). Run it. The job report will flag the resource as drifted, showing what changed outside of Terraform's knowledge.

To reconcile: running **Plan** again will show Terraform's intent to revert the out-of-band change back to what's in your `.tf` files (since that's still the declared desired state). If you actually want to *keep* the manual change, you'd update your `.tf` file to match it instead, or use **Import** on the specific attribute — reconciliation direction is a real judgment call, not just "always re-apply."

### Step 9 — Clean up

**Terraform Actions → Destroy**. Confirm. This tears down both the subnet and VCN. Useful habit for lab work — don't leave lab resources running against your tenancy's quota/cost.

## Optional: running Terraform locally instead of (or before) using Resource Manager

Some people prefer testing locally before committing to a Resource Manager stack. This needs actual credentials since there's no resource principal outside Resource Manager:

1. **Install Terraform CLI**: `brew install terraform` (Mac) or download from terraform.io
2. **Generate an API signing key**: Console → your user profile (top right) → **API Keys** → **Add API Key** → generate a key pair. Oracle shows you a config file snippet with `user_ocid`, `tenancy_ocid`, `fingerprint`, and `region` — copy it.
3. Save the downloaded private key locally (e.g. `~/.oci/oci_api_key.pem`) and lock down permissions: `chmod 600 ~/.oci/oci_api_key.pem`
4. Fill in the full `provider "oci"` block from the "OCI Terraform provider" section above using those values (this is the version *with* `user_ocid`/`fingerprint`/`private_key_path` — the local CLI has no resource principal to fall back on)
5. Run `terraform init` (downloads the OCI provider plugin), then `terraform plan`, then `terraform apply` — same commands, same `.tf` files, just executing on your machine instead of inside Resource Manager

This local path is useful for fast iteration while writing code, but for the actual exam and for team workflows, Resource Manager (Steps 1–9 above) is the pattern you'll be tested on and the one that matches real governance practice (centralized state, IAM-controlled execution, no credentials on laptops).

## First-timer gotchas

- **Terraform version mismatch**: if your `required_providers` block pins a version incompatible with the Terraform CLI version you selected for the stack, Plan will fail immediately with a version error — check both match.
- **Variable prompts blank on Configure step**: means `variables.tf` wasn't at the zip root — Resource Manager can't find it if it's nested inside a subfolder.
- **Compartment quota errors on Apply**: some compartments have service limits; if Apply fails with a limit error, check Governance → Limits, Quotas and Usage before assuming it's a code problem.
- **Job seems stuck**: Resource Manager jobs typically run in under a minute for simple resources like this; if it's spinning past a few minutes, check the job log for an API throttling or auth error rather than waiting it out.
