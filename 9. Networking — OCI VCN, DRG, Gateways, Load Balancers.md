### AWS-to-OCI networking translation

| AWS memory anchor | OCI service or pattern | OCI-specific distinction |
| --- | --- | --- |
| VPC | Virtual Cloud Network (VCN) | A VCN contains subnets, route tables, security lists, DHCP options, gateways, DNS, and NSGs. Rebuild the traffic path; names alone are not a migration design. |
| Public/private subnet | Public/private subnet | In OCI, a public subnet permits public IP assignment; internet access also requires a route to an Internet Gateway and security rules. A private subnet does not allow public IPs. |
| Security group / NACL | Network Security Group (NSG) / security list | NSGs protect selected VNICs/resources; security lists are subnet-wide. Either OCI rule type can be stateful or stateless—do not import AWS's SG=stateful/NACL=stateless rule. |
| Internet Gateway / NAT Gateway | Internet Gateway (IGW) / NAT Gateway | IGW supports public-IP traffic; NAT Gateway gives private instances initiated outbound access, with no unsolicited inbound connections. Both still need correct subnet route tables and rules. |
| VPC endpoint / PrivateLink | Service Gateway / private endpoint / Private Access Channel | Service Gateway privately reaches supported Oracle services; OCI's private-access patterns vary by service. There is no single AWS endpoint-type mapping. |
| Direct Connect / site-to-site VPN | FastConnect / Site-to-Site VPN | Both attach through a DRG. Choose private connectivity versus IPSec over internet based on throughput, latency, redundancy, and recovery requirements. |
| Transit Gateway | Dynamic Routing Gateway (DRG) | DRG is a virtual router. Its attachment route tables and route import/export distributions determine which attached networks communicate. |
| VPC peering | Local Peering Gateway (LPG), Remote Peering Connection (RPC), or DRG transit | Use LPG for same-region VCN peering and RPC/DRG for cross-region designs. Account for routing and tenancy policies; CIDRs cannot overlap. |
| ALB / NLB | OCI Load Balancer / Network Load Balancer | OCI Load Balancer provides L7/L4 features; Network Load Balancer distributes using L3/L4 data. Select by protocol, source preservation, and application features. |
| Route 53 routing/failover | OCI DNS, Traffic Management steering policies, Health Checks | Model TTL/caching and the steering policy. Traffic Management can use health checks and supports failover, load-balance/weighted, geolocation, and AS-path steering patterns. |
| Elastic Fabric Adapter | OCI Cluster Network / RDMA-capable Compute shapes | Not a direct product mapping. For HPC, design around OCI compute shape, RDMA/cluster networking, placement, and storage requirements. |

## 1. VCN, CIDR planning, and subnet fundamentals

- A **VCN** is OCI's isolated virtual network. Design non-overlapping IPv4/IPv6 CIDRs before peering, DRG attachment, hybrid connectivity, or future expansion.
- Subnets are regional within a VCN. A subnet can have IPv4 and optionally IPv6 ranges; IPv6-enabled subnets use a /64 prefix.
- OCI reserves the **first two and last IP address** of each subnet CIDR for Networking. Do not apply AWS's five-address reservation calculation.
- A subnet is a unit of configuration: route table, security lists, and DHCP options. It can use default VCN components or dedicated components.
- A **public subnet** allows public IPs on its VNICs. A **private subnet** prohibits public IP assignment. Internet reachability still depends on the route table, gateway, and security rules.
- Use distinct subnets by trust zone/function: public ingress, private application, database, management, and endpoint/inspection paths. Do not make a subnet public merely because it needs outbound package access.

### Baseline three-tier pattern

1. Internet-facing OCI Load Balancer in a public subnet; only intended listener ports are allowed.
2. Application instances in private subnets, reachable only from the load balancer/app-tier NSG as required.
3. Database in private subnets, reachable only from the application-tier NSG on database ports.
4. Use Bastion for time-bound operator access; avoid public SSH/RDP.
5. Private workloads reach the public internet through NAT Gateway and Oracle services through Service Gateway when supported.

## 2. Routing and gateways

A route rule matches a destination CIDR or service label and names the next-hop target. A security rule is not a route rule: both must permit the desired path.

| Requirement | OCI route target/pattern | Design note |
| --- | --- | --- |
| Internet access to/from a public IP | Internet Gateway | Subnet route table needs the route; public IP and ingress/egress rules are also required. |
| Outbound internet from private instances | NAT Gateway | Private instances initiate connections; unsolicited inbound connections are not allowed. Use it for updates/third-party endpoints, not Oracle services reachable through Service Gateway. |
| Private access to supported Oracle services, such as Object Storage | Service Gateway | Route the Oracle Services Network service label to the Service Gateway; traffic does not require IGW or NAT. |
| On-premises or other VCNs through a hub | DRG | Configure both VCN route tables and DRG attachment route tables/distributions. |
| Central traffic inspection | Network Firewall endpoint | Route tables must explicitly steer the selected flows through the endpoint; avoid asymmetric return routing. |
| Controlled private administration | Bastion | Temporary managed SSH sessions to private resources; not a substitute for NSGs, host firewall, or IAM. |

### NAT and service-gateway traps

- OCI NAT Gateway is managed and highly available. It is **not** an instance deployed in an availability domain or fault domain.
- A NAT Gateway permits connections initiated from private resources; it cannot make a private instance publicly reachable.
- Prefer a **Service Gateway** for supported Oracle services. It avoids sending that traffic to an internet/NAT gateway.
- OCI prevents certain route-table combinations that would create asymmetric routing for Oracle-services traffic. Validate the exact service-label/IGW/Service-Gateway path before deployment.
- Gateway attachment alone changes nothing. Associate the correct route table with each subnet.

## 3. Network security controls

### NSGs versus security lists

- **NSG:** rules apply to the VNICs/resources made members of the group. This is normally the better least-privilege control for application tiers.
- **Security list:** rules apply to all VNICs in its associated subnet. Use for subnet-wide baseline controls or when an NSG cannot be applied.
- OCI security-list and NSG rules can each be **stateful or stateless**. With a stateful rule, return traffic is automatically allowed; with a stateless rule, write explicit ingress and egress rules for both directions.
- Both are additive allow controls; neither provides an AWS NACL-style ordered deny rule set. For advanced inspection/filtering, consider Network Firewall and route design.
- Also configure host firewalls and application authentication. OCI network rules do not override guest OS controls.

### Least-privilege example

- Load balancer NSG: allow TCP 443 from approved internet sources (or WAF/origin path).
- Application NSG: allow only application listener traffic from the load balancer NSG; allow narrowly scoped egress.
- Database NSG: allow database port only from the application NSG.
- Management NSG: allow only Bastion/admin paths, not broad internet access.

## 4. Private connectivity, peering, and transit

### Peering selection

- **Local peering (LPG):** private connectivity between VCNs in the same region.
- **Remote peering (RPC):** connects DRGs in different regions; can support cross-region/tenancy architectures with the required policies.
- **DRG transit:** choose for hub-and-spoke, many-VCN, hybrid, or centralized-inspection patterns. Do not assume all DRG attachments can communicate by default—design the route tables and route distributions.
- Peer/attached VCN CIDRs must not overlap. Plan CIDRs early; translation/inspection patterns do not erase all routing ambiguity.
- Model return paths. A route is only valid when the forward and return directions are permitted and unambiguous.

### DRG architecture

A DRG can attach VCNs, Remote Peering Connections, Site-to-Site VPN IPSec tunnels, and FastConnect virtual circuits.

- Every attachment uses an associated DRG route table for traffic entering the DRG.
- DRG route tables hold static and dynamically imported routes.
- Import/export route distributions control which attachment prefixes are shared. Use separate route tables to isolate production, shared-services, development, and on-premises paths.
- Use BGP for dynamic hybrid routing where appropriate. ECMP can load-balance flows across FastConnect circuits or across IPSec tunnels, but not a mixed circuit/tunnel set.
- A VCN attaches to one DRG. This makes DRG topology and route segmentation an intentional architectural decision.

### Hybrid connectivity

- **Site-to-Site VPN:** encrypted IPSec over the internet; deploy redundant customer equipment/tunnels and use BGP where appropriate. Good for rapid connectivity and as a FastConnect backup, subject to performance expectations.
- **FastConnect:** private dedicated connectivity between the customer edge and OCI DRG through virtual circuits. Design redundancy across locations/providers/edge equipment according to availability requirements.
- FastConnect is private connectivity, not automatically encrypted. Add IPSec overlay encryption when the requirement calls for encryption in transit.

## 5. Load balancing and application ingress

### Select the service by traffic requirement

| Requirement | OCI selection | Reasoning |
| --- | --- | --- |
| HTTP/HTTPS, TLS termination, host/path routing, session/application controls | Load Balancer | L7 capabilities and backend health checks. Place in public or private subnets according to exposure. |
| High-performance TCP/UDP/IP traffic, source-IP preservation, minimal L3/L4 distribution | Network Load Balancer | Operates from Layer 3/4 data; choose when L7 processing is not required. |
| Global DNS steering / active-passive / weighted rollout | DNS Traffic Management + Health Checks | DNS-level decision; TTL and resolver caching mean it is not instantaneous failover. |
| Web attack protection | WAF in front of appropriate origin | WAF is L7 protection, not a substitute for an LB, NSG, or Network Firewall. |

- A Load Balancer design needs listeners, backend sets, backend servers, health-check policies, and subnet security rules.
- Health checks remove unhealthy backends from rotation; define an endpoint that actually represents application readiness, not merely open TCP.
- For high-volume Load Balancer traffic, Oracle recommends stateless rules for load-balancer subnets. Ensure both directions are explicitly allowed where stateless rules are used.
- Use public load balancers for internet ingress and private load balancers for internal-only service exposure. This is an architectural choice, not only a DNS setting.

## 6. DNS, Traffic Management, and health

- OCI DNS hosts public and private zones. Use private views/resolvers for private naming architectures.
- **Traffic Management steering policies** make DNS answers based on policy, endpoint health, geography, ASN/path, or weighted distribution.
- Use **Failover** steering with health checks for active-passive endpoints. Use **Load Balancer** steering for weighted traffic distribution/canary designs.
- Health Checks test endpoint availability; they do not delete DNS records. Resolver/client caching remains bounded by TTL, so set recovery objectives and TTL before an outage.
- For multiregion applications, combine steering policy, regional load balancers, health checks, data replication, and explicit RTO/RPO. DNS routing alone is not DR.

## 7. OCI networking design checklist

- [ ] CIDRs are non-overlapping for all VCNs, on-premises networks, and planned peers.
- [ ] Each subnet has a defined route table, security controls, DNS/DHCP needs, and public/private purpose.
- [ ] Private outbound paths distinguish NAT Gateway from Service Gateway.
- [ ] NSGs express tier-to-tier least privilege; security-list rules are only subnet-wide baselines.
- [ ] DRG attachment route tables and import distributions explicitly allow required paths and isolate prohibited ones.
- [ ] Hybrid links and customer edge devices meet redundancy, BGP, encryption, throughput, and failure-recovery requirements.
- [ ] Load balancer health checks, backend security rules, TLS, and WAF/origin restrictions are tested end-to-end.
- [ ] DNS traffic steering's TTL behavior matches the application failover objective.

## Recall / design exercises

- [ ] A private application subnet needs OS updates and Object Storage access, but must never expose public IPs. Draw its routes and explain NAT Gateway versus Service Gateway.
- [ ] Two VCNs, on-premises, and a shared-services VCN need controlled hub connectivity. Define DRG attachments, route tables, and route distributions that prevent development-to-production transit.
- [ ] Translate an AWS question that says “security groups are stateful and NACLs are stateless.” Explain the OCI answer and how return traffic changes for stateless NSG/security-list rules.
- [ ] Design active-passive web failover across two regions. Identify what DNS Traffic Management/Health Checks handle and what database/data replication must handle separately.
- [ ] An app needs client source IP preservation for TCP traffic. Choose OCI Network Load Balancer versus Load Balancer and justify the choice.
